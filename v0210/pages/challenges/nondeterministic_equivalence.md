# Equivalence of nondeterministic queries

> What does "equivalent" mean when a query can legitimately return different results on the same database, run to run, and how do we check it without false counterexamples or false agreement?

<p class="tags"><a class="tag" href="#/tags/bounded">bounded</a><a class="tag" href="#/tags/cex">cex</a><a class="tag" href="#/tags/nondet">nondet</a><a class="tag" href="#/tags/theory">theory</a></p>

## Challenge
Many real queries don't have one correct output. Two such queries can be semantically equivalent (each is a correct implementation of the same intent) and still return different results on the same database, or even differ from themselves on a second run. The task: define equivalence for these queries, check it, and keep nondeterminism from corrupting the certified signals every other challenge relies on.

**Sources of nondeterminism:**

| Source | Example | What varies |
|---|---|---|
| Row order without `ORDER BY` | `SELECT * FROM t` | Presentation only; harmless under bag comparison, but two translation benchmarks score displayed order ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.1, [PARROT](#/papers/zhou2025parrot "PARROT: A Benchmark for Evaluating LLMs in Cross-System SQL Translation (2025)") §4; [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection)) |
| Ties under `ORDER BY` + `LIMIT` / `OFFSET` / `FETCH` | "top-1 by salary" when two people tie | *Which* rows are returned |
| Order-dependent [window functions](#/glossary/window-function) over ties | `ROW_NUMBER`, `LAG`, `FIRST_VALUE`, `ROWS` frames | Values assigned to tied rows |
| Arbitrary row choice | `DISTINCT ON`; MySQL non-aggregated columns in `GROUP BY` (with `ONLY_FULL_GROUP_BY` off); SQLite bare columns (with `MAX`/`MIN`, only on ties: sqlite.org/lang_select.html, accessed 2026-10-01) | Which row's values appear |
| Order-sensitive aggregates without an order | `GROUP_CONCAT`, `string_agg`, `array_agg`, `json_agg` | Element order inside a value |
| Volatile functions and sampling | `random`, `now`, `uuid`, sequences, `TABLESAMPLE`; LLM operators such as BigQuery's `AI.IF` ([The Stochastic Shift](#/papers/alrashed2026stochastic "The Stochastic Shift: A New Evaluation Paradigm for Text-to-SQL with AI Operators (2026)") §2) | Values, or which rows |
| Errors under an unspecified evaluation order | SQL doesn't fix the order of `AND`/`OR` operands, so a query whose skipped operand would raise "can succeed or fail depending on the chosen plan" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §6.4, PDF p. 34) | Whether the query errors or returns rows |
| Floating-point aggregation | `SUM`/`AVG` over floats with parallel plans | Low-order digits |
| Engine and configuration defaults | `NULLS FIRST/LAST`, collation | Order or values between engines and settings; the list of such differences is in [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection) |

**Candidate definitions of equivalence:**

- **Same output sets.** Q1 ≡ Q2 if, on every database, the sets of outputs each can legally produce are equal. This is the strongest definition. Logos's FormalSQL semantics works this way: sorting "admits every bag-preserving list" consistent with the sort keys, so ties stay nondeterministic ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") §3.2). An early form of the idea that a query denotes a set of possible lists is Coburn and Weddell's "possible results semantics" ([A logic for rule-based…](#/papers/coburn1993logic "A logic for rule-based query optimization in graph-based data models (1993)") §3, printed pp. 128–129).
- **Refinement.** Q2 refines Q1 if every output Q2 can produce is one Q1 could also produce. This is what a *rewrite* needs: an optimizer may pick any legal output, so a rewrite that narrows the choices is correct even though the two aren't "equal". It's one-directional, unlike equivalence. Coburn and Weddell already define refinement this way: `(Ref E1 E2)` holds when ⟦E2⟧ ⊆ ⟦E1⟧ ([A logic for rule-based…](#/papers/coburn1993logic "A logic for rule-based query optimization in graph-based data models (1993)") Def. 4.1, printed p. 136).
- **Equivalence where deterministic.** Compare only on databases where both queries are deterministic (no ties, volatile values fixed). This is weaker, but it's the definition ordinary counterexamples already check.
- **Equivalence after normalization.** Compare results after sorting rows, rounding floats and sorting aggregated lists. It's cheap, and LASER sorts results before hashing in its data-generation phase ([LASER](#/papers/li2026laser "LASER: A Data-Centric Method for Low-Cost and Efficient SQL Rewriting based on SQL-GRPO (2026)") §4.2). It removes presentation-only differences but not *which tied rows* were chosen. Slivinskas et al. go one step further for `ORDER BY`: two results are equivalent if they are equal as multisets and their projections on the sort keys are equal as lists ([A Foundation for Conventional…](#/papers/slivinskas2001foundation "A Foundation for Conventional and Temporal Query Optimization Addressing Duplicates and Ordering (2001)") §5.5, PDF p. 17), so permutations within ties count as equal; they state it for "some temporal variants of SQL" queries with `ORDER BY` (§6, PDF p. 18). Top-k can still pick different tied rows.

Which definition applies depends on the use: rewrite verification wants refinement, [text-to-SQL](#/glossary/text-to-sql) evaluation and the round-trip loop arguably want overlapping output sets ("could these be the same answer?"), and benchmarks must state theirs. For text-to-SQL, Renggli et al. ask for a match function that compares "against all possible candidate results" ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)") §6.1) and say no evaluation method yet handles top-k questions answered by any k tied rows (§5.3.2). Some benchmarks state their notion: BIRD compares results as sets ([BIRD](#/papers/li2023bird "Can LLM Already Serve as A Database Interface? A BIg Bench for Large-Scale Database Grounded Text-to-SQLs (2023)") App. B.7), and ReViSQL marks each training item set-, subset- or list-graded, where subset grading checks an any-k answer against the gold's full result ([ReViSQL](#/papers/zhu2026revisql "Human-Level Text-to-SQL via Reinforcement Learning on Verified Data, Without Pipeline Engineering (2026)") §3.3.4). SQLDriller's dataset repairs pick the all-ties reading: they replace a `LIMIT 1` gold over tied extremes with `RANK … = 1`, since `LIMIT 1` "may choose different records in different situations" ([SQLDriller](#/papers/yang2025sqldriller "Automated Validating and Fixing of Text-to-SQL Translation with Execution Consistency (2025)") §6.4, Tab. 7, PDF pp. 20–21). Often, though, the notion is only in the code ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)") §6.2.2), and readers then misdescribe it, as Renggli et al. do for BIRD.

## Why it matters
Nondeterminism decides whether a "different" verdict, an execution-match score or a reward can be trusted at all, so a solution pays off in every search area rather than in one.

- **Labels and scores that are wrong today.** In text-to-SQL, the authors of [Evaluating Cross-Domain Text-to-SQL Models…](#/papers/pourreza2023evaluating "Evaluating Cross-Domain Text-to-SQL Models and Benchmarks (2023)") count a large share of Spider, Spider-DK and BIRD queries that can return tied rows, so a correct prediction that returns a different tied row is scored wrong (§1, Tab. 1). These are queries that *can* tie, not ties observed, and the same authors suspect the test data has few ties (§6.1), so today's main cost may be false agreement rather than false refutation (our reading). The same false "different" enters refutation labels, RL rewards and differential tests whenever a checker compares one run of each query.
- **A filter in use misses it.** SQL-Zero's determinism filter lets ties under `ORDER BY … LIMIT` through, so [self-play](#/glossary/self-play) training on SQL can reward or punish a tie-break.
- **Rewrites need a weaker notion than equality.** A correct optimizer rewrite may narrow which tied rows come back. A checker that demands equality rejects it, and one that compares a single run can accept a rewrite that is wrong on another plan. Refinement (above) is the notion rewrite verification needs; Coburn and Weddell justify replacing an unordered request by an [index](#/glossary/index-database) scan this way, since the scan's order is one of the request's possible results ([A logic for rule-based…](#/papers/coburn1993logic "A logic for rule-based query optimization in graph-based data models (1993)") §3, printed p. 128).
- **Not only SQL.** In code, the Monkeys authors report test suites that accept only one of several correct outputs, and candidate solutions over unordered sets that pass only on "lucky" runs ([Large Language Monkeys](#/papers/brown2024monkeys "Large Language Monkeys: Scaling Inference Compute with Repeated Sampling (2024)") §4.2.1–4.2.2); Absolute Zero keeps only deterministic programs "to keep the verifier simple" ([Absolute Zero](#/papers/zhao2025absolutezero "Absolute Zero: Reinforced Self-play Reasoning with Zero Data (2025)") §3.3.3). These are this challenge's false refutation, false agreement and pre-check outside SQL (our reading).

  | Area | Effect |
  |---|---|
  | [Query equivalence](#/glossary/query-equivalence) | Needs a definition for queries with several correct outputs. Few provers model them; Logos's semantics, which gives a query the set of its legal ordered outputs, is one that does |
  | Rewrite rules | A correct rewrite may legally pick different tied rows, so rules should be checked for refinement, not equality |
  | Dialect translation | Engines break ties, order NULLs and collate differently, so differential tests raise false alarms (NULL ordering and mixed-type comparisons are PolySQL's named residual false negatives, [PolySQL](#/papers/perlitz2026polysql "PolySQL: Scaling Text-to-SQL Evaluation Across SQL Dialects via Automated Backend Isomorphism (2026)") §8) |
  | LLM methods on checkable problems (benchmarks) | False refutations become wrong labels and noisy rewards |
  | Text-to-SQL | [Execution accuracy](#/glossary/execution-accuracy) on tied top-k answers marks right queries wrong, or wrong ones right |
  | the loop | The writer or describer gets blamed for a tie-break |

**Size of the gain:** enabler, measured as the share of "different" verdicts, benchmark labels and rewards that come from a tie-break or a volatile value rather than from a real difference. The gain shows up in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth), [Text-to-SQL can't be verified against intent](#/challenges/text_to_sql_verification), [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection), [Refuting faulty rewrite rules](#/challenges/faulty_rewrite_rules), [Verified query speedups](#/challenges/verified_query_speedup) and the [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop). SpotIt reports what share of its counterexamples survive re-execution ([SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)") §5, Tab. 2) but doesn't split the spurious ones into nondeterminism and over-approximation (§4.2), so measuring that share is a first result in itself. This is our estimate.

## Verifiable signal
Weak by default. It becomes a [certificate](#/glossary/certificate) in these ways:

1. **Tie-free counterexamples.** Build the [counterexample database](#/glossary/counterexample-database) so that sort keys are unique and volatile values are fixed. Both queries are then deterministic on it, and an ordinary execution check is a valid certificate. This is the cheapest route, but only for pairs that also differ without ties: `ORDER BY x DESC LIMIT 1` and `WHERE x = (SELECT MAX(x) …)` differ only when the maximum is tied (our probe), so a tie-free database can't separate them, and route 2 must.
2. **Order-insensitive differences.** The outputs differ in something no tie-break can change: row count, the multiset of a column not involved in the tie, or a value that appears in no tied row. ParSEval's motivating counterexample is one: the top rating is tied, and the `LIMIT 1` query returns one row whichever it picks, against the other query's two ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §1, Fig. 2).
3. **Exhaustive outcomes on small databases.** Enumerate all legal outputs of Q1 (for example, every tie-break permutation) and show that Q2's output isn't among them. This is feasible because counterexamples are usually tiny. Logos does this by proof: it accepts non-equivalence only through a countermodel that exhibits "a legal outcome on one side that no legal outcome on the other can match", not through one execution in an engine ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") §1, §4). TRAF evaluates each MSSQL and Oracle SQLancer++ query under two evaluation orders "to avoid spurious mismatches" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §6.4), a small case of the same idea for errors.
4. **Volatile functions as parameters.** Replace `now`/`random` with a shared input value, so both queries see the same value and become deterministic.
5. **Order-aware proofs** for the *equivalent* side.

The gate that decides when a "different" verdict needs one of these routes is the determinism pre-check.
