# Equivalence under schema constraints

> Queries that look different can be equivalent because of keys, foreign keys, NOT NULL or CHECK constraints, and a checker has to know about them.

<p class="tags"><a class="tag" href="#/tags/cex">cex</a><a class="tag" href="#/tags/prove">prove</a><a class="tag" href="#/tags/smt">smt</a></p>

## Challenge
Decide equivalence relative to the databases the schema actually allows, not relative to all databases. A counterexample that violates a constraint is not a valid refutation. Shrinking one can break a foreign key: RATest's sub-instances keep keys, NOT NULL and functional dependencies, but each foreign key becomes an implication ([RATest](#/papers/miao2019ratest "Explaining Wrong Queries Using Small Examples (2019)") §2.1, §4.3).

## Why it matters
- **Refutations that hold on legal databases.** A checker that ignores constraints refutes equivalent queries with databases the schema forbids. The VeriEQL authors measured this: with [integrity constraints](#/glossary/integrity-constraint) dropped, most of the refutations VeriEQL reported on LeetCode came from databases that violate them ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.3; App. C.1). Those constraints were written by hand for each LeetCode problem (§6.1). Such refutations become wrong labels and rewards. ReViSQL cuts the RL reward when VeriEQL refutes a query ([ReViSQL](#/papers/zhu2026revisql "Human-Level Text-to-SQL via Reinforcement Learning on Verified Data, Without Pipeline Engineering (2026)") §4.2, App. D; [Weak checkers get exploited](#/challenges/weak_checker_exploitation)), and its code gives VeriEQL column types only, with no keys or NOT NULL (project `ReViSQL` @ 9fac371, `verieql_helper.py`; our reading).
- **Proofs for rewrites that need a key.** Some real rewrites hold only under constraints; how many depends on the source. About a third of WeTune's useful rules carry a Unique, NotNull or RefAttrs condition ([WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)") Tab. 7, our count), and its GitLab examples are on primary-key columns (Tab. 1). One of the rules the QO-Verify authors distill from LLM rewrites is stated over a primary-key–foreign-key join ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §3.3, Fig. 5). SlabCity seeks queries equivalent on databases meeting the constraint ([SlabCity](#/papers/dong2023slabcity "SlabCity: Whole-Query Optimization Using Program Synthesis (2023)") Def. 3.1, PDF p. 4), arguing rule-based rewriters exploit constraints largely through local changes (PDF p. 3). SPES encodes keys only as two normalization rules, a self-join on a primary key and grouping on a primary key ([SPES](#/papers/zhou2020spes "SPES: A Symbolic Approach to Proving Query Equivalence Under Bag Semantics (2022)") §4.2, §7.4), so none covers joins of different tables ([QED](#/papers/wang2024qed "QED: A Powerful Query Equivalence Decider for SQL (2024)") §1), and the QED authors report that none applies to an aggregate push-down from Calcite's tests that needs a key (§2). On the other side, among the minority of Calcite test pairs UDP can process, few need a constraint ([UDP](#/papers/chu2018udp "Axiomatic foundations and algorithms for deciding semantic equivalences of SQL queries (2018)") §6.2).
- **Other challenges inherit it.** "Different" labels in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth), refutations in [Refuting faulty rewrite rules](#/challenges/faulty_rewrite_rules) and proofs in [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) are only as right as the constraints the checker was given.

**Size of the gain:** incremental, measured as the share of refutations that hold on databases the schema allows, plus the share of constraint-dependent rewrites that get a proof. Declared keys, foreign keys and NOT NULL are already encoded by VeriEQL ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §4.3) and modelled by QED ([QED](#/papers/wang2024qed "QED: A Powerful Query Equivalence Decider for SQL (2024)") §3.3), so most of the gain is in passing them to pipelines that drop them; for implicit constraints, the SpotIt+ authors hypothesize that most mined constraints make counterexamples more realistic rather than remove them ([SpotIt+](#/papers/tremante2026spotitplus "SpotIt+: Verification-based Text-to-SQL Evaluation with Database Constraints (2026)") §V-A). This is our estimate.

## Verifiable signal
A [counterexample database](#/glossary/counterexample-database) is checked by loading it into an engine *with the constraints and column types declared*. The engine then rejects illegal counterexamples.
