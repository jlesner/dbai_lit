# Query equivalence: prove or refute

> Decide whether two SQL queries return the same result on every database, and back the answer with a certificate.

## Challenge
Given Q1, Q2 and a schema, answer *equivalent* (with a proof), *different* (with a [counterexample database](#/glossary/counterexample-database)) or *unknown*.

The question must say what "same result" means: set, bag or [list semantics](#/glossary/list-semantics) ([EQUITAS](#/papers/zhou2019equitas "Automated verification of query equivalence using satisfiability modulo theories (2019)") §3; [QED](#/papers/wang2024qed "QED: A Powerful Query Equivalence Decider for SQL (2024)") §3.2; [Mediator](#/papers/wang2017mediator "Verifying Equivalence of Database-Driven Applications (2017)") §10), where list equivalence implies bag and bag implies set ([A Foundation for Conventional…](#/papers/slivinskas2001foundation "A Foundation for Conventional and Temporal Query Optimization Addressing Duplicates and Ordering (2001)") Thm. 4.1, PDF p. 13), the set of legal ordered outputs when ties exist ([Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence); [Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") §3.2), how NULLs behave, since forms that two-valued logic calls equivalent, such as NOT IN and NOT EXISTS subqueries, can differ once NULLs occur ([Formal semantics of SQL queries](#/papers/negri1991semantics "Formal semantics of SQL queries (1991)") §4.2, PDF pp. 17–19; [A Formal Semantics of SQL Queries](#/papers/guagliardo2017semantics "A formal semantics of SQL queries, its validation, and applications (2017)") Example 1, PDF p. 2), and every database or only those the schema allows ([Equivalence under schema constraints](#/challenges/schema_constrained_equivalence)). Until it does, a wrong verdict and a different definition look alike: SQLSolver and SPES called a Calcite pair equivalent whose outputs differ in column order, SPES did the same for a pair equivalent only under [set semantics](#/glossary/set-semantics), and both groups acknowledged these as errors ([Verifying SQL Queries using…](#/papers/mohamed2024cvc5sql "Verifying SQL Queries using Theories of Tables and Relations (2024)") §5).

## Why it matters
This check sits under every other challenge: rewriters, translators and [text-to-SQL](#/glossary/text-to-sql) systems all produce a query that is supposed to mean the same as another one. A sound answer is what lets their users trust that query.

- **DBAs and tuning tools adopting LLM rewrites.** In the QO-Verify study, a large fraction of LLM rewrites returned different results from the original on the given database, which the authors count as incorrect ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §1, §4.2). They call checking equivalence "a major impediment that limits the practical adoption of LLM-based rewriting today" (abstract). The payoff is argued in [Verified query speedups](#/challenges/verified_query_speedup) and [Refuting faulty rewrite rules](#/challenges/faulty_rewrite_rules).
- **Text-to-SQL training data and benchmarks.** SQLDriller uses a SQL equivalence checker to get counterexample databases that tell candidate queries apart, and with them detects and fixes wrong NL-to-SQL mappings in training datasets ([SQLDriller](#/papers/yang2025sqldriller "Automated Validating and Fixing of Text-to-SQL Translation with Execution Consistency (2025)") abstract). In its checker chain only SQLSolver's "equivalent" is a proof, so a stronger checker turns more labels into [certificates](#/glossary/certificate): [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth), [Text-to-SQL can't be verified against intent](#/challenges/text_to_sql_verification).
- **Engine builders.** DBMS [test oracles](#/glossary/test-oracle) generate equivalent query pairs and report a bug when their results disagree ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") abstract). Argus has an LLM propose such pairs as query skeletons and keeps a pair only if a SQL equivalence prover proves it (abstract; SQLSolver, §1). Its authors note that the provers' limits omit some oracles (DBMS-specific and user-defined functions) and may cap query size (§8).
- **The gains come through the sub-challenges.** Full SQL is undecidable, so this challenge is attacked in parts, each argued in its own "Why it matters": [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps) turns *unknown* into proofs, [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence) removes false *different* verdicts caused by tie-breaks, and [Equivalence under schema constraints](#/challenges/schema_constrained_equivalence) keeps refutations to databases the schema allows.

**Size of the gain:** enabler, measured as the share of query pairs from rewriting, translation and text-to-SQL that get a certificate (a proof, or a counterexample validated by execution) instead of *unknown* or an uncertified verdict. The gain shows up in the challenges named above and in [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection) and the [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop); the problem as a whole is undecidable, so it improves only as its sub-challenges do. This is our estimate.

## Verifiable signal
Strong in one direction: a counterexample database is checked by running both queries in a real engine. *Equivalent* has only two certificates: a proof checked by a sound prover, within that prover's fragment, or agreement on a test family that a theorem makes complete for the pair's fragment. "No counterexample found" outside such a fragment, and an LLM verdict, are not certificates.
