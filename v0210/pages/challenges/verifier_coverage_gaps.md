# SQL features that verifiers don't cover

> Formal checkers support only a fragment of SQL. The pairs that matter most often fall outside it.

<p class="tags"><a class="tag" href="#/tags/bounded">bounded</a><a class="tag" href="#/tags/cex">cex</a><a class="tag" href="#/tags/prove">prove</a><a class="tag" href="#/tags/smt">smt</a></p>

## Challenge
Each checker supports a fragment, and realistic pairs often fall outside it. VeriEQL names correlated subqueries, [window functions](#/glossary/window-function) and `LIMIT` as unsupported, and treats strings and dates as integers ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") App. C, §6, §3). SpotIt adds string and date encodings but still lacks window functions and recursive CTEs ([SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)") App. C). Provers treat most engine-specific and user-defined functions as uninterpreted, the Argus authors say; Argus proves query skeletons and fills their blanks with such features afterwards ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") §8). The Mediator authors wrote in 2017 that query provers don't reason about updates ([Mediator](#/papers/wang2017mediator "Verifying Equivalence of Database-Driven Applications (2017)") §9). On realistic pairs the supported share can be small: student assignment pairs ([Can the Rookies Cut…](#/papers/singh2024sqlequiquest "Can the Rookies Cut the Tough Cookie? Exploring the Use of LLMs for SQL Equivalence Checking (2024)") Tab. 4), workload rewrites ([SQL-RewriteBench](#/papers/long2026sqlrewritebench "SQL-RewriteBench: A Correctness-Gated, Full-Denominator Benchmark for Statement-Level SQL Rewriting (2026)") §7.4), LLM rewrites of real enterprise queries, none of which QED could verify ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §5); LLM rewrites of TPC-DS queries and of ReSequel's eight benchmark and real workloads, where SQLSolver proves a minority ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §6, whose authors call checking "a common challenge for all LLM-based approaches" and report most of their simpler JOB rewrites proved; [ReSequel](#/papers/fathollahzadeh2026resequel "ReSequel: Robust LLM-assisted Query Rewriting and Optimization using Templatization and Sampling (2026)") §7.2, Tab. 4); and LLM [text-to-SQL](#/glossary/text-to-sql) predictions on BIRD and Spider, where `ORDER BY`, nested subqueries and `CAST` defeat the provers ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §5.2.1).

## Why it matters
- **Deploying LLM rewrites.** The QO-Verify authors call checking that a rewrite is equivalent "a major impediment that limits the practical adoption of LLM-based rewriting today" ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") abstract). Their own optimizer-based check proves only rewrites that the optimizer's existing rules can reach (§1). Rewrites beyond those rules need a prover, and on their real-world queries QED proved none (§5). Wider coverage would turn those *unknown* answers into proofs, which is what DBAs and tuning tools need before they apply a rewrite.
- **Shipping systems hit the same wall.** Microsoft's SQL Server demo loops LLM rewrites through an optimizer-based prover and skips the rewrites it can't prove ([Verified LLM-Based Query Rewriting…](#/papers/lee2026mssqlrewrite "Verified LLM-Based Query Rewriting for Microsoft SQL Server (2026)") §3.1, Alg. 1, PDF p. 3), which were most of the candidates in its worked example (§2.1, PDF p. 2). A vendor ships certified LLM rewriting, and *unknown* still discards most candidates (our reading).
- **Other challenges depend on it.** *Equivalent* needs a proof, or a test family that a theorem makes complete for the pair's fragment, and those fragments are small ([Query equivalence: prove or refute](#/challenges/query_equivalence) § Verifiable signal), so coverage limits how many "equivalent" labels [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) can certify, how many rules [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) can admit (RuleScript left out Calcite rules with `Sort` and `Window`, which need [list semantics](#/glossary/list-semantics), or `Sample`, which needs probabilistic semantics, as QED lacks both; its authors know no solver that handles them, [RuleScript](#/papers/pan2026rulescript "An Extensible and Verifiable Language for Query Rewrite Rules (2026)") §7.1), and how many pairs the [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop) can score without an LLM judge. RL rewards fall back the same way: E3-Rewrite's reward hands QED's *unknown* verdicts ("timeout or unsupported constructs") to an LLM judge ([E3-Rewrite](#/papers/xu2025e3rewrite "E3-Rewrite: Learning to Rewrite SQL for Executability, Equivalence, and Efficiency (2025)") § "[Reinforcement Learning](#/glossary/reinforcement-learning) for SQL Rewriting").
- **The method carries over.** Moving a problem into a checker's fragment without changing its meaning, then validating the result on the original, works for any verifier with a limited fragment, not only SQL (Rewriting into a verifier's fragment).

**Size of the gain:** step change, measured as the share of realistic query pairs (real workloads, LLM rewrites) that get a proof or a validated counterexample instead of *unknown*. In the one test on this site, a general prover (QED) proved none of the LLM rewrites of real enterprise queries ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §5; the paper doesn't say whether QED failed at parsing or at proof), so moving most of them into a checked fragment changes what can be deployed, not just how fast it is checked. This is our estimate; undecidability ([Query equivalence: prove or refute](#/challenges/query_equivalence)) means full coverage is out of reach.

## Verifiable signal
Execution still works for refutation: a counterexample found in the supported fragment is re-checked against the *original* queries in a real engine. The refute side needs no semantics for a feature, only data that triggers it: the ParSEval authors credit test generation's wider support to not having "to model the semantics of these operations" ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §5.2.1). Beyond SQL, ProbeGen's LLM, with execution feedback, writes inputs that disprove the equivalence of Python programs, needing only code "executable and deterministic on the explicit inputs provided" ([Disproving Program Equivalence with LLMs](#/papers/allamanis2025disproving "Disproving Program Equivalence with LLMs (2025)") §3); a failed search proves nothing (§1), and an LLM filter decides which differences matter (§3.1).
