# The Limits of Inference Scaling Through Resampling

## In brief

- Argues that resampling until a verifier passes is bounded when the verifier has false positives, since resampling can't lower their probability (abstract).
- Relates single-sample accuracy to false-positive rate on HumanEval and MBPP, whose unit tests have limited coverage (abstract).
- A weak check limiting inference scaling (<a class="tag" href="#/tags/hacking">hacking</a>), against weak-model-plus-sampling hopes such as [Large Language Monkeys](#/papers/brown2024monkeys "Large Language Monkeys: Scaling Inference Compute with Repeated Sampling (2024)"): it reports optimal sampling attempts often fewer than 10 (abstract).

## In plain words

A popular way to get more from an LLM is to sample answers until a checker accepts one; for code, until a program passes the unit tests. The authors argue that this cannot lift a weak model to a strong one when the checker sometimes accepts wrong answers: sampling more does not lower the chance that an accepted program is wrong, so accuracy hits a ceiling whatever the compute budget (abstract, §1). On two Python coding benchmarks, scored against larger hidden test suites, weaker models more often write programs that pass the original tests but are wrong, so in their measurements many weaker models stay below a single answer of GPT-4o even with unlimited sampling (§3). When accepting a wrong program has a cost, the best number of attempts is finite and, they report, often fewer than 10 (abstract). Accepted wrong programs also follow requested style rules less often (§5). The authors present this as evidence that "tempers" the hope of scaling inference by resampling (§1).

## Background and terms

**Terms to know:** [pass@k](#/glossary/passk) (Pass@1 is single-sample accuracy) · [soundness and completeness](#/glossary/soundness-and-completeness) (probabilities here, see below) · [self-consistency (majority voting)](#/glossary/self-consistency-majority-voting) · [LLM-as-a-judge](#/glossary/llm-as-a-judge) · [reward hacking](#/glossary/reward-hacking) (§1's worry that models trained against imperfect verifiers "learn to exploit weaknesses in the verifier") · [rejection sampling](#/glossary/rejection-sampling) (reasoning models are trained on datasets "curated through rejection sampling", §6).

**The paper's own terms:**
- **verifier**: accepts or rejects each candidate on its own; a **ranker** picks the best of several (§2).
- **oracle**, two senses: an **oracle verifier**, such as a proof checker, has no false positives, while **imperfect verifiers** (unit tests, LM judges) do (§2); in App. B.2 the "oracle implementation" is MBPP+'s reference solution.
- **false positive**: an incorrect solution that passes the verifier (§2); in the experiments, a program that passes the original HumanEval or MBPP tests but fails the extended ones (§3). False negatives are "less of a problem", since one can sample again (§2).
- **generalization gap**: "where a model performs well on benchmarks but fails to generalize to the real-world" (§1).
- **conditional accuracy**: the accuracy of a model's programs among those passing the original tests, read as the accuracy reachable "given an infinite compute budget" (Fig. 3).
- **cost-benefit ratio**: the cost of returning a false positive relative to a benefit of 1 for a correct one; ratio 0 is "the setting considered in previous work on inference scaling" (§4). **K** is the number of attempts.
- **completeness and soundness** (App. C.1): the probability that the verifier accepts a correct solution, and that it rejects an incorrect one; the glossary treats them as yes/no properties.

**Builds on:**
- Large Language Monkeys (Brown et al. 2024, [Large Language Monkeys](#/papers/brown2024monkeys "Large Language Monkeys: Scaling Inference Compute with Repeated Sampling (2024)")): its inference scaling laws, by which the fraction of tasks with a correct sample "scales predictably with the number of samples over multiple orders of magnitude", partly drive the enthusiasm (§2).
- HumanEval+ and MBPP+ (attributed to Liu et al. 2023, [EvalPlus](#/papers/liu2023evalplus "Is Your Code Generated by ChatGPT Really Correct? Rigorous Evaluation of Large Language Models for Code Generation (2023)")): HumanEval and MBPP with "additional hidden test cases" (§3); its sampling code is used too (App. B.1).
- Networks of Networks (Davis et al. 2024): App. C builds on its "verifier-based judge setup": a generator whose candidates an imperfect verifier accepts or rejects (App. C.1).
- Are More LLM Calls All You Need? (Chen et al. 2024a): §4's findings align with its inverse U-shaped accuracy curves, explained by uneven task difficulty (§4).

## Problem and setting

- **Question:** can resampling against an imperfect verifier let a weaker model match a stronger model's single-sample accuracy, and how many samples are worth drawing once false positives cost something (§1, §3, §4)?
- **Verifier and truth:** the original HumanEval and MBPP unit tests verify; the extended tests decide, and "we assume that solutions that pass the full set of tests are correct" (§3). All models share one verifier with "imperfect coverage, but no false negatives" (§6).
- **Models:** LLMs of several families and sizes, among them Llama 3.1 (8B, 70B, 405B), Code Llama 7B and 13B, GPT-4o, Phi-3, Cohere's Command models, and older models whose samples the HumanEval+ authors released (§3, App. B.1).
- **Sampling:** temperature 0.8; at least 200 samples per task on HumanEval+ (1,000 for Command Light), 50 on MBPP+ (§3, App. B.1). 14 HumanEval+ and 57 MBPP+ tasks are excluded for test problems (App. B.2–B.3).

## Approach

- **Survey (§2).** Tab. 1 sorts inference scaling techniques into ranking, majority voting, oracle verification and imperfect verification, with known limits; Tab. 2 lists papers using verifiers by category, type and domain.
- **The ceiling (§3).** Per model, Pass@1 on the extended tests is plotted against conditional accuracy. The "core insight": if a strong model's single-sample accuracy exceeds a weak model's accuracy among programs passing the base tests, the weak model "cannot match the performance of a single invocation of the stronger model, no matter how big the compute budget" (§3).
- **Scaling curves with a cost (§4).** For each K up to 200, the first passing sample scores 1 if correct, minus the cost-benefit ratio (0, 1, 2, 4 or 8) if a false positive, 0 if none passes; the reward is averaged over 1,000 random orderings of the same 200 samples (§4).
- **Why later samples are worse (§4).** Sampling is memoryless, yet the false positive rate rises with K (Fig. 5): task difficulty "turns out to be strongly bimodal" (Fig. 6), so easy tasks are solved early and the hard ones left yield more false positives.
- **A theoretical model (App. C).** Tasks are easy or hard with prior probabilities and per-type success rates; the verifier has a completeness and a soundness (App. C.1). Each rejection usually raises the belief that the task is hard (Eq. 2); the expected value of each attempt (Eq. 5) is summed into a reward (Eq. 6) that the optimal K maximizes. Parameters come from Llama 3.1 8B (Tab. 3).
- **Code quality (§5).** With the readability prompts and code of Zheng et al. 2024, models are asked for camelCase or snake_case names, a line-length limit, or line comments, and adherence is compared between false positives and correct programs on HumanEval+ (App. D.1). A manual look at 10 random false positives sorts them into logical errors, unhandled edge cases and too-slow implementations (§5).

## Results

- **Weaker models produce more false positives.** Conditional accuracy falls with single-sample accuracy along a fitted line with R² = 0.891 on HumanEval+ and 0.892 on MBPP+ (Fig. 3). "No model below the line can match the performance of GPT-4o through resampling" (§3).
- **Poor tests largely drive the effect.** On tasks whose original tests have a precision below 90% (under 90% of passing programs correct; 70 of 150 HumanEval+ tasks, 128 of 321 MBPP+ tasks), the relationship is "more pronounced" (Fig. 11).
- **Few samples are optimal.** Even without compute cost, the optimal number of samples is "finite and low" (§4). At a cost-benefit ratio of 4 it is at most 5 for the four models of Fig. 4 (Llama 3.1 8B and 70B, Code Llama 7B and 13B); at a high enough ratio it is zero (§4). For GPT-4o "the benefits of search are minimal" (Fig. 15).
- **The model.** With the Llama 3.1 8B parameters the optimal K is at most 3 for the costs plotted (Fig. 13); at a cost 10 times the benefit, K = 0 "for almost all models" (Fig. 14).
- **Code quality.** False positives "tend to have worse code quality across all metrics" (§5); §1 says "across all models and metrics".
- **Implications.** Imperfect tests used as evaluation ground truth "might result in misleading comparisons between models" (§1), and the findings "weaken support for previous papers' claims" that resampling is effective (§6).

## Limits the authors state

- Coding only: "other domains might exhibit different behavior" (§6 "Limitations").
- "Prompt engineering could influence false positive generation" (§6).
- They "did not investigate how benchmark contamination affects our findings" (§6), nor mitigations such as refining solutions after they pass, nor more diverse sampling (§6).
- "We do not provide empirical evidence for what specific ratio applies in any given real-world deployment" (§6).
- The results "rely on human-generated unit tests as verifiers" (§3).
- For Code Llama and Command the false positive rate rises gradually, giving much higher optimal K at low ratios: "We have not been able to identify any intuitive reason for this difference" (§4).
- Ambiguous edge cases should affect weak and strong models alike, "but have not tested this" (§5).
- Excluding the 29 MBPP+ tasks "did not significantly impact our final results" (App. B.2).
- Other code qualities "are harder to test automatically"; they "speculate that the same pattern holds" (§1).

## Open problems and building blocks

  - "It is an open question as to how the findings change when the unit-test verifiers are LLM-generated" (§3); such tests "could widen the generalization gap", left "as a next step" (§6).
  - Whether fine-tuning on code quality metrics could also reduce false positives (§5).
  - Reasoning, web agents and agent-user interaction (§6).
  - The named bottleneck, as a hypothesis: "without stronger base models or more accurate verifiers, gains from resampling-based data curation to train reasoning models are limited" (§6).
  - Accurate verifiers, perhaps "treating verification technology as a specialized subfield with its own metrics and benchmarks" (§1).
- **Released:** code for all experiments, in a repository that "also contains all code samples for all models" (§6 "Reproducibility"), and a notebook of the App. C model (§6).
- **To reuse it:** the HumanEval+/MBPP+ sampling code at a pinned commit (App. B.1); Zheng et al.'s readability prompts (App. D.1–D.2). The work relied primarily on external APIs, without GPUs or training (App. E).
- **Beyond its domain:** "our theoretical results are domain-agnostic" (§6), and the App. C model "generalizes these findings to other benchmarks" (§4); they draw implications for training reasoning models (§1, §6).
