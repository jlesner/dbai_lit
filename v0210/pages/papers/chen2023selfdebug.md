# Teaching Large Language Models to Self-Debug

**Self-Debugging** · preprint 2023 (published at ICLR 2024)

Read: [PDF](https://arxiv.org/pdf/2304.05128) · [arXiv](https://arxiv.org/abs/2304.05128)

<p class="notice">An AI-written summary for orientation, not a source: check the original paper before relying on anything here.</p>

## In brief

- Few-shot demonstrations teach an LLM to debug its own program from execution results and explanations (abstract).
- Evaluated on Spider text-to-SQL, TransCoder and MBPP (abstract).
- Execution feedback in a loop. On SQL, with no tests, the model runs its query, explains it and judges it against the question itself (§4.1): a back-translation critique (our reading).

## In plain words

For many programming tasks, writing correct code in one attempt is hard for LLMs; the authors say picking the best of many samples typically needs tens of samples, and earlier repair methods need extra training (§1). They propose Self-Debugging: few-shot examples teach a model, with no retraining, to run its own program, explain it in plain language, and use the results to find and fix its mistakes, like explaining code line by line to a rubber duck, "without any human feedback on the code correctness or error messages" (abstract). Tests cover writing SQL from questions (Spider), translating C++ to Python (TransCoder) and Python from descriptions (MBPP).

On SQL no tests are given, so the model judges its own query. There, with code explanation, they report it consistently beats the same model without debugging by 2–3%, and by 9% on the hardest questions (abstract). Where unit tests are available, gains reach up to 12% (abstract). They claim "the state-of-the-art performance" on all three, and notably better sample efficiency (abstract).

## Background and terms

**Terms to know:** [text-to-SQL](#/glossary/text-to-sql) · [self-consistency (majority voting)](#/glossary/self-consistency-majority-voting) · [pass@k](#/glossary/passk) · [code reranking](#/glossary/reranking) · [program repair](#/glossary/automated-program-repair)

**The paper's own terms:**
- **Self-Debugging**: the method; a pretrained model, not fine-tuned, repeats debugging turns of three steps, Generation, Explanation and Feedback, though a turn "does not always include all steps above" (§3, Fig. 1).
- **Rubber duck debugging**: the authors' analogy for the Explanation step, a programmer explaining code "line-by-line" to a rubber duck (§1, §3).
- **Simple feedback**: a sentence saying only whether the code is right or wrong, with no explanation (§3).
- **Unit test feedback (UT)**: the feedback adds the results of running the given unit tests, such as runtime errors and failing outputs (§3, Fig. 5).
- **Code explanation feedback (Expl)**: the model explains its own code in natural language (§3); on Spider it then compares the explanation with the question (§4.1).
- **Execution trace feedback (Trace)**: the model writes, line by line, what the code would do on a sample input; the trace is generated by the model, not by running the code; used when unit tests are available (§3).
- **Baseline**: the initial code before debugging, greedy or chosen among samples by execution (§2, §5).
- **Codex**: their name for `code-davinci-002`; the others are `gpt-3.5-turbo` (GPT-3.5), `gpt-4` (GPT-4) and StarCoder, "a strong open-source LLM for code generation" with 15.5B parameters (§1, §5).
- **Hardness levels**: Spider's own labels (easy, medium, hard, extra hard), annotated by the complexity of the reference SQL (§5.2.3, Fig. 6b).

**Builds on:**
- Selection by majority vote over execution results (MBR-Exec, the competition-programming system AlphaCode, others), which the paper follows, first dropping programs that fail given unit tests (§2); it cites [Self-Consistency](#/papers/wang2022selfconsistency "Self-Consistency Improves Chain of Thought Reasoning in Language Models (2023)") for the gain from many samples (§2).
- Reranking baselines it compares against first: the trained T5-3B + N-best Reranking (a T5-3B model trained for text-to-SQL, reranking its N best candidates) and LEVER (a trained verifier picks among Codex candidates using execution); and the prompting-only MBR-Exec (picks the program with the most common execution output) and Coder-Reviewer (scores the likelihood of the code given the problem and of the problem given the code) (§5, Tab. 1).
- Trained code repair, and repair from human feedback (e.g. Chen et al. 2023), which the authors say require "additional training" (§1, §6).
- Self-critique and refinement by prompting in some natural language and reasoning tasks: Reflexion ([Reflexion](#/papers/shinn2023reflexion "Reflexion: Language Agents with Verbal Reinforcement Learning (2023)")), Self-Refine, RCI and DERA (§1, §6).

## Problem and setting

- **Question:** can a pretrained LLM, taught by few-shot demonstrations, fix its own code without human feedback or extra training (§1, §3)?
- **Three settings** (§4):
  - **Spider** (text-to-SQL over many databases, unseen ones at test time; catalog [Spider](#/papers/yu2018spider "Spider: A Large-Scale Human-Labeled Dataset for Complex and Cross-Domain Semantic Parsing and Text-to-SQL Task (2018)")): the development set; no unit tests, so the model must judge correctness itself (§4.1).
  - **TransCoder** (a dataset of parallel functions in several languages, with unit tests): C++-to-Python on 560 problems with 10 unit tests each, all shown in the problem description (§4.2).
  - **MBPP** (Python problems with text descriptions): 500 test problems with 3 unit tests each; the first is shown, two are hidden for evaluation (§4.3).
- **Correctness:** §2 defines passing as matching the output of every unit test; Tab. 6 reports TransCoder as pass@1. Which SQL features are covered, [bag](#/glossary/bag-semantics) or [set semantics](#/glossary/set-semantics) (whether duplicate rows count) and NULLs are not discussed.
- **Decoding:** one greedy initial program, or several samples then execution-based selection; greedy decoding for all debugging; at most 10 turns (§5).

## Approach

- **A turn** (§3): the model generates code, explains it or writes a trace, then gets a feedback message on correctness, from itself or from unit tests; debugging stops when the feedback says the code is correct or at the turn limit. Simple feedback omits the Explanation step.
- **Spider prompt** (§4.1, Fig. 3, App. E): step 1, the model summarizes the question and infers its "return type", the number of columns the answer needs; step 2, the query is executed and the returned table (its first 2 rows when longer) goes into the model's explanation of each clause; step 3, the model "compares the inferred SQL explanation and question description, and then predicts the correctness of the current SQL query".
- **TransCoder** (§4.2, Fig. 5, App. F): debugging runs only when the translation fails a unit test, so "the model does not need to predict the feedback messages".
- **MBPP** (§4.3, App. G): failed given tests can be fed back, but the model "still needs to infer the code correctness" when the given test passes.
- "empirically the successful debugging processes mostly end within 3 turns" (§5).

## Results

- **Against reranking on Spider** (Tab. 1a; self-debugging and the prompting baselines use Codex, §5.1): self-debugging with explanation scores 84.1, against 81.3 for the authors' Codex baseline, 81.9 for LEVER, 80.6 for T5-3B + N-best, 75.2 for MBR-Exec and 74.5 for Coder-Reviewer. On MBPP, Tab. 1b reports it above MBR-Exec, Reviewer (named after Coder-Reviewer's Reviewer score) and LEVER, which draw 25 to 100 samples against its 10.
- **Feedback formats by model** (Tab. 2): on Spider, explanation takes Codex from 81.3 to 84.1, GPT-3.5 from 71.1 to 72.2, GPT-4 from 73.2 to 73.6 and StarCoder from 64.7 to 64.9 (Tab. 2a). The authors say simple feedback alone "does not notably improve the performance" on Spider, because the model "typically struggles to distinguish between correct and wrong SQL queries without explanation" (§5.1). On TransCoder and MBPP simple feedback still helps, since it uses execution results; for all tasks, models "generally benefit from richer feedback", "especially when the execution information is present" (§5.1, Tab. 2b–c). On TransCoder and MBPP, unit tests with explanation give up to 12% (§1).
- **GPT-4 on Spider** is "much worse than Codex" both before and after debugging (§5.1).
- **Sample efficiency** (§5.2.1, Fig. 6a, Codex on Spider): self-debugging on a greedy program matches the baseline that picks among 16 samples, and from 8 samples beats the 32-sample baseline; §1 sums this up as a consistent 2–3% gain "with different numbers of initial programs". "typically one debugging turn is sufficient" (§5.2.1). App. C.1 reports similar gains on TransCoder.
- **Hardest questions** (§5.2.3, Fig. 6b, Codex): the improvement is "more significant on hard problems", 9% on extra hard ones.
- **Without unit-test execution** (§5.2.2, Tab. 3), on TransCoder and MBPP: Codex still gains up to 5%; for GPT-3.5 and GPT-4 the authors say few-shot prompting does not notably improve self-debugging, compared to Codex. The authors conclude that "code execution plays an important role", but "sometimes LLMs can still improve their performance purely with self-generated feedback", and that trace feedback "offers consistent improvement".
- **Errors fixed** (§5.2.3, Tab. 4): on Spider (Codex) the initial queries are "usually not completely wrong", with wrong WHERE conditions the largest fixed category (Tab. 4a); on TransCoder (GPT-3.5) and MBPP (GPT-4) most fixes repair an output mismatch, not a runtime error (Tab. 4b).
- **Other comparisons:** on TransCoder, code explanation alone, without debugging, also gives a consistent gain (§1, App. C.1, Fig. 8b). App. A (Tab. 5) compares Codex and GPT-3.5 debugging from the same initial programs; App. B (Tab. 6) adds TransCoder baselines without debugging (the TransCoder model; the LLMs PaLM and PaLM-Coder).

## Limits the authors state

- GPT-4's weaker Spider results: "One possible reason is that GPT-4 is tuned for zero-shot prompting, and thus it does not follow few-shot exemplars as well as Codex" (§5.1).
- Without unit-test execution, GPT-3.5 and GPT-4 "tend to be overconfident in their own initial predictions" (§5.2.2).
- "the improvement using code explanation is less significant on MBPP" (App. C.2): unit tests expose wrong programs more easily; context length cuts the explanation prompt to 3 examples against 6; and "code explanation plays a smaller role when the initial predicted code is far from the correct solution".
- Codex seems better than GPT-3.5 "at learning from few-shot exemplars with long context" (App. A).
- "Our preliminary results suggest that model-generated feedback messages about semantic errors do not provide additional benefits on top of line-by-line code explanation" (§7).

## Open problems and building blocks

- **Open:** improving the model's ability to understand code, identify errors and follow error messages, which they consider "important future work"; "we hypothesize that better code explanation ability leads to better debugging performance"; directions: explanations giving the code's high-level meaning with its details, and feedback adding a description of potential bugs; "future work can explore techniques to predict more informative error messages" (§7).
- **Released:** no code or data release stated; the full few-shot prompts are printed in App. E–G (§2).
- **To reuse it:** a pretrained LLM, not fine-tuned (§3); a way to execute the code (a database for SQL, unit tests for Python) (§4); few-shot prompts that fit the context length (App. C.2).
