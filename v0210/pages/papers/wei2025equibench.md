# EquiBench: Benchmarking Large Language Models' Reasoning about Program Semantics via Equivalence Checking

**EquiBench** · EMNLP 2025

Read: [PDF](https://arxiv.org/pdf/2502.12466) · [arXiv](https://arxiv.org/abs/2502.12466)  
Code: [EquiBench](https://github.com/Anjiang-Wei/EquiBench)

<p class="notice">An AI-written summary for orientation, not a source: check the original paper before relying on anything here.</p>

## In brief

- Program-pair benchmark across 4 languages testing LLM reasoning about equivalence.
- It reports that models often rely on syntactic similarity (abstract; §5.2, with no numbers printed).

## In plain words

Do LLMs understand what code does, or only how it looks? Arguing that code-generation benchmarks give limited insight into this (§1), the authors propose a test: given two programs, decide whether they give the same output for every input. They built EquiBench, 2,400 labelled program pairs in Python, C, CUDA (GPU code) and x86-64 assembly, generated automatically by program analysis (tools that reason about code without running it), compiler and optimizer tools that they say ensure "high-confidence labels" (abstract), and tested 19 models. In the two hardest categories the best scores are 63.8% and 76.2%, against 50% for random guessing, which they call "only modestly above the 50% random baseline" (abstract). They also report that models often go by how alike the two programs look rather than by what they compute (abstract). They present equivalence checking as "a new task" for evaluating LLMs (§1).

## Background and terms

**Terms to know:** [decidable and undecidable](#/glossary/decidable-and-undecidable) · [soundness and completeness](#/glossary/soundness-and-completeness) · [query equivalence](#/glossary/query-equivalence) (the SQL case, which §2 cites as one domain of equivalence checking)

**The paper's own terms:**
- **equivalence checking**: deciding whether two programs "produce identical outputs for all possible inputs" (abstract). The authors note it is undecidable in general (§1), and that each category uses its own, more precise definition, all following "producing the same output given the same input" (§3).
- **The six categories** (§3, Tab. 1), each with 200 equivalent and 200 inequivalent pairs (§4):
  - **DCE** (C): one program has code removed by dead code elimination, the compiler pass that deletes statements with no effect. Equivalent here is stricter than same output: on the same input the two programs "always have identical program states at all corresponding points reachable by program execution" (§3.1).
  - **CUDA**: GPU programs generated by a tensor compiler; equivalent pairs differ in schedule. Equivalent means the same mathematical output for any valid input, "disregarding floating-point rounding errors" (§3.2).
  - **x86-64** (assembly): an assembly program against a superoptimizer's rewrite of it. Equivalent means identical outputs in the specified output registers for any input in the specified input registers; other registers and memory are ignored (§3.3).
  - **OJ_A, OJ_V, OJ_VA** (Python): online-judge submissions featuring algorithmic differences (OJ_A), variable renaming (OJ_V), or both (OJ_VA). Equivalent means the same output for any valid input as the problem description defines it; the description is given to the model (§3.4).
- **alias analysis**: a compiler analysis that "statically determines whether two pointers can reference the same memory location"; the DCE pass uses it to find dead code (§3.1).
- **tensor compiler, schedule**: a compiler (here TVM) that turns loop-based array programs into GPU code; a schedule is a choice of loop transformations such as tiling, fusion or unrolling. Schedules change speed but, the authors say, not correctness "(assuming no compiler bugs)" (§3.2).
- **superoptimizer**: a tool that searches a space of programs for one equivalent to a target, pruning candidates with test cases and proving the result correct by formal verification (§3.3). Here Stoke.
- **online judge (OJ)**: a programming-contest site that runs each submission against its tests and returns a verdict such as accepted or wrong answer (§3.4).
- **label soundness**: the paper's name for the requirement that every pair's equivalent/inequivalent label is correct (§1), one of its three design challenges with "problem difficulty" and "automation".
- **syntactic similarity**: how alike two programs look as text, scored with Moss, "a plagiarism detection tool" (§5.2).
- **reasoning models**: the paper's term; §5.1 gives OpenAI o3-mini, DeepSeek-R1 and o1-mini as examples ("such as") and doesn't say whether o4-mini, the best overall, counts.

**Builds on** (none is on this site):
- the equivalence datasets EQBENCH, which the authors call too small for LLM evaluation, and SeqCoBench, which "relies only on statement-level syntactic changes" (§2);
- CRUXEval, an input-output prediction benchmark; unlike such work, EquiBench asks about all inputs, not specific ones (§2);
- SemCoder, a code model trained on execution traces, tested in §6.

## Problem and setting

- **Question:** do LLMs reason about program semantics, and which kinds of program change defeat them (§1, §5.2)?
- **Task:** binary classification, scored by accuracy; random guessing scores 50% (Tab. 2). The prompt gives the category's definition of equivalence, the two programs and, for OJ, the problem description, and asks for Yes or No only (§4 "Prompts", App. A.3).
- **Data:** 2,400 pairs (§4). x86-64 programs are short; C and CUDA programs average several hundred lines (Tab. 1).
- **Labels** come from the generating tools and, for OJ_A, from judge verdicts (§3; next section).
- **Models:** 19 open and proprietary models, from Llama-3.2-3B to o4-mini, including reasoning models (Tab. 2).
- Decoding settings and possible overlap with the models' training data: not discussed.

## Approach

A fully automated pipeline per category (§3, Fig. 1):
- **DCE (§3.1, Fig. 2):** random C programs from the generator CSmith; an LLVM-based tool (LLVM is a compiler infrastructure) the authors built, with alias analysis and path feasibility analysis (whether a code path can actually run), classifies code as dead or live (§4). Live code is "further confirmed by executing random inputs with observable side effects". Removing dead code gives an equivalent pair; removing live code an inequivalent one.
- **CUDA (§3.2, Fig. 3):** TVM compiles schedules sampled from TenSet (a dataset of tensor programs and schedules) into equivalent pairs. Inequivalent pairs are "created by sampling code from different tensor programs".
- **x86-64 (§3.3, Fig. 4):** Stoke transforms assembly programs sampled from prior work. A pair is labelled equivalent if Stoke's verification succeeds, inequivalent if its generated test cases fail.
- **OJ (§3.4, Fig. 5):** Python submissions from CodeNet (a large dataset of online-judge submissions). For OJ_A, two accepted submissions count as equivalent, and an accepted and a wrong-answer submission as inequivalent. An open-source tool renames variables for OJ_V and OJ_VA.
- **Prompting strategies (§5.4):** 0-shot or 4-shot (two equivalent and two inequivalent examples), each with or without chain of thought.

## Results

All under 0-shot prompting unless stated.
- **Overall (Tab. 2, §5.1):** o4-mini is best overall at 82.3%, yet scores 60.8% on CUDA. The best scores in the two hardest categories are 63.8% (CUDA, claude3.7-sonnet) and 76.2% (DCE, o4-mini), against the 50% baseline; the authors call these "only modestly above the random baseline" (§5.1).
- **Reasoning models** "significantly outperform all others" (§5.1). Within the Qwen2.5, Llama-3.1 and Mixtral families, accuracy rises with model size (§5.1, Fig. 6).
- **Difficulty by category (§5.2):** mean accuracy over the 19 models ranges from 78.1% on OJ_V (variable renaming) to 49.0% on DCE, the hardest; the authors read this as purely syntactic changes being easy and structural, compiler-made changes hard.
- **Similarity (§5.2):** models tend to answer "inequivalent" for pairs that look different and "equivalent" for pairs that look alike; the authors report that a statistical test confirms that accuracy on equivalent pairs rises with similarity while accuracy on inequivalent pairs falls.
- **Bias (§5.3, Tab. 3):** a "pronounced tendency" to call equivalent CUDA and x86-64 pairs inequivalent; for o1-mini on CUDA, accuracy is 2.5% on equivalent pairs against 99.0% on inequivalent ones. More models are in Fig. A1. The authors attribute the bias to the extensive restructuring of CUDA schedules and the non-local rewrites of superoptimization.
- **Prompting (§5.4, Tab. 4):** few-shot and chain-of-thought prompting "barely improve performance", tested on o1-mini, gpt-4o, DeepSeek-V3 and gpt-4o-mini.
- **Fine-tuning (§6 "Effect of Fine-Tuning"):** LoRA fine-tuning of Qwen2.5-14B-Instruct on 1,200 labelled examples raised accuracy from 59.8% to 63.2%; the released SemCoder model also gains only modestly over its base model, DeepSeek-Coder-6.7B. The authors conclude that "binary labels alone provide limited learning signals".
- **Case study (App. A.1):** o3-mini classifies the Fig. 3 pair correctly but calls two variants with a removed `__syncthreads` (a GPU thread barrier) equivalent; with a hint about the removed synchronization it gets both right.

## Limits the authors state

- Labels can't be guaranteed: the toolchains (compilers, superoptimizers, analysis frameworks) "are not immune to subtle bugs or rare edge cases", and OJ programs "may themselves be mislabeled due to incorrect online judge verdicts or subtle implementation flaws that escape the test cases" (§ Limitations).
- The evaluation scores only the binary answer; checking explanations is hard, since "using LLMs as judges can produce unsound results" and a proof-based check with Lean (a [proof assistant](#/glossary/proof-assistant)) is "highly nontrivial"; reasoning traces get only a manual case analysis (§6 "Evaluation of Reasoning Trace", App. A.1).
- Scope: the benchmark covers six categories, those "where large-scale, high-confidence labels can be generated automatically" (§6 "Design and Extensibility").

## Open problems and building blocks

  - automated, robust evaluation of the reasoning behind a verdict (§6 "Evaluation of Reasoning Trace");
  - training directions: distilling reasoning traces from stronger models; more training data from the pipeline; agents that run and compare programs with tools to find inputs that expose differences; [reinforcement learning](#/glossary/reinforcement-learning) with execution-based feedback; datasets of program analysis concepts (§6 "Future Directions"; App. A.1);
  - benchmarks that stress "syntactically dissimilar yet equivalent" and "syntactically similar yet inequivalent" pairs (§5.2 "Implications for Benchmark Design").
- **Released:** "Our code and dataset are publicly available" (abstract).
- **To reuse it:** the pipeline relies on CSmith, the authors' 2,917-line LLVM-based tool (§4), TVM with TenSet schedules, the Stoke superoptimizer, CodeNet and a renaming tool (§3). The prompts are in App. A.3.
- **Beyond its domain:** the authors say "Any question about program semantics can be formulated as an equivalence checking problem" (§1), and that the modular design allows extension "to additional categories and languages" (§6 "Design and Extensibility").
