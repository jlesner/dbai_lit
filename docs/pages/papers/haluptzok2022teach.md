# Language Models Can Teach Themselves to Program Better

**Language Models Can Teach…** · ICLR 2023 (the PDF's running header, p. 1) · 2022

Read: [PDF](https://arxiv.org/pdf/2207.14502) · [arXiv](https://arxiv.org/abs/2207.14502)

<p class="notice">An AI-written summary for orientation, not a source: check the original paper before relying on anything here.</p>

## In brief

- An LM writes programming puzzles and solutions, a Python interpreter keeps the correct ones, and the LM is fine-tuned on them (abstract).
- Puzzles are programs whose solutions are verified by execution (abstract).
- Early self-play with a sound checker; [PSV (Propose](#/papers/wilf2025psv "Propose, Solve, Verify: Self-Play Through Formal Verification (2025)") cites it among self-play in easy-to-check domains (§1).

## In plain words

Code language models are generally trained on human-written code, which "contains bugs and inefficiencies that are reproduced by LMs", with ambiguous specifications (§1). Inspired by AlphaZero's self-play in Go, the authors ask whether a model can write its own programming problems and improve by training on them (§1). Problems are programming puzzles: a Python checking function that returns True for a correct answer, so answers are checked by running them (§2). The model writes puzzles like those in a small training set and tries to solve them, a Python interpreter keeps the solutions that pass, and the model is fine-tuned on the kept pairs (§3). The authors present this as showing "that it is possible" for a model to do this and improve (abstract). On held-out human-written puzzles (§1), "test accuracy more than doubles" in their experiments on public models (abstract). For the largest of three open models, solving within 100 tries after one pass of fine-tuning rises from 7.5% to 20.6% on its own data (Tab. 1). Data from OpenAI's larger Codex model gives 38.2% (Tab. 1).

## Background and terms

**Terms to know:** [self-play](#/glossary/self-play) · [Pass@k](#/glossary/passk) · [Distillation into compact models](#/glossary/distillation) · [catastrophic forgetting](#/glossary/catastrophic-forgetting) · [abstract syntax tree](#/glossary/abstract-syntax-tree-ast)

**The paper's own terms:**
- **programming puzzle**: a Python verification function `f` with zero or more inputs; a solution is a function `g` whose output makes `f` return True (§2; Fig. 1).
- **P3**: the open-source Python Programming Puzzles dataset of Schuster et al. [2021]; at the time of writing 397 puzzles, 155 marked train and 228 test (§4). The authors use its puzzles "but not their solutions" (§2).
- **self-play** (this paper's use): the model generates its own problems and verified solutions and is fine-tuned on them, by analogy with AlphaZero (§1; App. A).
- **trivial puzzle**: one solved by a fixed list of simple inputs (e.g. the integers −10 to 100, small lists), or any puzzle with a Boolean input; these are removed (App. C).
- **medium prompt**: P3's few-shot solving prompt, five fixed tutorial puzzles with solutions, then the puzzle to solve (Fig. 9, App. C); the fine-tuning data mirrors its format (§4.1).
- **Tab. 1's datasets**: Baseline (no fine-tuning); Human (635 Codex-written, verified solutions to 95 training puzzles, §4.3); Verified-X (1M verified pairs generated by model X); Unverified-Codex (1M Codex pairs without the correctness filter, §4.2).
- **interpreter Distillation into compact models**: learning from the interpreter's correctness filter, which "might be called interpreter Distillation into compact models", as opposed to knowledge Distillation into compact models from a larger model (§4.2).
- **diversity metric**: the entropy of a dataset's spread over k-means clusters of Codex embeddings of the P3 puzzles (App. D).

**Builds on:**
- Schuster et al. [2021]: the puzzle format, P3, the medium prompt and the judging code (§2; §4.1; App. C).
- Silver et al. [2018]: AlphaZero's self-play in Go, the stated inspiration (§1).
- Chen et al. [2021]: Codex, a code-trained model reached through an API, and the Pass@k metric and estimator (§4).
- Hinton et al. [2015] and Gou et al. [2021]: knowledge Distillation into compact models, which frames the ablation (§4.2).

## Problem and setting

- **Question (§1):** "Can an LM design its own programming problems to improve its problem-solving ability?"
- **Models (§4):** the open GPT-Neo models of Black et al. [2021] (125M, 1.3B and 2.7B parameters, pre-trained on the Pile, a large open text corpus "including English and GitHub code") generate data and are fine-tuned; Codex only generates data, since fine-tuning it "is not yet publicly available".
- **Data:** P3's train puzzles seed generation; its 228 test puzzles are held out (§4). No human-written solutions are used for fine-tuning or evaluation, other than the five examples in the solving prompt (§3).
- **Correct (§4.1):** the P3 judging code, with a one-second timeout, finds that the solution solves the puzzle.
- **Metric (§4):** Pass@k for k from 1 to 100, estimated from 256 candidates per test puzzle, at a single sampling temperature.

## Approach

- **The pipeline (§3, Fig. 2),** repeated for a set number of rounds (iterations):
  1. *Propose puzzles:* the prompt is a random sample of training puzzles without solutions, as many as fit the context window while leaving room for new ones, and the model continues it with new puzzles (Fig. 3).
  2. *Propose solutions:* a fixed number of attempts per puzzle with the medium prompt.
  3. *Verify:* the interpreter runs each attempt; at most a fixed number of correct solutions per puzzle are kept, the shortest when there are more.
  4. *Fine-tune* the model on the kept pairs.
- **Filters (§4.1, App. C).** Duplicates, puzzles without a valid argument type hint, puzzles "which did not parse in Python" and trivial puzzles are removed before solving; "approximately half of the generated puzzles were eliminated" (§4.1).
- **Settings (§4.1).** 128 attempts per puzzle, at most 8 kept, one epoch of fine-tuning. Neo runs two iterations (25K pairs, then 1M); Codex one (1M). Each Neo size is fine-tuned on each of the four 1M datasets.
- **Design choice (§3).** The authors aim for puzzles similar to the training set, since train and test come from one distribution: "While it may be natural to try to generate 'hard' problems, they may not be useful if they are from a very different distribution."
- **Ablation (§4.2).** To separate learning from the larger model from learning from the filter, Neo is also fine-tuned on unfiltered Codex pairs.

## Results

All on the held-out P3 test puzzles; few-shot with the medium prompt unless noted (§4.3).
- **Main comparison (Tab. 1; GPT-Neo 2.7B, Pass@100, one epoch).** The authors report the untuned baseline at 7.5%, Human 10.5%, data from Neo 125M, 1.3B and 2.7B 15.4%, 18.9% and 20.6%, and Verified-Codex 38.2%. They summarize that Neo fine-tuned on any verified 1M dataset "solves 2-5 times as many puzzles as the baseline model, with performance increasing as the model size that generated the data increases" (§4.3). Fig. 4 shows gains for all three Neo sizes; its caption says data from larger models "helps more".
- **Smaller teachers (§4.3).** Neo 2.7B improves even on Neo-125M data, which the authors attribute to the filtering: it learns from "watching its smaller sibling interact with the interpreter".
- **Filtering (§4.3, Fig. 6, Fig. 13).** Unverified Codex data gives 21.5% against 38.2% verified (Tab. 1, same setting); the authors say the results indicate "a significant part of the performance boost is due to the filtering by the interpreter", while unverified data still improved Pass@k "across all models".
- **Human dataset (§4.3):** it "only modestly improved the test accuracy of Neo, presumably because it was so small."
- **Iterations (§4.3, Fig. 7):** a large benefit from the first and a small one from the second; the caption says this suggests "performance may have plateaued".
- **Diversity, from Codex code embeddings (Fig. 5, Fig. 8 left, App. D):** smaller models' puzzles "appear more densely clustered" (§4.3); "the larger models generally produce puzzles with greater entropy across all values of C" (App. D), C being the number of clusters.
- **Closeness (§4.3, Tab. 2):** "No training puzzles were duplicated and a small fraction of synthetic puzzles were significantly closer to training puzzles than test puzzles, with this discrepancy being more pronounced for puzzles generated by smaller models". Human puzzles "tend to be significantly longer" in syntax-tree nodes, in large part, the authors say, because unsolved synthetic puzzles were dropped (App. E, Fig. 11).
- **App. G:** Codex Davinci (not fine-tuned) "outperforms the much smaller Neo models" (Fig. 14); fine-tuned Neo still does better few-shot than zero-shot after 11 epochs (Fig. 15); Tab. 3 splits the gain by P3 domain.

## Limits the authors state

- They stopped at two iterations "as further iterations were costly and the performance increase from iteration 1 to 2 was modest" (§4.1); "our model's Pass@k performance plateaus when trained on it's own self-generated data" (§5).
- "We expect Pass@1 performance to improve at lower temperatures, but a single temperature was used to conserve resources." (§4)
- Fine-tuning on millions of synthetic puzzle solutions "may make the model 'catastrophically forget'" other concepts such as English, and "benefits may only be realized once the synthetic code is of a higher quality" (§5).
- "some problem descriptions are not so easily translatable into code"; "training exclusively on Programming Puzzles would likely hurt the model's ability to understand natural language"; the method uses "a deterministic verifier, which isn't available in most problem domains outside code generation" (App. B).
- The P3 judge "prevents some malicious instructions from being executed by automated code checks, though other judging systems perform full sand-boxing" (App. C).
- Hand-examining a subset of generated puzzles, they found "many human concepts misused"; "input variables were sometimes unused, or puzzles did not test what they appeared like they should test" (App. F). Generated puzzles contain "occasional expletives, not present in P3" (App. B).

## Open problems and building blocks

  - "can this approach be improved to the point that LMs generate better code than humans for solving puzzles?"; the "holy grail" would be solving a longstanding open problem in P3, "such as the RSA factoring or Collatz puzzles".
  - "Future work could use reinforcement learning to improve the generation and filtering stages of the pipeline." ([RL](#/glossary/reinforcement-learning))
  - "how one could use synthetic puzzles to improve code LMs more broadly, e.g., generating code from English descriptions".
  - "our self-play pipeline could be combined with other search strategies for code generation".
- **Released:** datasets of 1M synthetic puzzles and solutions, and the source code (§1 "Contributions", footnote 2).
- **To reuse it:** a Python interpreter with the P3 judging code; training puzzles without solutions and five tutorial puzzles with solutions; a model that can be fine-tuned (GPT-Neo 125M to 2.7B here; Codex only generates) (§3, §4.1). No hardware or run time is stated.
- **Beyond its domain (§5):** "The idea of self-play may also be useful in other areas where synthesis and verification can be intertwined, such as theorem-proving"; it "offers a possible workaround to the data bottleneck for LMs".
