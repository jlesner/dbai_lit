# Knowledge Transfer from High-Resource to Low-Resource Programming Languages for Code LLMs

**MultiPL-T** · OOPSLA 2024 (PACMPL 8, OOPSLA2)

Read: [PDF](https://arxiv.org/pdf/2308.09895) · [arXiv](https://arxiv.org/abs/2308.09895) · [DOI](https://doi.org/10.1145/3689735)  
Code: [MultiPL-T](https://doi.org/10.5281/zenodo.12453932)

## In brief

- Makes fine-tuning data for programming languages code LLMs are weak in (Julia, Lua, OCaml, R, Racket): a code LLM translates documented Python functions from The Stack, and only translations that pass the function's LLM-written, execution-checked Python tests, compiled into the target language without an LLM, are kept (abstract; §4, Fig. 6).
- StarCoder models write the tests and translations (§2.1); StarCoderBase 1B and 15B and Code Llama 34B and 70B, and for Racket StarCoder2-15B and DeepSeek Coder 33B, are fine-tuned on the data and scored by pass@1 on MultiPL-E against their base models (§5.2, Tabs. 2–3). Two alternatives come first: training StarCoderBase-1B longer on The Stack's own Lua, OCaml and Scheme code (§3.1, Fig. 4), and prompting StarCoderBase-15B to write Racket programs from five examples (§3.2, Fig. 5).
- A test-filtered translate-then-train pipeline from a well-covered language into a poorly covered one, where, for StarCoderBase-15B on Racket, the check is what makes the data useful: the authors report that StarCoderBase-15B fine-tuned on Racket translations without test validation scores 11.6 against 11.8 for the base model and 21.0 with validation (§5.4.3, Tab. 9). Their data from a 15B model also improves 34B and 70B Code Llama models (§5.2.1, Tab. 2).

## In plain words

Code-writing language models do much better in languages with lots of public code, such as Python, than in rare ones such as OCaml, which the authors say puts those languages' programmers "at a disadvantage" (§1). They report that training longer on existing code in several such languages can hurt, and that training on the model's own programs fails, since it writes poor ones in them (§1, §3). Their pipeline, MultiPL-T, translates instead: a code model writes and runs tests for documented Python functions, translates each function into the rare language many times, and keeps only translations that pass the same tests, converted by a simple compiler (abstract; §4). Models of 1 to 70 billion parameters fine-tuned on such data for Julia, Lua, OCaml, R and Racket beat their bases "across the board" (§5.2.3); the 15-billion-parameter StarCoderBase goes from 6.9% to 19.9% of OCaml problems solved in one attempt, at its best epoch (Tab. 2; §5.2.1). Trained on Racket translations without the tests, it scores slightly below its base (§5.4.3, Tab. 9). The authors present "a new and effective approach" (§1).

## Background and terms

**Terms to know:** [pass@k](#/glossary/passk) · [rejection sampling](#/glossary/rejection-sampling) · [Distillation into compact models](#/glossary/distillation) · [data contamination](#/glossary/data-contamination) · [line and statement coverage](#/glossary/line-and-statement-coverage) · [greedy decoding and temperature sampling](#/glossary/greedy-decoding-and-temperature-sampling) · [BLEU and ROUGE](#/glossary/bleu-and-rouge) · [weak-to-strong supervision](#/glossary/weak-to-strong-supervision) (here StarCoderBase-15B's data fine-tunes CodeLlama-34B and 70B, §2.1, §5.2.1)

**The paper's own terms:**
- **Code LLM**: an LLM trained on source code, often with natural-language text (§2.1).
- **High- and low-resource languages**: languages "well represented in their training data (e.g., Java, Python, or JavaScript)" against those "that have limited training data available (e.g., OCaml, Racket, and several others)" (abstract).
- **Natural, synthetic and semi-synthetic data**: "code written by human programmers" (§3.1); "data generated by an LLM itself" (§1); and the paper's kind, natural code translated by an LLM and kept only when tests pass (§1, Fig. 2).
- **Natural language to code task**: from a function signature and a comment, write the function; it is correct only if it passes all hidden tests (§2.2).
- **Self-instruction**: prompt the model with hand-picked seed programs to generate more, and iterate (§3.2).
- **Test compilers**: the compilers of MultiPL-E (a benchmark translator, under Builds on) for assertions that are "simple equalities between first-order values" (atomic values, lists, tuples, dictionaries) into 20+ languages; other tests are dropped (§4.3).
- **No-resource languages**: languages "that StarCoderBase is not trained on at all" (§6).

**Bridges to the glossary:** keeping only the sampled translations that pass the tests is rejection sampling used to make fine-tuning data (ours).

**Builds on:**
- MultiPL-E (Cassano et al. 2023), which mechanically translates most of HumanEval's Python problems (prompts with hidden tests, Chen et al. 2021) into other languages; MultiPL-T reuses its prompt translation and test compilers and adds OCaml (§2.2, §4.3).
- StarCoder (Li et al. 2023), open code models trained on The Stack, an open set of permissively licensed code by Kocetkov et al. 2023 (§2.1); its open data lets the authors decontaminate benchmarks and compare with training longer (abstract, §2.3).
- TransCoder-ST (Roziere et al. 2021) and CMTrans (Xie et al. 2024), which make training data for code translation between Java, Python and C++ with test-checked translations (§7).
- Self-instruct (Wang et al. 2023) and WizardCoder (Luo et al. 2024), LLM-generated fine-tuning data for high-resource languages, the alternative §3.2 tests.

## Problem and setting

- **Question:** how to fine-tune pretrained Code LLMs for low-resource languages, where more natural data "is hard to find by definition" (§1).
- **Models:** StarCoder-15B (StarCoderBase-15B trained further on Python) writes tests and StarCoderBase-15B translates (§2.1). Fine-tuned: StarCoderBase 1B and 15B, Code Llama 34B and 70B (stronger code models with undisclosed training data), and for Racket StarCoder2-15B and DeepSeek Coder 33B, two newer base models (§2.1, §5.2). Closed models were not used: they lacked fine-tuning, cost too much at this scale, or forbade training other LLMs on their outputs (§2.3).
- **A correct training item** passes every compiled test in the target language's runtime (§4.3); its Python source has tests that passed in isolation and reach at least 90% line coverage (§4.2).
- **Evaluation:** MultiPL-E pass@1, the mean pass rate (§5.2), at the best epoch (§5.2.1); natural language to code only, other tasks being "beyond the scope of this article" (§2.2). Python functions that exactly match benchmark prompts or solutions are removed (§4.1).
- **Baselines:** the base model, other fine-tunes of it, and several model families and sizes (§5.2).

## Approach

The pipeline (§4, Fig. 6):
1. **Filter Python (§4.1, Tab. 1):** functions with docstrings that the Pyright type checker finds return a value and use only the standard library, a quality heuristic, as "Pyright uses heuristics and makes no attempt at being sound" (no guarantee its verdicts are right).
2. **Tests (§4.2):** StarCoder-15B writes five test suites per function at temperature 0.8; translatable tests that pass alone are kept, and functions under 90% line coverage dropped, leaving about 133,000 (Tab. 1). The authors argue the model acts as "a weak detector for inconsistencies between code and comments" (§4.2, example in Fig. 8).
3. **Types (§4.2, Fig. 9):** for typed targets, types are read off the test values: an argument seen as an integer and as None becomes an optional integer.
4. **Translate (§4.3):** the prompt holds the docstring and signature in the target language and the Python code as a comment; StarCoderBase-15B samples 50 translations at temperature 0.8 (100 for OCaml).
5. **Filter (§4.3):** every candidate passing all compiled tests is kept, possibly several per function.
6. **Deduplicate (§4.4, Alg. 1):** near-duplicates by ROUGE-L, compared in groups.

## Results

- **Alternatives (§3):** more epochs on The Stack's own Lua, OCaml and Scheme code (Scheme standing in for Racket's poor-quality subset) barely help StarCoderBase-1B and can hurt it, at full size or at MultiPL-T's size (§3.1, Fig. 4). Prompted with hand-written Racket examples, StarCoderBase-15B wrote five programs, four buggy (§3.2, Fig. 5).
- **Main (§5.2.1, Tab. 2):** every model and language improves; e.g. StarCoderBase-15B 6.9 → 19.9 on OCaml, CodeLlama-70B 21.9 → 33.1 on Racket. Relative gains are largest for Racket and OCaml, where fine-tuned 1B models "perform comparably to the base 15B models"; the 70B models gain less than the smallest (§5.2.3). Improving Code Llama with StarCoderBase-15B's data is "an uncommon result", the authors say (§1).
- **Newer models (§5.2.2, Tab. 3):** both Racket fine-tunes improve. The authors report the DeepSeek Coder one beat every fine-tuned model on the BigCode Models Leaderboard for Racket at the time of writing, and conclude MultiPL-T "is significantly more data efficient than alternative approaches to fine-tuning" for low-resource languages (§5.2.3).
- **Beyond single functions (§5.3.1, Tabs. 4–5):** on 14 hand-built problems in OCaml, Racket and Lua needing user-defined types, higher-order functions, helpers or libraries, for StarCoderBase 1B and 15B, "all other fine-tuned models do the same or better" except the 15B OCaml model, which drops from 50.6 to 42.9.
- **Style (§5.3.2, Fig. 11):** two graders scored StarCoderBase-1B's Racket solutions to the 35 HumanEval problems both versions solve at least once on a rubric (Tab. 6): 89.5% base, 85.2% fine-tuned.
  - With 25,000 items per language, StarCoderBase-1B gains substantially on Racket and OCaml after one epoch; Lua needs more data (§5.4.1, Fig. 10).
  - Adding the Python source to the prompt raises translation success (pass@50) for Racket from 34.7 to 56.8 and Lua from 51.4 to 68.5, but lowers OCaml from 26.1 to 23.9 (§5.4.2, Tab. 7).
  - Without test validation, Racket fine-tuning leaves StarCoderBase-15B at 11.6 against 11.8 for the base and 21.0 validated; the 1B model reaches 8.6 against 11.3 validated (§5.4.3, Tab. 9).
  - Deduplication barely changes the 1B model's Lua score and cuts training time (§5.4.4); fine-tuning on the filtered Python itself doesn't improve the 1B model's Python (§5.4.5).

## Limits the authors state

- Every training item "is a single function without any other context", so it is plausible that models overfit to that format; "the 15B OCaml-tuned model may have overfit to the MultiPL-T format" (§5.3.1, Tab. 4).
- Fine-tuning "slightly decreases the model's ability to generate idiomatic Racket code": more nested if-expressions, and iteration where recursion is available (§5.3.2).
- Data generation costs more compute for the lower-resource languages, so the efficiency gap between languages "is narrower than the figure suggests" (§5.4.1).
- MultiPL-T is "unlikely to work as-is" for no-resource languages; prompting the model with enough about one may bootstrap generation, "But, doing so efficiently may be challenging" (§6).
- Code Llama's undisclosed training data is "preventing us from conducting the exhaustive evaluation on Code Llama that we do with StarCoder" (§2.1).
- StarCoder2's pretraining included these datasets: "All we can conclude is that they did not hurt performance on the target languages and that further fine-tuning still help" (§5.2.2).
- On the Python source hurting OCaml: "We can only speculate about why this happens" (§5.4.2).
- "It is not a goal of this paper to maximize MultiPL-E scores" (§5.2.1).

## Open problems and building blocks

  - For other languages MultiPL-E supports (D, Bash, MATLAB, Haskell, Perl among them), generating data "may just be a matter of running the MultiPL-T pipeline for a few days on GPUs"; a source language closer to the target (C++ for Rust) may work better, the authors speculate (§6).
  - Other models: "we expect our results will generalize to the other languages" for DeepSeek Coder and StarCoder2; a stronger generator "would improve conversion rates", but GPT-4 "would violate its terms of use" (§6).
  - Self-instruct in a high-resource language, then MultiPL-T translation: "this composition seems likely to succeed" (§6).
  - "We speculate that fine-tuning on a mix of natural and MultiPL-T data will decrease the likelihood of overfitting" (§5.3.1).
  - "We need to develop these kinds of benchmarks for low-resource languages", e.g. specialized tasks (§6).
- **Released:** "All code, data, and models from this paper are available with open licenses": a reproduction guide on Zenodo, datasets on Hugging Face with links to fine-tuned models (Data-Availability Statement); the contributions list the five datasets, the filtered Python functions with tests, and the models (§1).
- **To reuse it:** a code model for tests and translations (§2.1); per language, a prompt translator, a compiler for simple assertions (§6) and a runtime (§4.3). The authors estimate about 550 A100 GPU-days for the whole work, mostly dataset generation, and say larger generators "would take up significantly more resources" (§5.1).
