# GenRewrite: Query Rewriting via Large Language Models

**GenRewrite** · PACMMOD 4(1) / SIGMOD 2026

Read: [PDF](https://arxiv.org/pdf/2403.09060) · [arXiv](https://arxiv.org/abs/2403.09060) · [DOI](https://doi.org/10.1145/3786684)

<p class="notice">An AI-written summary for orientation, not a source: check the original paper before relying on anything here.</p>

## In brief

- LLM rewriting beyond fixed rules, with Natural Language Rewrite Rules (NLR2s) as hints and transferable knowledge.
- A loop fixes syntax errors from `EXPLAIN` feedback and semantic errors from counterexamples the LLM reasons out, not executes (§4.3).
- Checks: SQLSolver, then SlabCity's tester, else discard (§4.4; §1 says a human confirms instead); it reports SQLSolver verifying only 18.9% of its TPC-DS rewrites (§6). Its rules are in natural language, which no prover can check (<a class="tag sub" href="#/tags/rules-discover">rules-discover</a>).

## In plain words

Queries written by inexperienced users or generated by reporting tools are often needlessly slow, which the authors say costs time and cloud money, while automatic rewriters either apply a fixed list of known transformations or manage only simple queries (§1). GenRewrite asks a large language model to rewrite a slow query into a faster one with the same answer. Each successful rewrite yields a short plain-English lesson, stored as a hint for later queries with a similar slowdown. The model is asked to argue whether the two queries could return different results and to repair the candidate, and the database checks that it parses. An equivalence prover or, failing that, a testing tool then decides whether it is kept. The authors call it "the first holistic system that leverages LLMs for query rewriting beyond traditional rules" (abstract). With four candidates per query and the o3-mini model, they report speeding up 25 of the 99 queries of TPC-DS, a standard analytics benchmark, at least twofold, against 18 for plain prompting and at most 16 for four other rewriters (§5.2).

## Background and terms

**Terms to know:** [query rewriting and rewrite rules](#/glossary/query-rewriting-and-rewrite-rules) · [query equivalence](#/glossary/query-equivalence) · [correlated subquery](#/glossary/correlated-subquery) · [semijoin and anti-semijoin](#/glossary/semijoin-and-anti-semijoin) · [common table expression (CTE)](#/glossary/common-table-expression-cte) · [query plan and EXPLAIN](#/glossary/query-plan-and-explain)

**The paper's own terms:**
- **NLR2 (Natural Language Rewrite Rule)**: "a textual explanation summarizing the rewrite", written by the LLM without table or column names; a hint for later rewrites and an explanation for users (§1, §4.1). Example: "Eliminate union operations by computing aggregates in dedicated subqueries per data source" (Tab. 1).
- **NLR2 Repository**: the store of NLR2s, with the query features and speedup of each (§4.1).
- **Dominant NLR2**: of the NLR2s listed for one rewrite, the one credited with its speedup (§4.1).
- **Semantic error / syntax error**: a rewrite that runs but returns different results / one that does not run (§4.3).
- **Counterexample** (in this paper): example tables the LLM gives in its answer to show two queries differ; semantic correction "relies on counterexamples identified by the LLM through logical reasoning" (§4.3, Fig. 6).
- **Desired speedup threshold θ**: the smallest speedup for which a rewrite is kept; 1.2x by default (Alg. 1, §5.4).
- **Recurrent workloads**: the same query template run many times, as in dashboards and reporting (§1).
- **Baseline LLM**: the query plus "Rewrite this query to improve performance.", without correction (Fig. 3, §5.1).

**Builds on:**
- Rule-based rewriters, with expert or automatically inferred rules (e.g. [WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)")), which the authors say cannot optimize "new query patterns that do not match their existing rules", and synthesis-based SlabCity ([SlabCity](#/papers/dong2023slabcity "SlabCity: Whole-Query Optimization Using Program Synthesis (2023)")), which builds rewrites without prior rules but "only handles simple queries" (§1).
- The baselines (§5.1): LITHE ([LITHE](#/papers/dharwada2025lithe "LITHE: A Query Rewrite Advisor using LLMs (2026)")), an LLM rewriter whose prompts carry handcrafted rewrite rules; LLM-R² ([LLM-R2](#/papers/li2024llmr2 "LLM-R2: A Large Language Model Enhanced Rule-Based Rewrite System for Boosting Query Efficiency (2024)")) and R-Bot ([R-Bot](#/papers/sun2024rbot "R-Bot: An LLM-based Query Rewrite System (2025)")), which use an LLM to pick and order rules of Apache Calcite, an open-source query-processing framework ([Apache Calcite](#/papers/begoli2018calcite "Apache Calcite: A Foundational Framework for Optimized Query Processing Over Heterogeneous Data Sources (2018)")); LearnedRewrite ([LearnedRewrite](#/papers/zhou2021learnedrewrite "A learned query rewrite system using Monte Carlo tree search (2021)")), which orders Calcite rules by tree search. QUITE ([QUITE](#/papers/song2025quite "QUITE: A Query Rewrite System Beyond Rules with LLM Agents (2025)")), another LLM rewriter, is compared in words only.
- Reused checkers: the SQL equivalence prover SQLSolver ([SQLSolver](#/papers/ding2023sqlsolver "Proving Query Equivalence Using Linear Integer Arithmetic (2023)")) and SlabCity's tester, which generates test data (§4.4); compared checker: Miniature & Mull, an equivalence prompt of LLM-SQL-Solver ([LLM-SQL-Solver](#/papers/zhao2023llmsqlsolver "LLM-SQL-Solver: Can LLMs Determine SQL Equivalence? (2025)")) (§5.4).

## Problem and setting

- **Question:** "how to best leverage LLMs for query rewriting beyond rules and how to address the challenges involved" (§1). Named challenges: unparsable or wrong rewrites, no cost model, call costs, misleading hints, hard-to-verify rewrites (§1, C1–C5).
- **Input and output:** a workload of queries; for those it can optimize, an equivalent, likely faster rewrite with an explanation (§1, Alg. 1).
- **Target use:** recurrent workloads, and very expensive queries expected to take tens of minutes (§1 "Target workloads").
- **Correctness:** equivalence to the input, checked by tools (§4.4). [Set](#/glossary/set-semantics) or [bag semantics](#/glossary/bag-semantics) and NULLs are not discussed, apart from App. B's rule preconditions.
- **Speed:** measured run time, the mean of 3 runs; a method succeeds on a query if any of its four candidates is equivalent and faster (§5.1).
- **Setup (§5.1)**: PostgreSQL 14.17 on a 2-vCPU, 16 GB cloud machine, no indexes. Benchmarks: TPC-DS (a synthetic decision-support benchmark; 10 GB, all 99 queries); JOB, the Join Order Benchmark (many-join queries over IMDB movie data); and from SQLStorm, which generates complex queries with LLMs, the 100 slowest TPC-DS-schema and 50 slowest JOB-schema queries, released after the LLM's training cutoff. Four candidates per query for every LLM method; empty NLR2 Repository at start; correction loops capped at 3 rounds. Default LLM o3-mini; also gpt-4o and gpt-4o-mini (§5.4).

## Approach

- **The loop (Alg. 1, Fig. 1):** each round, every remaining query goes through suggestion, correction and evaluation; rewrites faster than θ are kept, NLR2 benefit scores updated, until the kept set stops changing or the budget runs out (§4).
- **Collecting NLR2s (§4.1):** the prompt adds "Describe the rewrite rules you are using" and asks to leave out table and column names.
- **Crediting one rule (§4.1):** the LLM rewrites the query once per NLR2 alone, and `EXPLAIN` gives each plan without running it. The rule whose plan matches the fast rewrite's estimated cost, or else is closest (by bert-base-uncased text embeddings), gets the measured speedup. Only the fast rewrite is executed.
- **Grouping (§4.1, Fig. 5):** a multiple-choice prompt asks whether a new NLR2 means the same as a known one; only new ones are tried.
- **Choosing hints (§4.2, Fig. 4):** the LLM summarizes "the most critical performance bottleneck" from the query and its execution plan; past queries with similar summaries are retrieved by embedding, the LLM picks the best match or none, and that query's most beneficial NLR2 goes into the prompt.
- **Correction (§4.3, Fig. 6)**: semantic correction: the LLM describes both queries step by step, tries to give example tables on which they differ, declares them equivalent or not, and if not revises the candidate, repeating "until the LLM deems the candidate query equivalent". Syntax correction feeds `EXPLAIN` error messages back.
- **Evaluation (§4.4)**: a correctness gate tries SQLSolver; if it answers "UNKNOWN", SlabCity's tester; if neither certifies equivalence, the rewrite is discarded. A performance gate runs it offline and accepts it only under a "never-worse-off" policy. "In the exploratory setting", manual review is optional and "not required for the deployment".

## Results

- **Queries sped up (Tab. 3, §5.2–5.3)**: at ≥2x on TPC-DS, GenRewrite 25 of 99 against Baseline LLM 18, LITHE 16, LLM-R² 10, R-Bot 9 and LearnedRewrite 6; on the SQLStorm TPC-DS set, 25 of 100 against 12, 19, 2, 2 and 4. The authors say it "consistently optimizes more queries at every speedup threshold than all baselines" (abstract). On JOB and its SQLStorm set they describe "a slight edge" (§5.2).
- **Correctness of rewrites (Tab. 4, §5.2)**: on TPC-DS, 70.0% of GenRewrite's rewrites are equivalent against 51.8% for Baseline LLM; on JOB both near 100%.
- **Correction ablation (Tab. 7, §5.4)**: semantic plus syntax correction gives the most queries with an equivalent rewrite at every candidate budget.
- **Semantic check (§5.4)**: on random TPC-DS rewrites without correction, their prompt marks 29% as equivalent with a 6% false-positive rate, against 26% with 22% for Miniature & Mull.
- **Ablation (Tab. 6, §5.4):** GenRewrite's 25 queries at ≥2x drop to 19 without bottleneck analysis, 14 with gpt-4o and 2 with gpt-4o-mini. Without grouping, speedups are unchanged but LLM time rises 153.9% and cost 140.3%.
- **Discovered patterns (Tab. 5, §5.3, App. A)**: of seven rewrite patterns, five have no exact structural match in prior work, per the authors.
- **Cost (§5.5, Tab. 9):** with o3-mini, one TPC-DS candidate averages $0.029 and 36.15 s, mostly in semantic correction.
- **Preliminary study (§3):** with plain prompts GPT-4 never suggested removing the redundant `UNION ALL` in TPC-DS Q4 over ten attempts; a hint naming that idea did it consistently.

## Limits the authors state

- GenRewrite is "not designed for real-time adhoc workloads, where queries are novel and relatively light", since the LLM overhead cannot be amortized (§1 "Target workloads").
- When the verifier cannot prove equivalence, "a human expert needs to inspect the rewrite, which incurs an additional delay" (§1 "Target workloads").
- Crediting one dominant NLR2 "simplifies the real-world scenario, where interactions between rules can occur"; evaluating all combinations is "computationally prohibitive" (§4.1).
- NLR2s that speed up some queries "may degrade performance when applied to others" (§4.2).
- SQLSolver "can verify only 18.9% of the generated TPC-DS rewrites", against 74.4% on JOB; testers struggle more as queries grow; and "To ensure correctness, all rewrites reported in the evaluation section have been manually inspected" (§6).
- TPC-DS "does not perfectly capture the recurring, user-specific workloads seen in production" (§5.1).
- Performance "critically depends on LLM's reasoning capabilities"; more candidates give "diminishing returns and proportionally higher cost" (§5.4).

## Open problems and building blocks

- **Open:** §3 outlines "key challenges and opportunities for future research" (§1, contributions). "Determining the equivalence of rewrites is a common challenge for all LLM-based approaches" (§6). Proposed: turn several verified query pairs sharing an NLR2 into one guarded pattern-matching rule (with explicit preconditions) for rewriters such as Calcite, since "a rule distilled from only one such pair is brittle" (§5.3, §6, App. B). Counterexamples from semantic correction "can also be incorporated into the tester" (§4.4).
- **Released:** Nothing stated.
- **To reuse it:** a strong reasoning LLM (o3-mini by default, §5.1); `EXPLAIN` plans and plans from past executions (§4.1–4.2); SQLSolver and SlabCity's tester, with 5 s and 60 s timeouts (§5.5). Since NLR2s hold no schema names, the authors say one workload's repository can bootstrap another's (§1); the experiments start empty (§5.1).
