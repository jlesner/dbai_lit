# Long-Horizon State Tracking in LLMs: Executing MD5 through a Deep Sequence of Dependent Tool Calls

**Long-Horizon State Tracking in LLMs** · preprint 2026

Read: [PDF](https://arxiv.org/pdf/2609.00012) · [arXiv](https://arxiv.org/abs/2609.00012)

<p class="notice">A summary for orientation, not a source: check the original paper before relying on anything here.</p>

## In brief

- Has gpt-oss-120b, an open mixture-of-experts model, compute an MD5 hash step by step through tools, carrying the four 32-bit state words in its own context across a canonical 196 dependent calls; every call is aligned to a from-scratch reference trace and the digest is checked to the bit (abstract; §4, §4.2).
- In the strongest setting a stateless "worker" LLM (the same model, three samples and a majority vote) replaces every primitive tool; the authors name two conditions for success, keeping the model's own reasoning in its context each turn and voting on the worker, and sort the failures by origin: driver state, worker arithmetic, serving (abstract; §5.2–5.4, Tab. 2).
- A long job with an exact check available at every step, used here only to measure and attribute failures, not to correct them in the from-scratch runs (§4.2): a testbed for whole-job reliability in which the authors report the driver's state-carrying, not the arithmetic, as the harder error source (§5.2, §5.4).

## In plain words

When each step depends on the last, errors cascade; the authors say existing agent benchmarks cannot show why a long run fails (abstract). They have an open model, gpt-oss-120b, compute an MD5 hash (a bit-exact checksum) one operation at a time, through a canonical 196 dependent tool calls, each checked against their own reference implementation (abstract; §4). With exact code as the tools, no random sampling, and its own reasoning fed back each turn, the model returned the correct hash in 21 of the 34 runs that ended with a hash on one provider (Tab. 1). The authors present this as "A positive result" (§1), and add a setting where a second LLM, with majority voting, replaces every tool (§5.2).

## Background and terms

**Terms to know:** [tool calling](#/glossary/tool-calling-function-calling) · [mixture of experts (MoE)](#/glossary/mixture-of-experts-moe) · [self-consistency (majority voting)](#/glossary/self-consistency-majority-voting) · [greedy decoding and temperature sampling](#/glossary/greedy-decoding-and-temperature-sampling)

**The paper's own terms:**
- **MD5**: maps a message to a 128-bit digest; one 512-bit block takes 64 rounds, each updating four 32-bit words (a, b, c, d) by bitwise functions, addition modulo 2³² and a rotation, then re-ordering the words (§2).
- **driver**: the LLM that issues the tool calls and carries (a, b, c, d) between them (§1; Alg. 1).
- **worker**: an LLM that replaces a primitive tool, one operation per call, its context discarded afterwards (§5.2; Fig. 2). **Swap mode** uses workers; **CPU mode** uses exact code (§4 "Tools").
- **reasoning channel**: gpt-oss writes its intermediate work in a separate "analysis" channel of OpenAI's Harmony chat format; "echo on" feeds it back next turn (§5.3; Tab. 1).
- **first divergence** and **counterfactual digest**: where the carried state first departs from the reference, and the hash that slip alone would produce (§4.2).
- **serving**: the provider endpoint running the weights, its own error source (§4.1; §5.4).

**Builds on:**
- Sinha et al. (2025), [The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)"): errors compound and models "self-condition" (err more after their own earlier mistakes): pessimism the paper argues against (§1; §3).
- Long-context degradation: Liu et al. 2024; Modarressi et al. 2025; Adhikary, Contractor et al. 2025 for tool calling (§2; §3).
- Nye et al. 2022 (scratchpads: writing out intermediate work) and chain of thought, of which the reasoning-channel result is "its serving-time analogue" (§3).
- Self-consistency (Wang et al., [Self-Consistency](#/papers/wang2022selfconsistency "Self-Consistency Improves Chain of Thought Reasoning in Language Models (2023)")), applied per primitive "rather than a new method" (§3).

## Problem and setting

Can an LLM itself carry exact state across many tool calls, rather than a hand-built controller (§1)? Inputs are single blocks of at most 55 bytes, never famous ones whose digests may be memorized; the single block is fixed "deliberately" (§4). Driver and worker are both gpt-oss-120b, an open-weight MoE with about 117B total and 5.1–5.5B active parameters per token, its experts stored in about 4 bits (MXFP4) (§4.1). Success: the final digest equals the true MD5 exactly (§4.2).

## Approach

- **The loop (§4, Alg. 1).** Seven tools; a correct run is 2 setup calls, 3 per round for 64 rounds, and 2 to finalize. The driver re-orders the words itself, marked "most error-prone".
- **Settings (§4.1).** Driver at temperature 0, short fixed system prompt. Each worker op is sampled three times at temperature 0.7 and the majority returned; "ties trigger an escalation round" (Fig. 2).
- **Verification (§4.2).** Calls are aligned with the reference trace; replaying each first divergence separates a fresh error from its propagation. Worker ops are checked against their code twin "for measurement and human legibility only"; a setting lets a wrong value cascade or corrects it, to attribute failures.

## Results

- **Driver with CPU tools (§5.1, Tab. 1).** It reports 21 correct of 34 completed runs on one provider's (Fireworks) endpoints, against 0 of 2 on another's (Groq), runs without a digest excluded. The most common fresh error is the word re-ordering.
- **Swap-all (§5.2).** With voting, per-op worker pass rates are "high across all six computed primitives", so the pair computes the hash "from scratch". When a run fails it is "overwhelmingly the driver mis-carrying state": correcting every worker op does not by itself rescue a driver-slipped run.
- **Reasoning in context (§5.3).** Stripped, "success collapses"; moving the same tokens into the visible message still fails, "usually within the first 12 to 24 of 196 steps". Of 105 logged Fireworks sessions, 71 emit no digest, nearly half halting within 24 calls.
- **The 40→48 skip (§5.3).** Seven long runs, none successful, jump from round 39 to 48.
- **Taxonomy (§5.4, Tab. 2).** Errors split by origin (driver, worker, serving), called independent; driver errors dominate.

## Limits the authors state

- Tab. 1's cells are "raw counts from the logged corpus, to be finalized on a frozen N ≥ 20 grid" (N: runs per cell); excluded runs include "aborted development runs" (Tab. 1).
- "temperature 0" is "not bit-deterministic on quantized serving" (§4.1).
- The skip is "a candidate model fingerprint rather than a claim that it happens on every run" (§5.3).
- Route changes latency and, "historically", correctness for the same serverless weights; speed is reported "only as context" (§5.3).

## Open problems and building blocks

- **Open:** one agent that carries its state, computes its primitives and "curates its own context" (§6 "Toward a self-managing agent"); a tool to edit its own context, checkable to the bit, as a testbed for self-editing memory such as MemGPT (§6 "Self-editing context").
- **Released:** Nothing stated.
- **To reuse it:** an endpoint that accepts the reasoning field back (§5.3); a thinking-enabled worker endpoint (§4.1); a from-scratch MD5 reference (§4).
- **Beyond its domain:** workflows such as accounting close-out need exact state over many steps (§6 "Practical reach"); the authors expect self-editing context to carry over to them (§6 "Self-editing context").
