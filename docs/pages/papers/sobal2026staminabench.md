# StaminaBench: Stress-Testing Coding Agents over 100 Interaction Turns

**StaminaBench** · preprint 2026

Read: [PDF](https://arxiv.org/pdf/2606.19613) · [arXiv](https://arxiv.org/abs/2606.19613)  
Code: [StaminaBench](https://github.com/amazon-science/StaminaBench)

<p class="notice">An AI-written summary for orientation, not a source: check the original paper before relying on anything here.</p>

## In brief

- A benchmark of how many consecutive change requests a coding agent survives: the agent implements a REST API server and then modifies it through procedurally generated schema changes, up to 100 turns (abstract; §3.2).
- Each turn's tests are generated programmatically from the reference schema, with no LLM, and run black-box over HTTP (abstract; §3.2). It evaluates seven open models with three open-source harnesses plus the providers' own, with and without a retry loop that feeds test failures back (§4; §4.1, Tabs. 2–3).
- A long job with a programmatic check at every turn. The authors report that with no feedback loop even GLM-5, their best model, fails after 6.2 turns on average with its best harness (§4.1, Tab. 2), and that the retry loop and the harness matter more than model rankings suggest (abstract; §4.1).

## In plain words

Developers use coding agents over long sessions of follow-up requests, but most popular coding benchmarks, the authors say, judge one self-contained task at a time (§1). StaminaBench measures "how many consecutive interaction turns (change requests) they can handle before failing" (abstract). The agent writes a small web server and then changes it through generated change requests, 100 per run in the experiments; each turn's tests are generated by a program, with no LLM, and sent to the server over HTTP (abstract). Seven open models are tested in six agent programs (harnesses) (abstract). When a failed test ends the run, even the best model, GLM-5, fails after 6.2 turns on average with its best harness (§4.1, Tab. 2). Sending test failures back and allowing retries "improves passed turn count by up to 12×", and "a good harness is required for strong performance" (abstract). The authors present a benchmark, a framework for building such benchmarks and an empirical study (§1), calling the benchmark "unique" in procedurally generating arbitrarily long change sequences (Tab. 1 caption).

## Background and terms

**Terms to know:** [agent harness](#/glossary/agent-harness) · [Markov decision process](#/glossary/markov-decision-process) · [Wilcoxon signed-rank test](#/glossary/wilcoxon-signed-rank-test) · [multiple testing](#/glossary/multiple-testing) · [statistical power](#/glossary/statistical-power) · [mixture of experts (MoE)](#/glossary/mixture-of-experts-moe) · [lost in the middle](#/glossary/lost-in-the-middle)

**The paper's own terms:**
- **interaction turn**: one user request; "multi-turn" means "multiple interaction turns between the user and the agent, not the internal tool-use steps the agent takes within a single user request" (§1, footnote 2).
- **scenario**: one seeded run, an initial specification plus N change turns (§3.2; N=100 in §4).
- **reference system, agent system, test function**: the framework's parts. The reference is an evolving state (here an API schema) changed by actions the environment picks; the agent keeps its own state (a codebase) and sees the reference only through text descriptions; the test function compares the two each turn (§3.1, Alg. 1). Unlike in a Markov decision process, the action-picking "policy" belongs to the environment (§3.1).
- **sampler**: picks the changes, either an LLM or a programmatic sampler that "draws uniformly from valid changes" (§4.2).
- **retry budget R, "@R"**: after a failed turn the agent gets feedback and up to R more tries; R=0 ends the scenario at the first failure, and the default is R=2 (§3.2; §4.1). Second sense: Tab. 12 writes "@3" and "@11" for attempts, i.e. R=2 and R=10 (App. G.1).
- **average turns passed @R**, **pass rate @R**: mean turns passed per scenario, and the share of scenarios completed end to end (§3.2).
- **feedback levels**: detailed (assertion messages), medium (pass/fail per test), minimal (only that tests failed) (§4.2).
- **model provider agent**: the harness made by the model's maker (Mistral Vibe, Kimi CLI, QwenCode) (§4).
- **infrastructure retries**: up to 10 re-runs of an agent call whose harness process fails, not counted against R (App. F).

**Missing glossary terms:**
- **REST API**: a server exposing typed resources over HTTP, with create/read/update/delete mapped to HTTP methods and outcomes given as status codes, so it can be tested as a black box (App. C).
- **context compaction**: a harness compressing the conversation history when it passes a token threshold, so long sessions fit the context window (App. F).
- **vibe coding**: not defined; generally, building software by prompting an agent and accepting its code with little review.

**Builds on:**
- Single-task coding benchmarks such as SWE-Bench ("real GitHub issues for agents to resolve"), the framing it contrasts with (§1; §2).
- SlopCodeBench, which tracks code-quality loss as agents extend their own solutions over several turns: "Closely related to our work" (§2), but "the number of user interaction turns still remains very low" (§1).
- Multi-turn benchmarks: coding ones (FronTalk, front-end tasks; EvoClaw, dependent subtasks) and simulated-user ones outside coding (τ-Bench, [τ-bench](#/papers/yao2024taubench "$\tau$-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains (2025)"), and τ²-Bench, §2; τ²-Bench and UserBench in Tab. 1).
- Its harness results echo [25], the Holistic Agent Leaderboard (§4.1).

## Problem and setting

The question: how many consecutive change requests can a coding agent handle, and how do model, harness, feedback and retries change that (abstract; §4)?

- **Task:** implement a REST API server from a generated specification (2–3 entities at first), then apply 100 change turns, each combining several changes of the types in Tab. 8 (§3.2; App. D). Specifications reach dozens of entities, codebases thousands of lines (§3.2, Fig. 3b).
- **Correct** means passing the generated HTTP test suite for the current schema, from a typical 20–30 tests at first to 100+ by turns 20–30 (App. D.3). A README "contains all information needed to pass all tests without retries" (§3.2; App. E.1). The agent works in a Docker container without access to the tests (§1).
- **Models and harnesses:** seven open models, from a 24B dense model to a 1T mixture-of-experts one (§4); OpenCode, Mini-SWE (one bash tool, modified to add context compaction) and OpenHands for every model, plus the provider harness where one exists: 26 cells (§4; §4.1; App. F).
- **Defaults:** K=20 scenarios, the same everywhere, N=100 turns and R=2 "unless otherwise noted", Python by default (§4); LLM-driven sampling in the Python runs (Tab. 4 caption). Claims are tested with paired Wilcoxon signed-rank tests, Holm-corrected when one hypothesis spans many cells (§4).
- **Not discussed:** which LLM drives the LLM sampler.

## Approach

- **Framework (§3.1, Alg. 1).** A reference trajectory, deterministic once the seed and action picker are fixed, is tracked by the agent from text descriptions; each turn is tested, and the run stops at the first failure that retries don't fix. The authors claim "correctness guarantees (validity, infinite procedural generation, controlled difficulty)" (§1). App. B sketches three other instantiations, "hypothetical examples showing the framework's generality".
- **REST instantiation (§3.2; App. D).** States are typed OpenAPI-like schemas (structured API descriptions) with entities, relationships, analytics endpoints and business logic (guarded state transitions with side effects). Changes follow strict per-type schemas for validation; tests are generated from the schema and sent through one exposed port, independent of the agent's language.
- **Failure analysis (§5).** An agent reads each run's logs and assigns a failure category (App. G.2).

## Results

As the authors report, on the 20 scenarios.
- **No feedback (R=0, Tab. 2).** Best is GLM-5 with Mini-SWE at 6.2 turns, "highlighting that multi-turn reliability is still a challenge even for the strongest models" (§4.1).
- **Retry loop (R=2, Tab. 3; in the glossary's terms, [self-correction](#/glossary/self-correction)).** All 26 cells improve significantly over R=0 (Holm-corrected) (§4.1); the abstract gives "up to 12×".
- **Harness (Tab. 3).** "OpenCode is the best or statistically indistinguishable from the best for all 7 models" (§4.1). GLM-5 passes 57.0 turns (25% of scenarios completed) with OpenCode, 15.1 with Mini-SWE and 8.7 with OpenHands. "Provider-built harnesses do not reliably help", and model rankings shift across harnesses (§4.1). Weaker models "fail with any harness" (abstract). Qwen3.5-122B is "vastly more efficient for the price" (§4.1, Fig. 2c).
- **More retries (Fig. 2b; Tab. 10).** Stronger models such as GLM-5, Kimi K2.5 and Qwen3.5-122B "improve drastically over the first 5 attempts, and plateau after"; weaker models gain much less (§4.1). At R=10, GLM-5 with OpenCode passes 82.5 turns and completes 65% of scenarios (App. G, Tab. 10).
- **Feedback (Fig. 2a; Tab. 11).** Detailed feedback yields "6–12× more turns completed than minimal feedback across all models"; GLM-5 falls from 57 to 10.7 (§4.2).
- **Language and sampler (Tab. 4).** All models trend lower in Rust, significantly for some, hypothesized to reflect less Rust REST training data; the programmatic sampler "does not significantly differ from LLM-driven sampling for any model except Nemotron Super" (§4.2).
- **Noise (App. G.1, Tab. 12).** From five reruns of Qwen3.5-122B with OpenCode, per-configuration averages are "stable to within ∼6–7 turns" (§4).
- **Failures (§5; Figs. 3–6).** With R=0 and R=2, "most agents make mistakes by not following the provided instructions exactly", making validation too strict or too loose; agents "likely pay less and less attention to them as the context grows across turns", as prior work found ([28, 19]; [19] is on context rot, quality loss as inputs grow). Agents also "hallucinate new unrequested changes". At R=10 infrastructure issues "come up more": tool calls during OpenCode's compaction, OpenHands' loop detector ending sessions, agents killing their own harness with a loose `pkill`. "With feedback and enough retries, agents are able to eventually figure out a lot of the implementation issues, and are bottlenecked by infrastructure more" (§5).

## Limits the authors state

- "Multi-turn evaluation is inherently expensive": billions of input tokens per configuration, "putting a full closed-source comparison out of reach for us" (§6 "Limitations"; App. A).
- "More scenarios may be needed for more statistical power" (§6 "Limitations"); repeating every configuration "would be prohibitively costly", so noise is estimated on one (App. G.1).
- One task, REST servers: "specific findings may not hold in other domains", though they "argue that REST is broad enough to encompass a large portion of software engineering problems" (§6 "Limitations").
- Detailed feedback "is not available in most contexts" (§6).
- Several ablation trends do not reach significance with 20 scenarios (§4.2).
- Re-reading the always-present instructions file "does not fully prevent the failures" (§5).

## Open problems and building blocks

- **Open:** the benchmark is released "to enable further research into multi-turn coding agent behavior" (abstract); the authors stress "improving reliability of coding agents beyond single one-off tasks" (§6). Named bottleneck: with feedback and retries, infrastructure (§5); multi-turn work tests a harness's ability "to compress context without losing important instructions, and to recover from infrastructure issues like malformed tool calls" (§6).
- **Released:** "the benchmark and the generated tasks" (abstract); the implementation, for new scenarios "possibly spanning far more than 100 turns", and "the data we used in our experiments" (§6); "all code and configurations" (§6 "Broader Impact").
- **To reuse it:** Docker with full shell access (App. F). A scenario takes "roughly 4–8 hours", and 20-scenario sweeps finish "in under a day on commodity infrastructure when fully parallelized" (App. A).
- **Beyond its domain:** the framework is "instantiable in any domain where initial design, change requests, and tests can be procedurally defined" (§1; App. B).
