# Sourcing realistic, hard query pairs

> Checkers and benchmarks need many query pairs that are *nearly* equivalent. Where do they come from, and how are they labelled?

<p class="tags"><a class="tag" href="#/tags/dialect">dialect</a><a class="tag" href="#/tags/pairgen">pairgen</a><a class="tag" href="#/tags/pairs">pairs</a></p>

## Challenge
Build a steady supply of diverse query pairs with known or checkable labels, covering the SQL features where tools fail. Not yet done (ours): public sets are small, narrow or equivalent-only, and realistic pairs cost hand work and lack certified labels.

## What's known
- Public pair sets are small or narrow, the SQLEquiQuest authors say ([Can the Rookies Cut…](#/papers/singh2024sqlequiquest "Can the Rookies Cut the Tough Cookie? Exploring the Use of LLMs for SQL Equivalence Checking (2024)") §3), and its Tab. 4 takes SPES's, EQUITAS's and UDP's results on Calcite's equivalent-only rule tests from their own papers. LLM rewrites of TPC-DS queries and of ReSequel's workloads mostly fall outside what SQLSolver proves ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §6; [ReSequel](#/papers/fathollahzadeh2026resequel "ReSequel: Robust LLM-assisted Query Rewriting and Optimization using Templatization and Sampling (2026)") §7.2, Tab. 4; [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps) § What's known). Of LLM rewrites of benchmark and StackOverflow queries that agree on generated test databases, EquiTrace, QED and SQLSolver together prove fewer than half ([EquiTrace](#/papers/chen2026equitrace "Building SQL Equivalence Proofs from Query Rewrite Rules (2026)") §4.1, §4.3, Tab. 3, our count).
- Pairs with labels by construction: Argus has an LLM write equivalent query skeletons, keeps those a prover proves, and fills their blanks with reusable snippets, giving many equivalent pairs ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") abstract, §1, §6.2); SLER's text links none of its enumerated rules (ours, a search of its LaTeX: [SLER](#/papers/zhang2026sler "Efficient Query Rewrite Rule Discovery via Standardized Enumeration and Learning-to-Rank (2026)")). Outside SQL, Poon et al.'s [self-play](#/glossary/self-play) has one model copy rewrite a Haskell function into an equivalent one with a Liquid Haskell proof or a different one with a diverging input, keeps a pair only if the tool accepts the proof or execution confirms the input, and scores its difficulty by how often a second copy misjudges it ([Semantic Equivalence Self-Play (SEQ/SINQ](#/papers/poon2026selfplay "Improving LLM Code Reasoning via Semantic Equivalence Self-Play with Formal Verification (2026)") §3.3, §3.4.1, §4); its authors report that, with both games chosen equally often, accepted proofs were rare, so the verified pairs were mostly inequivalent (§5.4, §8).
- Realistic pairs today cost hand work and lack certified labels (ours): SQL-RewriteBench's DBAs enriched workload queries, which may expose no measurable rewrite opportunity, and each enriched query was reviewed by hand against its reference rewrite ([SQL-RewriteBench](#/papers/long2026sqlrewritebench "SQL-RewriteBench: A Correctness-Gated, Full-Denominator Benchmark for Statement-Level SQL Rewriting (2026)") §4.1), and its labels are result consistency on packaged data (§5.1).

Still open (ours): a steady supply of diverse, realistic near-miss pairs, covering the SQL features where tools fail, each with a proof, a counterexample or an honest *unknown*.

## Why it matters
- **Coverage numbers that match real use.** The SQLEquiQuest authors call Calcite's rewrite tests a collection "repurposed to verify that the formal equivalence checking algorithms are indeed behaving as expected", with only equivalent pairs (§3). QED verified none of QO-Verify's LLM rewrites of real enterprise queries ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §5). On SQL-RewriteBench's DBA-enriched pairs, SQLSolver mostly returned unknown or timed out, and VeriEQL couldn't parse or support most ([SQL-RewriteBench](#/papers/long2026sqlrewritebench "SQL-RewriteBench: A Correctness-Gated, Full-Denominator Benchmark for Statement-Level SQL Rewriting (2026)") §7.4). Realistic pairs turn [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps) into a measured number. Not every checker drops: QO-Verify verifies similar fractions of real and benchmark rewrites (§4.3, Fig. 12).
- **Bugs in the checkers.** Every certified label in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) rests on the checkers (ours), and the prover bugs reported so far (Argus, cvc5's authors) are in [Can SQL equivalence checkers be trusted?](#/challenges/checker_soundness); pairs sourced near their rules' edges are what would find more (ours).
- **LLM evaluations that measure reasoning, not a lean or a memory.** On Calcite's equivalent-only pairs, the model that almost never answers "not equivalent" on the other two sets scores best ([Can the Rookies Cut…](#/papers/singh2024sqlequiquest "Can the Rookies Cut the Tough Cookie? Exploring the Use of LLMs for SQL Equivalence Checking (2024)") Tab. 2, §5.1); in our reading, such a set rewards the bias. The SQLEquiQuest authors argue that LLMs have likely seen existing datasets (§1, §3.1), and the QO-Verify authors that writing on tuning public benchmark queries has likely been used for training (§1). On near-miss pairs the authors made by hand from real workloads, the models Rahaman et al. test mostly err by calling non-equivalent pairs equivalent, often where a condition was changed ([Evaluating SQL Understanding in…](#/papers/rahaman2024sqlunderstanding "Evaluating SQL Understanding in Large Language Models (2025)") §1, §3.2, §4.4). Outside SQL, the EquiBench authors report that models lean towards "equivalent" for syntactically similar program pairs and "inequivalent" for dissimilar ones, and suggest that benchmarks emphasize dissimilar equivalent and similar inequivalent pairs ([EquiBench](#/papers/wei2025equibench "EquiBench: Benchmarking Large Language Models' Reasoning about Program Semantics via Equivalence Checking (2025)") §5.2); [Bringing compact models to frontier accuracy](#/challenges/compact_model_accuracy) needs such pairs (ours).

**Size of the gain:** enabler, our estimate. The quantity it lifts is what [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps), [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and [Bringing compact models to frontier accuracy](#/challenges/compact_model_accuracy) measure on realistic pairs, counted here as the realistic, nearly equivalent pairs with a [certificate](#/glossary/certificate) or an honest *unknown*. The reason: pairs are an input to all three, and today realistic pairs cost hand work and lack certified labels (§ What's known); much of the supply would come as a by-product of [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) and the [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop).

## Why it's hard
- Pairs made with trusted rules are equivalent by construction only if the rules, the prover and the rewriter that applies them are right (rewriter bugs: [ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") abstract; prover bugs: [Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") §8), and they follow rule patterns rather than real workloads.
- Mutants of a query are cheap near-misses, but some are equivalent to it, and a refuter that fails to kill one can't tell which case it is in. XData's authors wrote their mutants by hand for this reason ("we would not be sure if that was because of the incompleteness of our tool or because of equivalence of mutation and the original query", [XData](#/papers/chandra2014xdata "Data generation for testing and grading SQL queries (2015)") §13.1, footnote), and [test-suite accuracy](#/glossary/test-suite-accuracy)'s undistinguished neighbour queries include some "accidentally semantically equivalent to the gold" ([Semantic Evaluation for Text-to-SQL…](#/papers/zhong2020testsuite "Semantic Evaluation for Text-to-SQL with Distilled Test Suites (2020)") App. A.2). A prover would label the equivalent ones ([SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps)).
- Realistic near-misses ([text-to-SQL](#/glossary/text-to-sql) outputs, LLM rewrites, dialect translations) have no labels until they are checked. VeriEQL's authors pair queries LeetCode accepted with their own reference; some accepted ones are wrong, as the site's tests miss cases ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.1). Outside SQL, JudgeBench keeps questions where one model's samples split between right and wrong, giving hard pairs that its authors say may be disproportionately hard for that model ([JudgeBench](#/papers/tan2024judgebench "JudgeBench: A Benchmark for Evaluating LLM-based Judges (2025)") §3).
- Hand labels err too: pairs listed as equivalent in [Evaluating SQL Understanding in…](#/papers/rahaman2024sqlunderstanding "Evaluating SQL Understanding in Large Language Models (2025)") (Listing 2) and [Taming SQL Complexity](#/papers/zeng2025taming "Taming SQL Complexity: LLM-Based Equivalence Evaluation for Text-to-SQL (2025)") (App.

## Verifiable signal
Labels come from the checker: a proof or counterexample, or *unknown* (the hard pairs worth keeping).
