# Reliability that holds with size, by handing the procedure to an engine

> When a compact model writes a DSL program and an engine runs it, does its success rate hold as tasks grow, in data and in composition, and does the model know when the engine is the right tool?

<p class="tags"><a class="tag" href="#/tags/compact">compact</a><a class="tag" href="#/tags/longctx">longctx</a><a class="tag" href="#/tags/offload">offload</a></p>

## Challenge
A model reasoning in text must carry every step itself, so its errors compound with the length of the job ([Whole-job reliability of multi-step LLM work](#/challenges/whole_job_reliability)). A model that writes a program hands the steps to an engine that runs them exactly. Two kinds of growth are worth separating:
- **Data:** more rows, nodes or events. When the engine reads the data, the program stays the same length, so DSL use should hold where reasoning over the data in context fails (ours).
- **Composition:** more steps, joins, predicates or rule exceptions in the program the task needs. The program grows, so this is where writing it well, and a learned skill, should matter (ours).

## What's known
- Routed to a constraint solver, GPT-4o stayed steady on ordering puzzles of three to seven objects while zero-shot and CoT prompting fluctuated, the authors report ([Adaptive LLM-Symbolic Reasoning via…](#/papers/xu2025adaptive "Adaptive LLM-Symbolic Reasoning via Dynamic Logical Solver Composition (2026)") §3.5, Fig. 2).
- E.2).
- **The flattening is not uniform:** in most model–dataset pairs of planning and logic puzzles, revised Python formalizations still lost much accuracy as constraints grew ([A Reality Check of…](#/papers/amonkar2025realitycheck "A Reality Check of Language Models as Formalizers on Constraint Satisfaction Problems (2026)") §5.2), and with a code tool small Qwen instruct models still declined as circuit depth grew, while frontier ones with it held ([Tool Use Reduces Depth-Induced…](#/papers/koplow2026depthcollapse "Tool Use Reduces Depth-Induced Collapse in OOD Reasoning (2026)") Fig. 4, §4.3). Handing ordering puzzles to an enumerative solver kept a 4B Qwen model accurate from three to seven entities as direct answering collapsed, its authors report ("not a full [scaling law](#/glossary/scaling-law)"), but Gemma-3n-E4B's formalizations, all executable there, lost accuracy with size ([Resource-Aware Neuro-Symbolic Reasoning for…](#/papers/ramirez2026vfr "Resource-Aware Neuro-Symbolic Reasoning for Local Small Language Models (2026)") §5, §7, Tab. 4).
- **Text arms, one axis at a time:** on tasks easy item by item, the authors report, success fell as the item count grew in every model tested, and tracked the count more than the total length ([Understanding LLM Performance Degradation…](#/papers/chen2026multiinstance "Understanding LLM Performance Degradation in Multi-Instance Processing: The Roles of Instance Count and Context Length (2026)") §5.1, §6.2); with the context held fixed, four open models' accuracy on Prolog queries still fell with proof depth, which the authors find weighed about as much as length ([Probing for Long-Horizon Deductive…](#/papers/alnegheimish2026prolong "Probing for Long-Horizon Deductive Reasoning Capabilities in Language Models with Prolog (2026)") §4.5), though SWI-Prolog answers even the largest programs quickly (§3.3) and the paper has no engine arm (ours). A 4B model fine-tuned per task lost far more as the collection grew on tasks whose work grows quadratically, such as finding all contradicting pairs, than on linear ones ([No More Free Lunch](#/papers/singhal2026ctcbench "No More Free Lunch: Corpus Task Complexity Matters as Corpora Grow (2026)") §2.1, §3).
- **Over agent logs, outside DSLs:** the authors report that TallyMem, where deterministic code counts the events a model specifies, did not decline as the count grew, while reading the history did ([When Agent Memory Needs to Compute](#/papers/yang2026tallymem "When Agent Memory Needs to Compute: Evidence Access and Executable Aggregation (2026)") abstract, §7.4, Fig. 2). With Qwen3-8B as reader it fell at the highest bound when the reader recounted (App. H), and in Tab. 13 the fixed counter, and TallyMem by one question, dip at the largest software bound, though App.
- **On table questions** (WikiTableQuestions), [exact match](#/glossary/exact-match) fell with table size before context limits mattered (§6.3.1), and a GPT-3-written row filter helped more as tables grew, but only behind a detector: applied to every question, it lowered OmniTab's score ([Externalising Reasoning by Teaching…](#/papers/gemmellgorriz2026externalising "Externalising Reasoning by Teaching Language Models to Use Programs as Tools (2026)") §6.5.2, §6.5.4, Tabs. 6.3, 6.6, PDF pp. 90–99).
- **Open:** the same measurement on compact open models writing data DSLs ([XPath](#/glossary/xpath), SQL, SPARQL, recurrence rules, regular expressions); none was found. It includes deciding to use the engine at all (§ Why it's hard).

## Why it matters
- **It tests the brainstorm's premise directly:** that a DSL moves an LLM from informal to procedural reasoning, measured as reliability against size rather than accuracy at one size (ours).
- **For DSL users:** XPath, SQL and the rest run real systems; a model that writes them reliably as the request grows is the practical form of the gain.

**Size of the gain:** step change, measured as the composition level at which a compact model keeps a fixed success rate, with a learned skill against zero-shot DSL use. This is our estimate: the flattening is shown mostly with large models, on arithmetic, logic and graph tasks ([PAL (Program-aided Language Models)](#/papers/gao2022pal "PAL: Program-aided Language Models (2022)"), [Logic-LM](#/papers/pan2023logiclm "Logic-LM: Empowering Large Language Models with Symbolic Solvers for Faithful Logical Reasoning (2023)"), [Unified Multi-Dimensional Benchmark for…](#/papers/wang2026graphgym "Unified Multi-Dimensional Benchmark for Complex Graph Reasoning in Large Language Models (2026)")), and not uniformly (§ What's known).

## Why it's hard
- **Compact models write DSLs poorly:** "models with small parameter sizes have significant difficulties in understanding and writing executable paths" ([AutoScraper](#/papers/huang2024autoscraper "AutoScraper: A Progressive Understanding Web Agent for Web Scraper Generation (2024)") §5.2), and with models whose "code modeling ability" is weak, CoT beat PAL ([PAL (Program-aided Language Models)](#/papers/gao2022pal "PAL: Program-aided Language Models (2022)") §6); in small-scale tests, models "without sufficient coding capabilities struggle" as recursive models over a long input in a [REPL](#/glossary/repl-read-eval-print-loop) ([RLM (Recursive Language Models)](#/papers/zhang2025rlm "Recursive Language Models (2025)") App. B).
- **Programs miscopy values:** in the authors' manual analysis of greedy PoT's failures on TAT-QA numerical questions, most errors are value-grounding errors, a variable given a wrong value from the table or text ([PoT (Program of Thoughts prompting)](#/papers/chen2022pot "Program of Thoughts Prompting: Disentangling Computation from Reasoning for Numerical Reasoning Tasks (2023)") §3.3); the paper doesn't relate them to composition or question complexity.
- **The measurement is of the model–engine pair:** driving a SQL client's agent with local models, the authors trace many failed runs to the interface (complete tool calls written as reply text, values under the wrong field), raise several models' results with server-side fixes that touch no model, prompt or task ("field observations with known confounds, not an ablation", §7), and suggest that a benchmark fixing its rejection messages and argument parsing "is measuring the pair rather than the model" ([What Stops a Small…](#/papers/bozoglan2026slmdbagent "What Stops a Small Language Model From Driving a Database Agent (2026)") §6, §7, §9). On a function-calling benchmark, malformed or truncated output was a far larger share of an 8B endpoint's failures than of the 70B and Gemini endpoints' ([Noise Floor Audit for Agent Benchmarks](#/papers/chen2026noisefloor "Noise Floor Audit for Agent Benchmarks (2026)") §4, Tab. 4), so interface failures that shrink with size could pass for reasoning gains (ours).
- **When the program must carry the data,** as a PDDL problem file does, it grows: a 32B open model's PDDL degraded at the largest BlocksWorld instances, though writing it one line per call restored it ([Language Models as Higher-Order…](#/papers/jiang2026higherorder "Language Models as Higher-Order Planning Formalizers (2026)") §2.2, Fig. 4a); a Python program printing the PDDL improved it clearly in BlocksWorld and Transport, barely in Elevators and not in ChildSnack (Fig. 4b–e; ours, against §4's "nearly all domains"; that its prompts may carry the gain: Program-aided reasoning).
- **Choosing the tool is itself unreliable:** testing several steering methods, "there is no optimal method to correctly steer LLMs to write code when needed", code's results "are not always better than using textual reasoning, even if the task could be solved through code", and the choice shows, with model size, "an astonishingly inverse scaling behavior" ([Steering Large Language Models…](#/papers/chen2024steering "Steering Large Language Models between Code Execution and Textual Reasoning (2025)") abstract, §2.2). Given several solvers, GPT-4o and DeepSeek-V3.1 nearly always picked the right one ([Adaptive LLM-Symbolic Reasoning via…](#/papers/xu2025adaptive "Adaptive LLM-Symbolic Reasoning via Dynamic Logical Solver Composition (2026)") §3.2, Tab. 1); for open-source models, DeepSeek-V3.1 among them, invalid formalization was the main error type, GPT-4o's mostly semantic (§3.7, which calls it DeepSeek-V3).
- **Results claimed but never computed:** in legal entailment with Z3, the authors of [Know Your Limits](#/papers/wang2026limits "Know Your Limits: On the Faithfulness of LLMs as Solvers and Autoformalizers in Legal Reasoning (2026)") report that every model tested sometimes gave solver-style verdicts "without executing the underlying code", which they call scope laundering (§5.4); a harness that runs the engine on every answer rules this out (ours).
- **A wrong program runs without complaint**, so the check must compare results with a reference on data that separates right from wrong ([Weak checkers get exploited](#/challenges/weak_checker_exploitation)).
- **Baselines are uneven:** plain-text reasoning works only while the data fits in context, so the main baseline is the same model with the same engine and no learned skill (ours).
- **Composition needs a generator with a dial**, which few existing datasets have (ours; [A gym of DSL tasks with answer keys made by code](#/challenges/dsl_gym)).

## Verifiable signal
The engine runs the model's program and the task's hidden program on the shown data and on held-out variants; the answer passes only if the results match on all of them. Success rate is reported per size bucket on each axis, with [pass^k](#/glossary/passk-reliability-over-k-trials) (all k samples pass) for reliability, and the arms are compared as [Comparing LLM methods under noise](#/challenges/method_comparison_under_noise) requires.
