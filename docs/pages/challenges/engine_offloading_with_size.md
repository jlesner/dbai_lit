# Reliability that holds with size, by handing the procedure to an engine

> When a compact model writes a DSL program and an engine runs it, does its success rate hold as tasks grow, in data and in composition, and does the model know when the engine is the right tool?

<p class="tags"><a class="tag" href="#/tags/compact">compact</a><a class="tag" href="#/tags/general">general</a></p>

## Challenge
A model reasoning in text must carry every step itself, so its errors compound with the length of the job ([Whole-job reliability of multi-step LLM work](#/challenges/whole_job_reliability)). A model that writes a program hands the steps to an engine that runs them exactly. Two kinds of growth are worth separating:
- **Data:** more rows, nodes or events. When the engine reads the data, the program stays the same length, so DSL use should hold where reasoning over the data in context fails (ours).
- **Composition:** more steps, joins, predicates or rule exceptions in the program the task needs. The program grows, so this is where writing it well, and a learned skill, should matter (ours).

- E.2).
- **The flattening is not uniform:** in most model–dataset pairs, revised Python formalizations still lost much accuracy as constraints grew ([A Reality Check of…](#/papers/amonkar2025realitycheck "A Reality Check of Language Models as Formalizers on Constraint Satisfaction Problems (2026)") §5.2), and with an interpreter small instruct models still declined with depth, while frontier ones with tools held ([Tool Use Reduces Depth-Induced…](#/papers/koplow2026depthcollapse "Tool Use Reduces Depth-Induced Collapse in OOD Reasoning (2026)") Fig. 4, §4.3).
- **On table questions,** [exact match](#/glossary/exact-match) fell with table size before context limits mattered, and a generated row filter helped more as tables grew, but only behind a detector: applied to every question, it lowered OmniTab's score ([Externalising Reasoning by Teaching…](#/papers/gemmellgorriz2026externalising "Externalising Reasoning by Teaching Language Models to Use Programs as Tools (2026)") §6.3.1, Tabs. 6.3, 6.6, PDF pp. 90–99).
- **Open:** the same measurement on compact open models writing data DSLs (XPath, SQL, SPARQL, recurrence rules, regular expressions); none was found. It includes deciding to use the engine at all, since "results from LLM written code are not always better than using textual reasoning, even if the task could be solved through code" ([Steering Large Language Models…](#/papers/chen2024steering "Steering Large Language Models between Code Execution and Textual Reasoning (2025)") abstract).

## Why it matters
- **It tests the brainstorm's premise directly:** that a DSL moves an LLM from informal to procedural reasoning, measured as reliability against size rather than accuracy at one size (ours).
- **For DSL users:** XPath, SQL and the rest run real systems; a model that writes them reliably as the request grows is the practical form of the gain.

**Size of the gain:** step change, measured as the composition level at which a compact model keeps a fixed success rate, with a learned skill against zero-shot DSL use. This is our estimate: the flattening is shown mostly with large models, on arithmetic, logic and graph tasks ([PAL (Program-aided Language Models)](#/papers/gao2022pal "PAL: Program-aided Language Models (2022)"), [Logic-LM](#/papers/pan2023logiclm "Logic-LM: Empowering Large Language Models with Symbolic Solvers for Faithful Logical Reasoning (2023)"), [Unified Multi-Dimensional Benchmark for…](#/papers/wang2026graphgym "Unified Multi-Dimensional Benchmark for Complex Graph Reasoning in Large Language Models (2026)")), and not uniformly (§ What's known).

## Why it's hard
- **Compact models write DSLs poorly:** "models with small parameter sizes have significant difficulties in understanding and writing executable paths" ([AutoScraper](#/papers/huang2024autoscraper "AutoScraper: A Progressive Understanding Web Agent for Web Scraper Generation (2024)") §5.2), and with models whose "code modeling ability" is weak, CoT beat PAL ([PAL (Program-aided Language Models)](#/papers/gao2022pal "PAL: Program-aided Language Models (2022)") §6); in small-scale tests, models "without sufficient coding capabilities struggle" as recursive models over a long input in a [REPL](#/glossary/repl-read-eval-print-loop) ([RLM (Recursive Language Models)](#/papers/zhang2025rlm "Recursive Language Models (2025)") App. B).
- **Programs miscopy values:** in the authors' manual analysis of 198 PoT (greedy) failures on TAT-QA numerical questions, 47% are value-grounding errors (a variable gets a wrong value from the table or text) and 15% combine them with logic errors ([PoT (Program of Thoughts prompting)](#/papers/chen2022pot "Program of Thoughts Prompting: Disentangling Computation from Reasoning for Numerical Reasoning Tasks (2023)") §3.3, Fig. 7). The paper does not relate these errors to composition or question complexity.
- **The measurement is of the model–engine pair:** driving a SQL client's agent with local models, the authors trace many failed runs to the interface (complete tool calls written as reply text, values under the wrong field), raise several models' results with server-side fixes that touch no model, prompt or task ("field observations with known confounds, not an ablation", §7), and suggest that a benchmark fixing its rejection messages and argument parsing "is measuring the pair rather than the model" ([What Stops a Small…](#/papers/bozoglan2026slmdbagent "What Stops a Small Language Model From Driving a Database Agent (2026)") §6, §7, §9). On a function-calling benchmark, malformed or truncated output was a far larger share of an 8B endpoint's failures than of the 70B and Gemini endpoints' ([Noise Floor Audit for Agent Benchmarks](#/papers/chen2026noisefloor "Noise Floor Audit for Agent Benchmarks (2026)") §4, Tab. 4), so interface failures that shrink with size could pass for reasoning gains (ours).
- **Choosing the tool is itself unreliable:** testing several steering methods, "there is no optimal method to correctly steer LLMs to write code when needed", and the choice shows "an astonishingly inverse scaling behavior" ([Steering Large Language Models…](#/papers/chen2024steering "Steering Large Language Models between Code Execution and Textual Reasoning (2025)") abstract). Given several solvers, GPT-4o and DeepSeek-V3.1 nearly always picked the right one ([Adaptive LLM-Symbolic Reasoning via…](#/papers/xu2025adaptive "Adaptive LLM-Symbolic Reasoning via Dynamic Logical Solver Composition (2026)") §3.2); for open-source models, DeepSeek-V3.1 among them, invalid formalization was the main error type, GPT-4o's mostly semantic (§3.7, which calls it DeepSeek-V3).
- **Results claimed but never computed:** in legal entailment with Z3, the authors of [Know Your Limits](#/papers/wang2026limits "Know Your Limits: On the Faithfulness of LLMs as Solvers and Autoformalizers in Legal Reasoning (2026)") report that every model tested sometimes gave solver-style verdicts "without executing the underlying code", which they call scope laundering (§5.4); a harness that runs the engine on every answer rules this out (ours).
- **A wrong program runs without complaint**, so the check must compare results with a reference on data that separates right from wrong ([Weak checkers get exploited](#/challenges/weak_checker_exploitation)).
- **Baselines are uneven:** plain-text reasoning works only while the data fits in context, so the main baseline is the same model with the same engine and no learned skill (ours).
- **Composition needs a generator with a dial**, which few existing datasets have ([A gym of DSL tasks with answer keys made by code](#/challenges/dsl_gym)).

## Verifiable signal
The engine runs the model's program and the task's hidden program on the shown data and on held-out variants; the answer passes only if the results match on all of them. Success rate is reported per size bucket on each axis, with [pass^k](#/glossary/passk-reliability-over-k-trials) for reliability, and the arms are compared as [Comparing LLM methods under noise](#/challenges/method_comparison_under_noise) requires.
