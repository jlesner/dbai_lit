# A gym of DSL tasks with answer keys made by code

> Task families in several DSLs (predict a program's output, write a program from examples or from English, decide whether two programs agree and show where they don't) whose answer keys come from the engine, with a size setting on two axes, and checks whose false accepts are measured.

<p class="tags"><a class="tag" href="#/tags/general">general</a><a class="tag" href="#/tags/labels">labels</a></p>

## Challenge
Every claim about DSL use rests on tasks whose answers a program checks.
- **Families that differ in what they produce:** a program's output on an input; a program from examples; a program from English; whether two programs agree, with a distinguishing input when they don't.
- **Answer keys made by code:** the engine computes every key, and the input fixes the answer.
- **A size setting on two axes,** data (rows, nodes) and composition (steps, predicates) ([Reliability that holds with size, by handing the procedure to an engine](#/challenges/engine_offloading_with_size)).
- **Checks with measured false accepts** on planted wrong and degenerate answers.

## What's known
Some DSLs already have families that pass them: regular expressions and recurrence rules; SQL is the yardstick there. Filed regex families: Query4Regex computes each target by applying a short sequence of sampled operations and checks answers by DFA equivalence ([Query4Regex](#/papers/hahn2026query4regex "Query4Regex: Verifiable Regex Transformation through Formal Operations from NL and DSL Queries (2026)") §3.2, §4.3, PDF p. 3), and CEGL's regex-from-examples tasks have an exact checker and two difficulty axes, minimized-DFA states and star depth ([Counterexample Guided Learning in…](#/papers/liu2026cegl "Counterexample Guided Learning in the Large using Reasoning Agents (2026)") §5). AutoScraper's web-extraction evaluation counts a generated XPath as correct when its precision and recall both equal 1 ([AutoScraper](#/papers/huang2024autoscraper "AutoScraper: A Progressive Understanding Web Agent for Web Scraper Generation (2024)") §3.3), a check by results rather than by matching a reference path (ours). Generated families outside DSLs show the parts working: CodeI/O turns Python functions into output- and input-prediction tasks whose answers are checked by running the code, with caps on run time and object size ([CodeI/O](#/papers/li2025codeio "CodeI/O: Condensing Reasoning Patterns via Code Input-Output Prediction (2025)") §2.3–2.4, App. A); Guru generates Zebra and ordering puzzles from a sampled solution, at set difficulty levels, and keeps ordering puzzles' answers unique by [constraint propagation](#/glossary/constraint-propagation) ([Revisiting Reinforcement Learning for…](#/papers/cheng2025guru "Revisiting Reinforcement Learning for LLM Reasoning from A Cross-Domain Perspective (2025)") App. B.4). For OCL and Alloy, whose constraints can't always be run, one study scores correctness with an LLM judge it validated against one author's labels ([A framework for assessing…](#/papers/delgado2026constraintdsl "A framework for assessing the capabilities of code generation of constraint domain-specific languages with large language models (2026)") §1, §5.1, Tab. 2; LLM as judge), the kind of check that keys made by code replace (ours).

Still open (ours): the four parts together, with keys made by code and false accepts measured across the size range, for XPath or any other DSL of the family.

## Why it matters
- **Everything else is scored here:** the loop, the size curves and the control all depend on it (ours).
- **It is the prompt-only testbed the user's purposes list**, serving a methods paper on compact models across several testbeds and a public benchmark suite.
- **Fresh instances in any number:** generated tasks keep appearing after any training cutoff (ours).

**Size of the gain:** enabler, our estimate. The quantity it lifts is the one [Reliability that holds with size, by handing the procedure to an engine](#/challenges/engine_offloading_with_size) measures, the composition level at which a compact model keeps a fixed success rate, which [Prompt-space self-play judged by an engine](#/challenges/prompt_space_self_play) and [Learning a rarely seen DSL in prompts](#/challenges/unseen_dsl_in_prompts) also report on. The reason: none of them can be measured without tasks whose keys are made by code and whose checks' false accepts are known.

## Why it's hard
- **The input must fix the answer:** from examples, many programs fit, the more the richer the grammar ([Overfitting in Synthesis](#/papers/padhi2019overfitting "Overfitting in Synthesis: Theory and Practice (2019)") §3.3); the check must be consistency with what the solver was shown, or the generator must keep only instances whose answer is unique (§ 8, T7).
- **Code-made keys and scorers can be wrong:** an audit found defects in some Reasoning Gym tasks and SynLogic generators, such as a scorer giving full credit to any nonempty answer, and its authors conclude "procedural generation alone does not guarantee correctness" ([Reasoning Core](#/papers/sileo2026reasoningcore "Reasoning Core: Designing Broad Procedural Data for Completion-Supervised Reasoning Training (2026)") abstract, §3.4); some of GraphGym's LLM-written reference solvers were wrong before human tests ([Unified Multi-Dimensional Benchmark for…](#/papers/wang2026graphgym "Unified Multi-Dimensional Benchmark for Complex Graph Reasoning in Large Language Models (2026)") §3). VeRA's audits of code-made math items found "edge-case arithmetic, ambiguous renderings, and degenerate parameter regimes", which its authors say "motivate independent item review even after a program passes execution checks" ([VeRA](#/papers/cheng2026vera "VeRA: Renewing Reasoning Benchmarks with Executable Specifications (2026)") App. B).
- **Equivalence needs a decision procedure or a search:** for the regular fragment of regular expressions an automaton decides it (the authors of [Word Problems Requiring Exponential Time](#/papers/stockmeyer1973word "Word Problems Requiring Exponential Time (Preliminary Report) (1973)") say equivalence of Kleene's regular expressions "has several effective solutions, all of which are computationally inefficient", §1, PDF p. 1; equivalence of deterministic finite automata is decided by [A Linear Algorithm for…](#/papers/hopcroft1971linear "A Linear Algorithm for Testing Equivalence of Finite Automata (1971)"), algorithm §III, Thms. 1–2 in §IV, PDF pp. 5–8; turning an expression into such an automaton is the standard construction, in neither paper: ours; § 10.48 runs it through greenery); for SQL a distinguishing database must be searched for, and failing to find one doesn't prove agreement (ours; [Query equivalence: prove or refute](#/challenges/query_equivalence)); for XPath a static analyzer decides equivalence on a navigational fragment without counting or value tests (the decision procedure: [Efficient Static Analysis of…](#/papers/geneves2007efficient "Efficient Static Analysis of XML Paths and Types (2007)") §8, PDF p. 9, and Thm. 6.3, PDF p. 7, with its cost in Lemma 6.7; the tool: [XML Static Analyzer User Manual](#/papers/geneves2008analyzer "XML Static Analyzer User Manual (2008)") §2 Example 3, Fig. 7, §3.1), and outside it a document must be searched for.
- **Engines disagree at the edges:** dialects and engine versions read some programs differently (§ 10.48 for regular expressions; ours for XPath 1.0 against later versions).

## Verifiable signal
The gym is itself checked: for each family, the share of planted wrong and degenerate answers its check accepts, and for each generated instance, that the engine's key is unique under the family's rule ([Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth)).
