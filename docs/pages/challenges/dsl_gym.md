# A gym of DSL tasks with answer keys made by code

> Task families in several DSLs (predict a program's output, write a program from examples or from English, decide whether two programs agree and show where they don't) whose answer keys come from the engine, with a size setting on two axes, and checks whose false accepts are measured.

<p class="tags"><a class="tag" href="#/tags/dsl">dsl</a><a class="tag" href="#/tags/gym">gym</a><a class="tag" href="#/tags/labels">labels</a></p>

## Challenge
The research path's claims (self-taught DSL skills) rest on tasks whose answers a program checks.
- **Families that differ in what they produce:** a program's output on an input; a program from examples; a program from English; whether two programs agree, with a distinguishing input when they don't.
- **Answer keys made by code:** the engine computes every key, and the input fixes the answer.
- **A size setting on two axes,** data (rows, nodes) and composition (steps, predicates) ([Reliability that holds with size, by handing the procedure to an engine](#/challenges/engine_offloading_with_size)).
- **Checks with measured false accepts** on planted wrong and degenerate answers.

## What's known
Some DSLs already have families that pass them: regular expressions and recurrence rules (§ 10.2), with SQL the yardstick; [XPath](#/glossary/xpath) 1.0's result is in § 10.50. AutoScraper's web-extraction evaluation counts a generated scraper (a sequence of XPaths, §4.1) as correct when its precision and recall both equal 1 ([AutoScraper](#/papers/huang2024autoscraper "AutoScraper: A Progressive Understanding Web Agent for Web Scraper Generation (2024)") §3.3), a check by results rather than by matching a reference path (ours). Generated families outside the DSL family show the parts working: CodeI/O turns Python functions into output- and input-prediction tasks whose answers are checked by running the code, with caps on run time and object size ([CodeI/O](#/papers/li2025codeio "CodeI/O: Condensing Reasoning Patterns via Code Input-Output Prediction (2025)") §2.3–2.4, App. A); Guru generates Zebra and ordering puzzles from a sampled solution, the Zebra puzzles at defined difficulty levels, and keeps ordering puzzles' answers unique by [constraint propagation](#/glossary/constraint-propagation) ([Revisiting Reinforcement Learning for…](#/papers/cheng2025guru "Revisiting Reinforcement Learning for LLM Reasoning from A Cross-Domain Perspective (2025)") App. For OCL and Alloy, whose constraints can't always be run, one study scores correctness with an LLM judge it validated against one author's labels ([A framework for assessing…](#/papers/delgado2026constraintdsl "A framework for assessing the capabilities of code generation of constraint domain-specific languages with large language models (2026)") §1, §5.1, Tab. 2; LLM as judge), the kind of check that keys made by code replace (ours).

Still open (ours): the four parts together, with false accepts measured across the size range, for XPath or any other DSL of the family. An open design point, not yet a requirement (ours): a third size control that holds the part of the input a task needs fixed while composition grows, which ProloNg's fixed-context queries don't do (above).

## Why it matters
- **Everything else is scored here:** the loop, the size curves and the control (ours).
- **It is a prompt-only testbed,** which the user's purposes say serves, in order, a methods paper on compact models across several testbeds, a long-term home and a public benchmark suite.
- **Fresh instances in any number,** after any training cutoff (ours).

**Size of the gain:** enabler, our estimate. The quantity it lifts is the one [Reliability that holds with size, by handing the procedure to an engine](#/challenges/engine_offloading_with_size) measures, the composition level at which a compact model keeps a fixed success rate, which [Prompt-space self-play judged by an engine](#/challenges/prompt_space_self_play) and [Learning a rarely seen DSL in prompts](#/challenges/unseen_dsl_in_prompts) also report on. The reason: none of them can be measured without tasks whose keys are made by code and whose checks' false accepts are known.

## Why it's hard
- **The input must fix the answer:** from examples, wrong programs can fit, and in SyGuS theory a grammar that contains another never has fewer that fit ([Overfitting in Synthesis](#/papers/padhi2019overfitting "Overfitting in Synthesis: Theory and Practice (2019)"): [Weak checkers get exploited](#/challenges/weak_checker_exploitation) § What's known); the check must be consistency with what the solver was shown, or the generator must keep only instances whose answer is unique (§ 8, T7).
- **Code-made keys and scorers can be wrong:** an audit found defects in some Reasoning Gym tasks and SynLogic generators, such as a scorer giving full credit to any nonempty answer, and its authors conclude "procedural generation alone does not guarantee correctness" ([Reasoning Core](#/papers/sileo2026reasoningcore "Reasoning Core: Designing Broad Procedural Data for Completion-Supervised Reasoning Training (2026)") abstract, §3.4); some of GraphGym's LLM-written reference solvers were wrong before human tests ([Unified Multi-Dimensional Benchmark for…](#/papers/wang2026graphgym "Unified Multi-Dimensional Benchmark for Complex Graph Reasoning in Large Language Models (2026)") §3). VeRA's audits of code-made math items found "edge-case arithmetic, ambiguous renderings, and degenerate parameter regimes", which its authors say "motivate independent item review even after a program passes execution checks" ([VeRA](#/papers/cheng2026vera "VeRA: Renewing Reasoning Benchmarks with Executable Specifications (2026)") App. B). A check can test less than the task: IFBench's program check of appended output constraints counts a response with little answer content as successful ([CaLIF](#/papers/yoon2026calif "Diagnosing and Correcting Reward Hacking in Verifiable Instruction Following (2026)") §3, Fig. 2).
- **Checks written by LLMs need their own audit,** as when agents build gyms or environments. LLM-written verifiers for agent tasks rejected far more valid solutions than they accepted planted attacks ([VerifierBench](#/papers/yin2026verifierbench "VerifierBench: Benchmarking the Generation of Executable Verifiers for LLM Agents (2026)") §3.2, Tab. 2), and after verifiers were repaired against attacks, which lowered every [attack success rate](#/glossary/attack-success-rate-asr), an attacker that could read the verifier still often succeeded, on Terminal Bench and on SETA's automatically built terminal tasks ([Scalable Weak-to-Strong Verifier Hardening…](#/papers/zeng2026hardening "Scalable Weak-to-Strong Verifier Hardening for Agent Environments (2026)") §4.2, Tab. 1; §4.3.2, Tab. 5). Neither is DSL work; keys and checks made by our code avoid the first, not the second (ours).
- **Equivalence needs a decision procedure or a search:** for the regular fragment of regular expressions an automaton decides it (for Kleene's regular expressions, the authors of [Word Problems Requiring Exponential Time](#/papers/stockmeyer1973word "Word Problems Requiring Exponential Time (Preliminary Report) (1973)") say equivalence "has several effective solutions, all of which are computationally inefficient", §1, PDF p. 1; [A Linear Algorithm for…](#/papers/hopcroft1971linear "A Linear Algorithm for Testing Equivalence of Finite Automata (1971)") decides it for deterministic finite automata, §III–IV, Thms. 1–2, PDF pp. 4–8; turning an expression into one is the standard construction, ours; § 10.48 uses greenery); for SQL, provers cover fragments; outside them a distinguishing database must be searched for, and not finding one doesn't prove agreement (ours; [Query equivalence: prove or refute](#/challenges/query_equivalence)); for XPath a static analyzer decides equivalence, its authors say, on a fragment without counting or data values ([Efficient Static Analysis of…](#/papers/geneves2007efficient "Efficient Static Analysis of XML Paths and Types (2007)"): the fragment §1, §5; the decision procedure §8, PDF p. 9, and Thm. 6.3, PDF p. 7, with its cost in Lemma 6.7; the tool: [XML Static Analyzer User Manual](#/papers/geneves2008analyzer "XML Static Analyzer User Manual (2008)") §2 Example 3, Fig. 7, §3.1), and outside it a document must be searched for.
- **Engines and dialects disagree at the edges** on some programs (§ 10.48 for regular expressions; ours for XPath 1.0 against later versions).

## Verifiable signal
The gym is itself checked: for each family, the share of planted wrong and degenerate answers its check accepts, and for each generated instance, that the engine's key is unique under the family's rule ([Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth)). Also the share of the solver's own wrong answers the check accepts, since planted errors can differ from the ones a solver makes (ours); an audit run only on a policy's fresh outputs can lose sight of the failures it has stopped making, and its authors' repair audits on the policy's own failures and keeps them in the refresh data ([Better Policies, Worse Verifier Audits](#/papers/cieslak2026audits "Better Policies, Worse Verifier Audits (2026)") abstract, §3, §6).
