# Refuting faulty rewrite rules

> Rewriters have edge-case bugs that change query results ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") Tab. II), and so do published rules. Find them with counterexamples.

<p class="tags"><a class="tag" href="#/tags/qo">qo</a><a class="tag" href="#/tags/rewrite">rewrite</a><a class="tag sub" href="#/tags/rules-verify">rules-verify</a></p>

## Challenge
Given a rule-based query rewriter (Calcite, WeTune, the rewriter in SQLSolver's repository, LearnedRewrite: the four that [ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") tests), find rules, or rule implementations, that change query results on some database.

## Why it matters
- **Wrong answers with no warning.** A faulty rule doesn't crash: it changes the result of every query its pattern matches. The ARG authors say such deviations go "silently propagating incorrect data to downstream systems" ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") §III-C) and report them in all four rewriters they tested (Tab. II; the paper doesn't mark which of its reports developers confirmed, §V-B). The RuleScript authors cite optimizer bugs from incorrect transformations in MySQL, PostgreSQL and SQLite ([RuleScript](#/papers/pan2026rulescript "An Extensible and Verifiable Language for Query Rewrite Rules (2026)") §1), and the Calcite team confirmed two rule bugs that VeriEQL's counterexamples exposed ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.3).
- **One rule, many systems.** Calcite's authors name Hive, Flink and others that adopted it as their optimizer ([Apache Calcite](#/papers/begoli2018calcite "Apache Calcite: A Foundational Framework for Optimized Query Processing Over Heterogeneous Data Sources (2018)") §1). LearnedRewrite applies Calcite's rules ([LearnedRewrite](#/papers/zhou2021learnedrewrite "A learned query rewrite system using Monte Carlo tree search (2021)") §6.1), and ARG lists the same `ON FALSE` and `CAST` bugs under both (Tab. II). LLM-R2 calls its rewrites' equivalence "guaranteed" because the rules come from existing rule platforms ([LLM-R2](#/papers/li2024llmr2 "LLM-R2: A Large Language Model Enhanced Rule-Based Rewrite System for Boosting Query Efficiency (2024)") §1), so its guarantee is only as good as those rules.
- **A belief that grows as it is retold.** LLM-rewriter papers describe rule-based rewriting as "verified for correctness" ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §4.3) or as giving "formal correctness guarantees" ([LITHE](#/papers/dharwada2025lithe "LITHE: A Query Rewrite Advisor using LLMs (2026)") App. A.2). Others say the opposite: QUITE's authors report that rule-based methods "suffer from incomplete semantic equivalence", their rules lacking formal verification ([QUITE](#/papers/song2025quite "QUITE: A Query Rewrite System Beyond Rules with LLM Agents (2025)") §7.2), and SlabCity's authors say most rules in rule-based rewriters "are not fully verified" and that their checker proved some of LearnedRewrite's Calcite-rule rewrites incorrect ([SlabCity](#/papers/dong2023slabcity "SlabCity: Whole-Query Optimization Using Program Synthesis (2023)") §5.5).
- **Labels built on rules.** Calcite's rule tests serve as an equivalent-only benchmark, and VeriEQL found non-equivalent pairs among them ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.2–6.3). A faulty rule becomes wrong labels in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and [Sourcing realistic, hard query pairs](#/challenges/query_pair_sourcing), and a wrong entry in the library [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) grows.
- **Refuted once, fixed for every query.** The argument for checking rules rather than queries is old: Starburst split rewriting into small rules "such that each rule can be shown to be correct separately", citing Ganski and Wong's corrections of earlier transformations ([Starburst query rewrite](#/papers/pirahesh1992starburst "Extensible/Rule Based Query Rewrite Optimization in Starburst (1992)") §1.3). The RuleScript authors make it again (§1), yet their verified rules run through adapters that are trusted, not verified (§7.2), so implementations need refuting by execution too (our reasoning).

**Size of the gain:** incremental, measured as confirmed wrong-result rule bugs found per rewriter beyond what rule-guided [fuzzing](#/glossary/fuzzing) (ARG) and bounded checking (VeriEQL) already find. Refuting rules by execution already works, so a better refuter finds more bugs rather than making something possible; the leverage is that each bug fixed protects every query its rule matches. This is our estimate.

## Verifiable signal
Strong. One instance plus a [counterexample database](#/glossary/counterexample-database) refutes the rule, and anyone can check it by execution. The engine is part of the check: ARG traced one result mismatch to MySQL's own behaviour and re-runs mismatches on several DBMSs to tell the two apart ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") §VI, Fig. 8).
