# Refuting faulty rewrite rules

> Rewriters have edge-case bugs that change query results ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") Tab. II), and so do published rules (§ What's known). Find them with counterexamples.

## Challenge
Given a rule-based query rewriter (Calcite, WeTune, the rewriter in SQLSolver's repository, LearnedRewrite: the four that [ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") tests), find rules, or rule implementations, that change query results on some database.

## What's known
Published rules fail on four classes of edge case that recur from the 1980s to now (our grouping):
- *empty inputs:* the COUNT bug in Kim's [subquery](#/glossary/subquery-nested-query) unnesting (found by Kiessling in a 1984 memo, [Optimization of Nested SQL Queries Revisited](#/papers/ganski1987nested "Optimization of Nested SQL Queries Revisited (1987)") §5.1; Kim's paper and the memo are not listed here; Ganski and Wong fixed it with an [outer join](#/glossary/outer-join), §5.2), the same flaw in a group-by push-down rule printed in a 2015 general unnesting procedure, and a Calcite rule that goes wrong on `SUM` over an empty table ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.3);
- *duplicates:* the outer-join fix to Kim's unnesting when the outer join column has duplicates ([Optimization of Nested SQL Queries Revisited](#/papers/ganski1987nested "Optimization of Nested SQL Queries Revisited (1987)") §5.4), rule examples that hold only under [set semantics](#/glossary/set-semantics), two duplicate-elimination rules, SqlRewriter's subquery-to-join rule without a key; under [bag semantics](#/glossary/bag-semantics) a join can't be added or dropped without a key or `DISTINCT` ([Optimization of real conjunctive queries](#/papers/chaudhuri1993real "Optimization of real conjunctive queries (1993)"); see [Canonical forms for queries](#/challenges/query_canonical_forms));
- *NULLs in a `UNIQUE` column*, which is not a key: QueryBooster's self-join rule and WeTune's released rewriter.

Two hazards outside these classes: in a [correlated subquery](#/glossary/correlated-subquery) the columns under an aggregate decide which group it ranges over, so "usual arithmetic equalities are no longer valid" there ([A Coq mechanised formal…](#/papers/benzaken2019coq "A Coq mechanised formal semantics for realistic SQL queries: formally reconciling SQL and bag relational algebra (2019)") §2.2); and optimizers "can skip or reorder expressions and thereby hide or expose runtime cast errors" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §3.6; cases in §6.5), so a refutation compares errors as well as rows (our reasoning). Each class is a hypothesis a fuzzer can be told to try on every rule (our reasoning).

The nearest work already refutes rules by execution: rule-guided [fuzzing](#/glossary/fuzzing) (ARG) and bounded checking (VeriEQL) both report wrong-result bugs in real rewriters (§ Why it matters).

Still open (ours): finding the wrong-result rule bugs that ARG and VeriEQL miss, in the rules and in the code that applies them, including the prover-verified rule files in our clones (§ Why it's hard).

## Why it matters
- **Wrong answers with no warning.** A faulty rule doesn't crash: it changes the result of every query its pattern matches. The ARG authors say such deviations go "silently propagating incorrect data to downstream systems" ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") §III-C) and report them in all four rewriters they tested (Tab. II; the paper doesn't mark which of its reports developers confirmed, §V-B). The RuleScript authors cite optimizer bugs from incorrect transformations in MySQL, PostgreSQL and SQLite ([RuleScript](#/papers/pan2026rulescript "An Extensible and Verifiable Language for Query Rewrite Rules (2026)") §1), and the Calcite team confirmed two rule bugs that VeriEQL's counterexamples exposed ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.3).
- **One rule, many systems.** Calcite's authors name Hive, Flink and others that adopted it as their optimizer ([Apache Calcite](#/papers/begoli2018calcite "Apache Calcite: A Foundational Framework for Optimized Query Processing Over Heterogeneous Data Sources (2018)") §1). LearnedRewrite applies Calcite's rules ([LearnedRewrite](#/papers/zhou2021learnedrewrite "A learned query rewrite system using Monte Carlo tree search (2021)") §6.1), and ARG lists the same `ON FALSE` and `CAST` bugs under both (Tab. II). LLM-R2 calls its rewrites' equivalence "guaranteed" because the rules come from existing rule platforms ([LLM-R2](#/papers/li2024llmr2 "LLM-R2: A Large Language Model Enhanced Rule-Based Rewrite System for Boosting Query Efficiency (2024)") §1), so its guarantee is only as good as those rules.
- **A belief that grows as it is retold.** LLM-rewriter papers describe rule-based rewriting as "verified for correctness" ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §4.3) or as giving "formal correctness guarantees" ([LITHE](#/papers/dharwada2025lithe "LITHE: A Query Rewrite Advisor using LLMs (2026)") App. A.2). Others say the opposite: QUITE's authors report that rule-based methods "suffer from incomplete semantic equivalence", their rules lacking formal verification ([QUITE](#/papers/song2025quite "QUITE: A Query Rewrite System Beyond Rules with LLM Agents (2025)") §7.2), and SlabCity's authors say most rules in rule-based rewriters "are not fully verified" and that their checker proved some of LearnedRewrite's Calcite-rule rewrites incorrect ([SlabCity](#/papers/dong2023slabcity "SlabCity: Whole-Query Optimization Using Program Synthesis (2023)") §5.5).
- **Labels built on rules.** Calcite's rule tests serve as an equivalent-only benchmark, and VeriEQL found non-equivalent pairs among them ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.2–6.3). A faulty rule becomes wrong labels in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and [Sourcing realistic, hard query pairs](#/challenges/query_pair_sourcing), and a wrong entry in the library [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) grows.
- **Refuted once, fixed for every query.** The argument for checking rules rather than queries is old: Starburst split rewriting into small rules "such that each rule can be shown to be correct separately", citing Ganski and Wong's corrections of earlier transformations ([Starburst query rewrite](#/papers/pirahesh1992starburst "Extensible/Rule Based Query Rewrite Optimization in Starburst (1992)") §1.3). The RuleScript authors make it again (§1), yet their verified rules run through adapters that are trusted, not verified (§7.2), so implementations need refuting by execution too (our reasoning).

**Size of the gain:** incremental, our estimate. The quantity is the confirmed wrong-result rule bugs found per rewriter beyond what rule-guided fuzzing (ARG) and bounded checking (VeriEQL) already find. The reason: refuting rules by execution already works, so a better refuter finds more bugs rather than making something possible, and each bug fixed protects every query its rule matches.

## Why it's hard
- The bugs sit in edge cases. ARG's semantic bugs include outer-join rewrites that swap `RIGHT JOIN` sides, `ON FALSE` predicates and `DISTINCT` handling ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") Tab. II); published rules fail on four recurring classes of them (§ What's known).
- A rule is a pattern, so a refutation needs a concrete query instance that triggers the pattern, a database that shows the difference, and a schema whose constraints let the rule fire: ARG varies schemas for that reason ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") §III-B, "Cross-Schema Rule Propagation").
- Bugs recur in related tools. ARG lists near-identical WeTune and SQLSolver bugs, one in "the ANTLR4 library integrated in WeTune" ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") Tab. II); the SQLSolver repository at the commit ARG tested contains WeTune's parser code (our reading of its file list).
- A verified rule is only as safe as its verifier, its semantics and the code that applies it ([Can SQL equivalence checkers be trusted?](#/challenges/checker_soundness), the home of that evidence): [formal semantics](#/glossary/formal-semantics) without NULLs, Ricciotti and Cheney say, "can and do prove equivalences that are false in real databases" ([A Formalization of SQL with Nulls](#/papers/ricciotti2020nulls "A Formalization of SQL with Nulls (2022)") §1). In our reasoning a prover-verified rule is a claimed theorem, so one counterexample on an instance is a certified bug in the rule *and* its verifier; the verified rule files in our clones (WeTune `wtune_data/prepared/rules.txt`, SQLSolver `sqlsolver_data/prepared/rules*.txt`) are ready targets for an LLM fuzzer checked by execution.

## Verifiable signal
Strong. One instance plus a [counterexample database](#/glossary/counterexample-database) refutes the rule, and anyone can check it by execution. The engine is part of the check: ARG traced one result mismatch to MySQL's own behaviour and re-runs mismatches on several DBMSs to tell the two apart ([ARG](#/papers/li2025arg "ARG: Testing Query Rewriters via Abstract Rule Guided Fuzzing (2025)") §VI, Fig. 8).
