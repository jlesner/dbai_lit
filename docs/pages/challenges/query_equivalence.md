# Query equivalence: prove or refute

> Decide whether two SQL queries return the same result on every database, and back the answer with a certificate.

<p class="tags"><a class="tag" href="#/tags/bounded">bounded</a><a class="tag" href="#/tags/cex">cex</a><a class="tag" href="#/tags/itp">itp</a><a class="tag" href="#/tags/judge">judge</a><a class="tag" href="#/tags/prove">prove</a><a class="tag" href="#/tags/smt">smt</a><a class="tag" href="#/tags/theory">theory</a></p>

## Challenge
Given Q1, Q2 and a schema, answer *equivalent* (with a proof), *different* (with a [counterexample database](#/glossary/counterexample-database)) or *unknown*.

The question must say what "same result" means: set, bag or [list semantics](#/glossary/list-semantics), the set of legal ordered outputs when ties exist ([Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence)), how NULLs behave, and every database or only those the schema allows ([Equivalence under schema constraints](#/challenges/schema_constrained_equivalence)).

## What's known
- **The definition decides the verdict.** Set, bag or list semantics: [EQUITAS](#/papers/zhou2019equitas "Automated verification of query equivalence using satisfiability modulo theories (2019)") §3; [QED](#/papers/wang2024qed "QED: A Powerful Query Equivalence Decider for SQL (2024)") §3.2; [Mediator](#/papers/wang2017mediator "Verifying Equivalence of Database-Driven Applications (2017)") §10; list equivalence implies bag and bag implies set ([A Foundation for Conventional…](#/papers/slivinskas2001foundation "A Foundation for Conventional and Temporal Query Optimization Addressing Duplicates and Ordering (2001)") Thm. 4.1, PDF p. 13). The set of legal ordered outputs when ties exist: [Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") §3.2. Forms that two-valued logic calls equivalent, such as NOT IN and NOT EXISTS subqueries, can differ once NULLs occur ([Formal semantics of SQL queries](#/papers/negri1991semantics "Formal semantics of SQL queries (1991)") §4.2, PDF pp. 17–19; [A Formal Semantics of SQL Queries](#/papers/guagliardo2017semantics "A formal semantics of SQL queries, its validation, and applications (2017)") Example 1, PDF p. 2). Until the definition is stated, a wrong verdict and a different definition look alike: SQLSolver and SPES called a Calcite pair equivalent whose outputs differ in column order, SPES did the same for a pair equivalent only under [set semantics](#/glossary/set-semantics), and both groups acknowledged these as errors ([Verifying SQL Queries using…](#/papers/mohamed2024cvc5sql "Verifying SQL Queries using Theories of Tables and Relations (2024)") §5).
- **Tools cover fragments or bounds.** Provers (SQLSolver, QED, Logos) cover fragments. Bounded checkers (VeriEQL) search only up to a bound, and VeriEQL's released code fills every table with exactly k rows at bound k, so empty tables and tables of different sizes are never tried. Polygon only refutes. LLM judges cover all of SQL but certify nothing (see LLM as judge).
- **Complete test families for small fragments.** Some fragments have a finite family of test databases that decides equivalence, so agreement on the whole family is a proof: the frozen body for set-semantics conjunctive queries ([Optimal Implementation of Conjunctive…](#/papers/chandra1977conjunctive "Optimal Implementation of Conjunctive Queries in Relational Data Bases (1977)") Lemma 13, proof) and one per member for their unions ([Equivalences Among Relational Expressions…](#/papers/sagiv1980union "Equivalences Among Relational Expressions with the Union and Difference Operators (1980)") Thm 3); the same after taking the "limit" under functional dependencies ([Equivalences among Relational Expressions](#/papers/aho1979equivalences "Equivalences among Relational Expressions (1979)") §4.3, Thm 6); one per ordering of the variables for comparisons over a dense order, which integer columns are not ([On conjunctive queries containing…](#/papers/klug1988inequalities "On conjunctive queries containing inequalities (1988)") Thm 1, §2); with SQL NULLs under set semantics, a family exponential only in some variables ([How Can We Shrink…](#/papers/sternbach2026shrink "How Can We Shrink the Family of Test Databases? Query Containment with Nulls and Comparisons (2026)") Thm 3.3); and per-table bounds for some conjunctive fragments over duplicate-free tables, under keys only for "key-anchorable" pairs ([Few Rows Tell Them Apart](#/papers/cohen2026fewrows "Few Rows Tell Them Apart: Equivalence of Queries Mixing Set and Bag Semantics (2026)") §1, §4). Under [bag semantics](#/glossary/bag-semantics) equivalence is easier than containment: conjunctive queries are bag-equivalent exactly when isomorphic ([Optimization of real conjunctive queries](#/papers/chaudhuri1993real "Optimization of real conjunctive queries (1993)") Thm 5.2), and inequivalent unions differ on a database with as many distinct rows as subgoals, though copy counts may be large ([Equivalence of Queries That…](#/papers/cohen2009multiplicities "Equivalence of Queries That Are Sensitive to Multiplicities (2009)") Thm 2.14), while bag containment with ≠ is undecidable ([The containment problem for…](#/papers/jayram2006inequalities "The containment problem for &lt;bi&gt;Real&lt;/bi&gt; conjunctive queries with inequalities (2006)") abstract) and without ≠ is still open ([Bag Semantics Conjunctive Query…](#/papers/marcinkowski2025smallsteps "Bag Semantics Conjunctive Query Containment. Four Small Steps Towards Undecidability. (2024)") abstract). With GROUP BY but no HAVING, the authors characterize equivalence for MAX, MIN, COUNT and SUM queries and leave COUNT DISTINCT with comparisons open ([Deciding Equivalences among Conjunctive…](#/papers/cohen2007aggregate "Deciding Equivalences among Conjunctive Aggregate Queries (2007)") §5, Tab. I, PDF pp. 20–22). All of these are conjunctive queries or unions without negation, and all but [Deciding Equivalences among Conjunctive…](#/papers/cohen2007aggregate "Deciding Equivalences among Conjunctive Aggregate Queries (2007)") (and COUNT, [Few Rows Tell Them Apart](#/papers/cohen2026fewrows "Few Rows Tell Them Apart: Equivalence of Queries Mixing Set and Bag Semantics (2026)") §2) without aggregation ([Few Rows Tell Them Apart](#/papers/cohen2026fewrows "Few Rows Tell Them Apart: Equivalence of Queries Mixing Set and Bag Semantics (2026)") §7; [How Can We Shrink…](#/papers/sternbach2026shrink "How Can We Shrink the Family of Test Databases? Query Containment with Nulls and Comparisons (2026)") §7), so they cover only the simplest SQL.

Still open (ours): [certificates](#/glossary/certificate) for pairs outside the provers' fragments and the complete-test-family fragments; in theory, bag containment of conjunctive queries without ≠ ([Bag Semantics Conjunctive Query…](#/papers/marcinkowski2025smallsteps "Bag Semantics Conjunctive Query Containment. Four Small Steps Towards Undecidability. (2024)")) and equivalence of COUNT DISTINCT queries with comparisons ([Deciding Equivalences among Conjunctive…](#/papers/cohen2007aggregate "Deciding Equivalences among Conjunctive Aggregate Queries (2007)")).

## Why it matters
This check sits under every other challenge: rewriters, translators and [text-to-SQL](#/glossary/text-to-sql) systems all produce a query that is supposed to mean the same as another one. A sound answer is what lets their users trust that query.

- **DBAs and tuning tools adopting LLM rewrites.** In the QO-Verify study, a large fraction of LLM rewrites returned different results from the original on the given database, which the authors count as incorrect ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §1, §4.2). They call checking equivalence "a major impediment that limits the practical adoption of LLM-based rewriting today" (abstract). The payoff is argued in [Verified query speedups](#/challenges/verified_query_speedup) and [Refuting faulty rewrite rules](#/challenges/faulty_rewrite_rules).
- **Text-to-SQL training data and benchmarks.** SQLDriller uses a SQL equivalence checker to get counterexample databases that tell candidate queries apart, and with them detects and fixes wrong NL-to-SQL mappings in training datasets ([SQLDriller](#/papers/yang2025sqldriller "Automated Validating and Fixing of Text-to-SQL Translation with Execution Consistency (2025)") abstract). In its checker chain only SQLSolver's "equivalent" is a proof, so a stronger checker turns more labels into certificates: [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth), [Checking text-to-SQL against intent](#/challenges/text_to_sql_verification).
- **Engine builders.** DBMS [test oracles](#/glossary/test-oracle) generate equivalent query pairs and report a bug when their results disagree ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") abstract). Argus has an LLM propose such pairs as query skeletons and keeps a pair only if a SQL equivalence prover proves it (abstract; SQLSolver, §1). Its authors note that the provers' limits omit some oracles (DBMS-specific and user-defined functions) and may cap query size (§8).
- **Checks across data models.** Graphiti reduces equivalence of a Cypher and a SQL query, modulo a user-given mapping between graph and relational data, to SQL equivalence, so a sound SQL checker gives sound verdicts for the pair ([Graphiti](#/papers/he2025graphiti "Graphiti: Bridging Graph and Relational Database Queries (2025)") §5.3, Thm. 5.9); with a bounded checker it refuted some of ChatGPT's SQL-to-Cypher translations (§6, §6.1).
- **The gains come through the sub-challenges.** Full SQL is undecidable (§ Why it's hard), so this challenge is attacked in parts, each argued in its own "Why it matters": [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps) turns *unknown* into proofs, [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence) removes false *different* verdicts caused by tie-breaks, and [Equivalence under schema constraints](#/challenges/schema_constrained_equivalence) keeps refutations to databases the schema allows.

**Size of the gain:** enabler, our estimate. The quantity it lifts is the share of query pairs from rewriting, translation and text-to-SQL that get a certificate (a proof, or a counterexample validated by execution) instead of *unknown* or an uncertified verdict, in the challenges named above, [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection) and the [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop). The reason: the problem as a whole is undecidable, so it improves only as its sub-challenges do.

## Why it's hard
- Undecidable for full SQL: it contains [first-order logic](#/glossary/first-order-logic), so Trakhtenbrot's theorem applies (reduction in [HoTTSQL](#/papers/chu2016hottsql "HoTTSQL: proving query rewrites with univalent SQL semantics (2017)") §7). No algorithm is sound, complete and terminating for all of SQL ([SQLSolver](#/papers/ding2023sqlsolver "Proving Query Equivalence Using Linear Integer Arithmetic (2023)") §5); QED and SQLSolver are complete only on stated fragments ([QED](#/papers/wang2024qed "QED: A Powerful Query Equivalence Decider for SQL (2024)") abstract; [SQLSolver](#/papers/ding2023sqlsolver "Proving Query Equivalence Using Linear Integer Arithmetic (2023)") Thm 5.2).
- Tools cover fragments or bounds, and the theory that makes a finite test family complete covers only the simplest SQL: conjunctive queries or unions without negation, mostly without aggregation (§ What's known). Example: VeriEQL searches only up to a bound, and LLM judges cover all of SQL but certify nothing.
- With order comparisons only the refutation is short. Containment of conjunctive queries with `<` is Π₂ᵖ-hard ([querying indefinite order data](#/papers/vandermeyden1992indefinite "The complexity of querying indefinite data about linearly ordered domains (1992)") Thm 3.2, with its §1 reduction), as Klug expected ("no [homomorphism](#/glossary/homomorphism-containment-mapping) property to provide short objects to guess", [On conjunctive queries containing…](#/papers/klug1988inequalities "On conjunctive queries containing inequalities (1988)") §5). In our reading, no short, quickly checked proof of *equivalent* exists for them in general, while a counterexample is one database.
- A forced binary answer leads to guessing. *Unknown* has to be an allowed answer.

## Verifiable signal
Strong in one direction: a counterexample database is checked by running both queries in a real engine. *Equivalent* has only two certificates: a proof checked by a sound prover, within that prover's fragment, or agreement on a test family that a theorem makes complete for the pair's fragment (§ What's known). "No counterexample found" outside such a fragment, and an LLM verdict, are not certificates.
