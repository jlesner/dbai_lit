# SQL features that verifiers don't cover

> Formal checkers support only a fragment of SQL. The pairs that matter most often fall outside it.

<p class="tags"><a class="tag" href="#/tags/bounded">bounded</a><a class="tag" href="#/tags/cex">cex</a><a class="tag" href="#/tags/prove">prove</a><a class="tag" href="#/tags/smt">smt</a></p>

## Challenge
Each checker supports a fragment, and realistic pairs often fall outside it. Widen what checkers cover, so that more realistic pairs get a proof or a validated counterexample instead of *unknown*.

## What's known
- **What the checkers leave out.** VeriEQL names correlated subqueries, [window functions](#/glossary/window-function) and `LIMIT` as unsupported, and treats strings and dates as integers ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") App. C, §6, §3). SpotIt adds string and date encodings but still lacks window functions and recursive CTEs ([SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)") App. C). Provers treat most engine-specific and user-defined functions as uninterpreted, the Argus authors say; Argus proves query skeletons and fills their blanks with such features afterwards ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") §8). The Mediator authors wrote in 2017 that query provers don't reason about updates ([Mediator](#/papers/wang2017mediator "Verifying Equivalence of Database-Driven Applications (2017)") §9).
- **On realistic pairs the supported share can be small:** student assignment pairs ([Can the Rookies Cut…](#/papers/singh2024sqlequiquest "Can the Rookies Cut the Tough Cookie? Exploring the Use of LLMs for SQL Equivalence Checking (2024)") Tab. 4), workload rewrites ([SQL-RewriteBench](#/papers/long2026sqlrewritebench "SQL-RewriteBench: A Correctness-Gated, Full-Denominator Benchmark for Statement-Level SQL Rewriting (2026)") §7.4), LLM rewrites of real enterprise queries, none of which QED could verify ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §5); LLM rewrites of TPC-DS queries and of ReSequel's eight benchmark and real workloads, where SQLSolver proves a minority ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §6, whose authors call checking "a common challenge for all LLM-based approaches" and report most of their simpler JOB rewrites proved; [ReSequel](#/papers/fathollahzadeh2026resequel "ReSequel: Robust LLM-assisted Query Rewriting and Optimization using Templatization and Sampling (2026)") §7.2, Tab. 4); and LLM [text-to-SQL](#/glossary/text-to-sql) predictions on BIRD and Spider, where `ORDER BY`, nested subqueries and `CAST` defeat the provers ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §5.2.1).

Still open (ours): a check that covers the features these tools leave out, matches each engine's behaviour, and proves or refutes most realistic pairs; some gaps, such as `COUNT(DISTINCT)` with comparisons, are open theory (§ Why it's hard).

## Why it matters
- **Deploying LLM rewrites.** The QO-Verify authors call checking that a rewrite is equivalent "a major impediment that limits the practical adoption of LLM-based rewriting today" ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") abstract). Their own optimizer-based check proves only rewrites that the optimizer's existing rules can reach (§1). Rewrites beyond those rules need a prover, and on their real-world queries QED proved none (§5), the one such test on this site; the paper doesn't say whether QED failed at parsing or at proof. Wider coverage would turn those *unknown* answers into proofs, which is what DBAs and tuning tools need before they apply a rewrite.
- **Shipping systems hit the same wall.** Microsoft's SQL Server demo loops LLM rewrites through an optimizer-based prover and skips the rewrites it can't prove ([Verified LLM-Based Query Rewriting…](#/papers/lee2026mssqlrewrite "Verified LLM-Based Query Rewriting for Microsoft SQL Server (2026)") §3.1, Alg. 1, PDF p. 3), which were most of the candidates in its worked example (§2.1, PDF p. 2). A vendor ships certified LLM rewriting, and *unknown* still discards most candidates (our reading).
- **Other challenges depend on it.** *Equivalent* needs a proof, or a test family that a theorem makes complete for the pair's fragment, and those fragments are small ([Query equivalence: prove or refute](#/challenges/query_equivalence) § Verifiable signal), so coverage limits how many "equivalent" labels [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) can certify, how many rules [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) can admit (RuleScript left out Calcite rules with `Sort` and `Window`, which need [list semantics](#/glossary/list-semantics), or `Sample`, which needs probabilistic semantics, as QED lacks both; its authors know no solver that handles them, [RuleScript](#/papers/pan2026rulescript "An Extensible and Verifiable Language for Query Rewrite Rules (2026)") §7.1), and how many pairs the [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop) can score without an LLM judge. RL rewards fall back the same way: E3-Rewrite's reward hands QED's *unknown* verdicts ("timeout or unsupported constructs") to an LLM judge ([E3-Rewrite](#/papers/xu2025e3rewrite "E3-Rewrite: Learning to Rewrite SQL for Executability, Equivalence, and Efficiency (2025)") § "[Reinforcement Learning](#/glossary/reinforcement-learning) for SQL Rewriting").
- **The method carries over.** Moving a problem into a checker's fragment without changing its meaning, then validating the result on the original, works for any verifier with a limited fragment, not only SQL (Rewriting into a verifier's fragment). Graphiti carries Cypher-to-SQL equivalence into SQL checkers through a transpilation it calls correct by construction, and inherits their fragments: its prover backend supports "a limited subset of SQL without aggregations or [outer joins](#/glossary/outer-join)" ([Graphiti](#/papers/he2025graphiti "Graphiti: Bridging Graph and Relational Database Queries (2025)") §2, §6.2).

**Size of the gain:** step change, our estimate. It is measured as the share of realistic query pairs (real workloads, LLM rewrites) that get a proof or a validated counterexample instead of *unknown*. The reason: moving most of them into a checked fragment changes what can be deployed, not just how fast it is checked, though undecidability ([Query equivalence: prove or refute](#/challenges/query_equivalence)) puts full coverage out of reach.

## Why it's hard
- Each feature needs a [formal semantics](#/glossary/formal-semantics), and it must match each engine's behaviour; vendors differ, so "no single semantics will account for all" of them ([A Formal Semantics of SQL Queries](#/papers/guagliardo2017semantics "A formal semantics of SQL queries, its validation, and applications (2017)") §1). Guagliardo and Libkin validated theirs against PostgreSQL and Oracle on random queries (§4), Benzaken and Contejean on a hand-picked query set over a small database ([A Coq mechanised formal…](#/papers/benzaken2019coq "A Coq mechanised formal semantics for realistic SQL queries: formally reconciling SQL and bag relational algebra (2019)") §2.2.2). Logos's FormalSQL extends the latter ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") §4) and reports no such test (our reading). Engines also differ in typing and implicit casts, which, the TRAF authors say, formal SQL semantics leave out by assuming every operation gets arguments of the right types ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §1, PDF p. 3; §7, PDF p. 38).
- SMT theories don't yet give SQL's order and aggregates together: the cvc5 SQL theories leave aggregation and `ORDER BY` to future work ([Verifying SQL Queries using…](#/papers/mohamed2024cvc5sql "Verifying SQL Queries using Theories of Tables and Relations (2024)") §1, §6), and the Logos authors argue that cvc5's bag and sequence theories define neither the link between a bag and all row orders SQL admits nor SQL's aggregate behaviour ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") §5.3).
- Some gaps are open theory, not missing engineering. Equivalence of `COUNT(DISTINCT)` queries with comparisons is "an open problem" ([Deciding Equivalences among Conjunctive…](#/papers/cohen2007aggregate "Deciding Equivalences among Conjunctive Aggregate Queries (2007)") §5.1), and queries with `HAVING` are not addressed (§10). The theory that makes a bounded search complete covers only conjunctive queries and their unions, without negation and mostly without aggregation ([Query equivalence: prove or refute](#/challenges/query_equivalence) § What's known).
- Coverage depends on the checker family and on the proposer. The QO-Verify authors say optimizer rules handle nesting and aggregation that SMT solvers struggle with, but lack their general theorem proving ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §3); combining the two on its *unknown* pairs is "an open question" (§6). Its coverage varies by prompt, highest for query-hint rewrites, and the authors suggest constraining the LLM's changes to raise it (§4.3, Fig. 13). Steering the proposer into the checker's reach is an LLM attack with a sound check (our reading).
- Encoding a feature's full semantics can make formulas large: Polygon's authors say fully encoding all grouping possibilities "would cause an exponential blow-up" for group-by and aggregation ([Polygon](#/papers/zhao2025polygon "Polygon: Symbolic Reasoning for SQL using Conflict-Driven Under-Approximation Search (2025)") §1, an assertion, not a measurement), and the VeriEQL authors guess ("hypothetically") that it reaches only low bounds on the Literature pairs because many combine operators such as `DISTINCT` and `GROUP BY` ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.4).
- Parsers of SQL tools fail on dialect-specific syntax ([SQLFlex](#/papers/an2026parsing "Dialect-Agnostic SQL Parsing via LLM-Based Segmentation (2026)") §2), and the SQLFlex authors say SQL solvers "also face challenges in multi-dialect support" (§8).

## Verifiable signal
Execution still works for refutation: a counterexample found in the supported fragment is re-checked against the *original* queries in a real engine. The refute side needs no semantics for a feature, only data that triggers it: the ParSEval authors credit test generation's wider support to not having "to model the semantics of these operations" ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §5.2.1). Beyond SQL, ProbeGen's LLM, with execution feedback, writes inputs that disprove the equivalence of Python programs, needing only code "executable and deterministic on the explicit inputs provided" ([Disproving Program Equivalence with LLMs](#/papers/allamanis2025disproving "Disproving Program Equivalence with LLMs (2025)") §3); a failed search proves nothing (§1), and an LLM filter decides which differences matter (§3.1).
