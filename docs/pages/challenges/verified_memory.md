# Checking a memory across problems before it is reused

> Check each lesson, skill or harness edit carried from one problem to the next with a sound check before it is reused, and name what an edit breaks before it is kept.

<p class="tags"><a class="tag" href="#/tags/harness">harness</a><a class="tag" href="#/tags/promptopt">promptopt</a></p>

**Source:** added. The method is Memory across problems.

## Challenge
A memory across problems puts what an LLM concluded earlier back into its prompt: lessons, playbooks, skills, harness edits. The challenge is to check each entry with a sound check before it is reused, and to name what an edit breaks before it is kept. Entries that are claims about programs (two query forms differ, a rewrite is equivalent) can be decided by a counterexample or a proof; strategy entries need another test. The aim is a store whose entries carry [certificates](#/glossary/certificate), measured against unchecked memory on certified verdicts (ours).

## What's known
The listed systems guard their stores in several ways (listed with sources in Memory across problems), but outside formal proof libraries none checks an *entry* with a sound check before reuse (our reading). The exception: LEGO-Prover's library holds only lemmas "verified by the Isabelle prover" ([LEGO-Prover](#/papers/wang2023legoprover "LEGO-Prover: Neural Theorem Proving with Growing Libraries (2024)") §4.3.2; abstract). Two gaps follow:
- **A wrong entry gets in and stays.** ACE's authors say that without reliable feedback "the constructed context can be polluted by spurious or misleading signals" ([ACE](#/papers/zhang2025ace "Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models (2026)") §4.4), and its released code only ever adds entries. Dynamic Cheatsheet's authors report that smaller models leave "the memory populated with flawed or incomplete strategies" ([Dynamic Cheatsheet](#/papers/suzgun2025cheatsheet "Dynamic Cheatsheet: Test-Time Learning with Adaptive Memory (2025)") §1). Combee's authors leave open "whether accumulated information becomes redundant or contradictory" ([Combee](#/papers/li2026combee "Combee: Scaling Parallel Prompt Learning for Self-Improving LLM Agents (2026)") App. B).
- **An edit's damage is invisible until it shows.** AHE's agent "cannot reliably name the tasks the same edit is about to break" ([Agentic Harness Engineering (AHE)](#/papers/lin2026ahe "Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses (2026)") §4.4.2). GEPA's prompt held per-task lessons (task IDs, literal error strings) and fell below baseline once new tasks were added ([Gains made against a checker, carried beyond it](#/challenges/transfer_beyond_the_checker) § Why it's hard), which the authors read as [overfitting](#/glossary/overfitting); their RELAI-VCL rejects any candidate that gains "by sacrificing previously working behavior" ([Do Agent Optimizers Compound?](#/papers/wang2026compound "Do Agent Optimizers Compound? A Continual-Learning Evaluation on Terminal-Bench 2.0 (2026)") App. B.2, §6.2, §4.4), an outcome gate, not a sound check (our reading). Under a strict gate that checks each edit on its own task family's private tests (and bounds its loss on earlier families, §4), the edit kept and given to every task lowered the held-back score in most streams, while storing each edit for its own family only raised the mean on re-scoring, with no harmful edit ([Scope Before You Persist](#/papers/cheng2026scope "Scope Before You Persist: Preventing Cross-Family Interference in Agent Memory (2026)") §6, Tab. 4).

In SQL, stores exist but check less than SQL allows: GenRewrite keeps a natural-language rule when the rewrite it came from passes a prover or, on *unknown*, a tester ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §4.1, §4.4), so the rule itself is never checked (our reading); E3-Rewrite adds pairs that "yield equivalent" to its demonstration pool by a check the paper doesn't name for inference ([E3-Rewrite](#/papers/xu2025e3rewrite "E3-Rewrite: Learning to Rewrite SQL for Executability, Equivalence, and Efficiency (2025)")); Crystallization stores a corrected query when its result matches the [gold query](#/glossary/gold-query)'s, while the card text written from it goes unchecked ([Measuring Crystallization in Text-to-SQL](#/papers/wang2026crystallization "From Test-Time Scaling to Reusable Memory: Measuring Crystallization in Text-to-SQL (2026)") §3.2, §3.5); ReSequel caches a rewritten template once it matches the original's results on sampled data with one query's constants, and reuses it for the template's later queries, picking the first of them or the original to finish ([ReSequel](#/papers/fathollahzadeh2026resequel "ReSequel: Robust LLM-assisted Query Rewriting and Optimization using Templatization and Sampling (2026)") §6.1, §6.3): one instance's check reused for others (our reading).

## Why it matters
- **Two sets of authors name it as their next step.** AHE's: "Closing this gap is the clearest direction for future self-evolution loops" ([Agentic Harness Engineering (AHE)](#/papers/lin2026ahe "Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses (2026)") §4.4.2). Dynamic Cheatsheet's: stored strategies need "careful memory refinement and verification of solution strategies" ([Dynamic Cheatsheet](#/papers/suzgun2025cheatsheet "Dynamic Cheatsheet: Test-Time Learning with Adaptive Memory (2025)") App. B.2). SkillOpt's authors say their loop fits best where tasks have "automatic verifiers, exact-match metrics, executable checks" ([SkillOpt](#/papers/yang2026skillopt "SkillOpt: Executive Strategy for Self-Evolving Agent Skills (2026)") App. B).
- **The loop accumulates state.** The [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop) improves over rounds, and an unchecked lesson compounds: "faulty heuristics that slip into memory can be equally amplified" ([Dynamic Cheatsheet](#/papers/suzgun2025cheatsheet "Dynamic Cheatsheet: Test-Time Learning with Adaptive Memory (2025)") §5). A gate on entries could also let memory help a compact model, whose own lessons Dynamic Cheatsheet found flawed ([Bringing compact models to frontier accuracy](#/challenges/compact_model_accuracy); our reasoning). The amplification has a proof and a SQL measurement: when an agent grades its own memories and the grade overrates wrong ones, the wrong ones gain influence on later answers ([Memory Reward Inflation in…](#/papers/asadolahi2026memoryinflation "Memory Reward Inflation in Self-Improving LLM Agents (2026)") Thm. 1), and on BIRD, over two runs, demoting episodes flagged by cheap checks of the SQL and how it runs beat the self-graded memory agent (Tab. 5).
- [Measuring Crystallization in Text-to-SQL](#/papers/wang2026crystallization "From Test-Time Scaling to Reusable Memory: Measuring Crystallization in Text-to-SQL (2026)") measures it on BIRD but gates with the gold result, which its authors say a deployment must replace by "an independently reliable verification channel"; its ungated self-vote bank fell below no memory (App. C, §5.3). What a deployable sound check buys is unmeasured (our reading).

**Size of the gain:** enabler. The quantity it lifts is the certified-verdict rate after many memory updates in the challenges it unblocks ([The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop), [Bringing compact models to frontier accuracy](#/challenges/compact_model_accuracy)), against the same system with no memory and with unchecked memory. Our estimate is that checked entries make memory usable in the loop and for compact models.

## Why it's hard
- **Most lessons are not claims about queries.** "Check NULL handling first" is a strategy: only its effect on held-out pairs tests it, an A/B comparison inside run-to-run noise unless large and paired (our reasoning).
- **A lesson generalizes past its evidence.** One counterexample shows that two particular queries differ; a lesson says a pattern always does or never does. Checking the general form is checking a rewrite rule, with the provers' limits ([Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) § Why it's hard).
- **Verified outcomes are not verified lessons.** In DIVE's comparison, retrieving summaries of verifier-labelled trajectories (Experience RAG) left the average at or below zero-shot on all three models, while ExpeL's rules drawn from the same kind of labels sat above it ([DIVE](#/papers/xiong2026dive "DIVE: Unlocking Self-Improvement in Frozen Language Models Through Diversity-Driven Skill Evolution (2026)") Tab. 1, our reading; baselines run by a competing method's authors). Traj-Bootstrap stores only trajectories the environment marks successful (on InterCode-SQL, a result match against a reference), yet its authors find that "some trajectories marked as successful lead to failures when retrieved" ([Self-Generated In-Context Examples Improve…](#/papers/sarukkai2025selfgenerated "Self-Generated In-Context Examples Improve LLM Agents for Sequential Decision-Making Tasks (2025)") §5.1, App. H.2, §5.3). Memory Transfer Learning writes lessons from failed runs too, an LLM judge's success label choosing only the writing prompt, and traces some [negative transfer](#/glossary/negative-transfer) to memories of verification routines that "create a false sense of certainty" ([Memory Transfer Learning (MTL](#/papers/kim2026memorytransfer "Memory Transfer Learning: How Memories are Transferred Across Domains in Coding Agents (2026)") §3.1.1, §4.4.1). Skill Issue's authors warn that an optimized SKILL can state "claims that are stale or over-general" and that their paired score "does not certify that the document is accurate" ([Skill Issue](#/papers/kozyrev2026skillissue "Skill Issue: Lessons from Optimizing Repository SKILLs for Coding Agents (2026)") § Responsible use statement). MEMCoder stores code that passed the tests, but its LLM-written usage guidelines enter unchecked; in the authors' audit of sampled records most were correct, which they read as "generally reliable", and they warn that "inaccurate reflections may introduce noisy guidance" ([Learning from Execution](#/papers/li2026privatelibrary "Learning from Execution: Self-Evolving Memory for Private-Library Code Generation (2026)") §IV-D, §VII-A). CwI admits a skill edit only once the repaired code recovers the gold answer on multiple failing cases ([Self-Evolving Code-with-Image Reasoning](#/papers/yang2026codewithimage "Self-Evolving Code-with-Image Reasoning (2026)") §4.2, App. D): the instances are checked, the skill's text is not (our reading). Which form of entry to keep (lesson, labelled record, certificate) is open.
- **A wrong entry must be stopped before it is stored.** Shang et al. argue that removing a bad skill afterwards leaves a worse pool than removing it with the skills written under its influence, whenever one of them inherited its flawed reasoning, so the gate must act before commit ([VaG ("When Self-Evolution Backfires")](#/papers/shang2026vag "When Self-Evolution Backfires: Pre-Commit Gating against Skill Contamination in LLM Agents (2026)") Eq. 5), though the condition they state doesn't imply their inequality; Suresh et al.'s curator probes the task's environment read-only to test a lesson before saving it ([Grounding Agent Memory](#/papers/suresh2026grounding "Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents (2026)") §3.3), the role a DSL engine can play (ours).
- **Regressions are hard to attribute.** Per-instance outcomes change between identical agent runs ([SWE-agent](#/papers/yang2024sweagent "SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering (2024)") App. B.5), so a task that flips after an edit may not be the edit's doing (our reading).
- **The checker must be sound, and the store prunable.** An unsound gate admits wrong lessons ([Can SQL equivalence checkers be trusted?](#/challenges/checker_soundness), [Weak checkers get exploited](#/challenges/weak_checker_exploitation)); even a gold-result gate on one database "can pass a semantically wrong query on a lucky database state" ([Measuring Crystallization in Text-to-SQL](#/papers/wang2026crystallization "From Test-Time Scaling to Reusable Memory: Measuring Crystallization in Text-to-SQL (2026)") App. C); in the systems cited here, removal is absent (ACE above), an outcome rule (AHE's rollback, [Agentic Harness Engineering (AHE)](#/papers/lin2026ahe "Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses (2026)") §3.3; MEMCoder's proposed pruning by use and success records, [Learning from Execution](#/papers/li2026privatelibrary "Learning from Execution: Self-Evolving Memory for Private-Library Code Generation (2026)") §VII-A) or an LLM's call (MEMO's agent, [MEMO](#/papers/xie2026memo "MEMO: Memory-Augmented Model Context Optimization for Robust Multi-Turn Multi-Agent LLM Games (2026)") §3.2; GRACE's repair prompts near each edit, [GRACE](#/papers/hsu2026grace "Scoped Verification for Reliable Long-Horizon Agentic Context Evolution under Distribution Shift (2026)") §4.2, App. G), never a sound check. Retiring entries by measured contribution needs a grader whose false-pass rate stays below a level the retirement margin sets; at or above it, the rule retires nothing at any sample size ([Ratchet](#/papers/zhang2026ratchet "Ratchet: How Reliable Must an LLM Judge Be to Retire a Skill? (2026)") §4.1). Nor can an LLM screen skills by their text: unguided, a GPT-5.4 judge picked the more useful of two skills at chance, while some extractor–target pairings scored lower with the skill than without ([From Raw Experience to Skill Consumption](#/papers/huang2026skillconsumption "From Raw Experience to Skill Consumption: A Systematic Study of Model-Generated Agent Skills (2026)") §5.2, §4.2); against a reference skill's key points, "coverage alone is an incomplete proxy for skill utility" ([SkillLearnBench](#/papers/zhong2026skilllearnbench "SkillLearnBench: Benchmarking Continual Learning Methods for Agent Skill Generation on Real-World Tasks (2026)") App. J, a case study).

## Verifiable signal
Cheap and sound for entries about query behaviour: a lesson that two query forms differ (for instance `NOT IN` over a nullable column versus `NOT EXISTS`) is confirmed on an instance by a validated [counterexample database](#/glossary/counterexample-database) (both queries run in a real engine, deterministic, no error or timeout; [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence)); a lesson that they are equivalent is refuted by one, and admitted only with a proof. For an edit to the memory or harness, rerun the stored certificates (counterexample databases and proofs of earlier pairs): each pair whose certified verdict the edited system now gets wrong names exactly what the edit broke, the regression list AHE's agent couldn't predict. Strategy entries have no cheap sound check (our reasoning throughout).
