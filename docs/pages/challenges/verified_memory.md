# Checking a memory across problems before it is reused

> Check each lesson, skill or harness edit carried from one problem to the next with a sound check before it is reused.

<p class="tags"><a class="tag" href="#/tags/harness">harness</a><a class="tag sub" href="#/tags/promptopt-context">promptopt-context</a></p>

**Source:** added. The method is Memory across problems.

## Challenge
A memory across problems puts what an LLM concluded earlier back into its prompt: lessons, playbooks, skills, harness edits. The challenge: check each entry soundly before reuse; whether an edit breaks what already worked is [Self-improvement that compounds](#/challenges/compounding_self_improvement)'s no-regression gate. Claims about programs (two query forms differ, a rewrite is equivalent) can be decided by a counterexample or a proof; strategy entries need another test. The aim: a store whose entries carry [certificates](#/glossary/certificate), measured against unchecked memory on certified verdicts (ours).

## What's known
Filed systems guard their stores in several ways (Memory across problems), but outside formal proof libraries none soundly checks an *entry* before reuse (our reading). The exception, LEGO-Prover, keeps only lemmas "verified by the Isabelle prover" ([LEGO-Prover](#/papers/wang2023legoprover "LEGO-Prover: Neural Theorem Proving with Growing Libraries (2024)") (unchecked) §4.3.2; abstract); re-running it, Berlot-Attwell et al. report "virtually zero reuse" of them ([Is This LLM Library…](#/papers/berlotattwell2025libraryfails "Is This LLM Library Learning? Evaluation Must Account For Compute and Behaviour (2026)") §3.2, Tab. 2, PDF p. 4). Two gaps follow:
- Dynamic Cheatsheet's authors report that smaller models leave "the memory populated with flawed or incomplete strategies" ([Dynamic Cheatsheet](#/papers/suzgun2025cheatsheet "Dynamic Cheatsheet: Test-Time Learning with Adaptive Memory (2025)") §1); Combee's leave open "whether accumulated information becomes redundant or contradictory" ([Combee](#/papers/li2026combee "Combee: Scaling Parallel Prompt Learning for Self-Improving LLM Agents (2026)") App. B). Re-running AWM and ReasoningBank on WebArena Shopping with two models, Hajimiri et al. find much of what their LLM judges stored as success came from trajectories the benchmark's evaluator failed (ASI's judge, too, passed episodes the agent recovered after its new function failed); a more powerful judge, they argue, given the same partial input "faces the same gap" ([Are Online Skill and…](#/papers/hajimiri2026worthtokens "Are Online Skill and Memory Modules Always Worth Their Tokens? A Budget-Constrained Study of Web Agents (2026)") App. F.1–F.4). Across three skill-learning methods and two models, noise confined to the learner's execution records or outcome–record pairings cost about as much on average as task-input noise ([When Non-Adversarial Noise Hurts Learning](#/papers/yu2026rsebench "When Non-Adversarial Noise Hurts Learning: Benchmarking Skill Self-Evolution in Agents (2026)") abstract, §1).
- **An edit's damage is invisible until it shows.** AHE's agent "cannot reliably name the tasks the same edit is about to break", a gap whose closing its authors call "the clearest direction for future self-evolution loops" ([Agentic Harness Engineering (AHE)](#/papers/lin2026ahe "Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses (2026)") §4.4.2). GEPA's prompt held per-task lessons (task IDs, literal error strings) and fell below baseline once new tasks were added, which the authors read as [overfitting](#/glossary/overfitting) ([Do Agent Optimizers Compound?](#/papers/wang2026compound "Do Agent Optimizers Compound? A Continual-Learning Evaluation on Terminal-Bench 2.0 (2026)") App. B.2, §6.2); their RELAI-VCL rejects any candidate that gains "by sacrificing previously working behavior" (§4.4), an outcome gate, not a sound check (our reading). Under a strict gate that checks each edit on its own task family's private tests (and bounds its loss on earlier families, [Scope Before You Persist](#/papers/cheng2026scope "Scope Before You Persist: Preventing Cross-Family Interference in Agent Memory (2026)") §4, though at round 0, when it accepted its edits, no earlier family existed, §6), the edit kept and given to every task lowered the held-back score in most streams, while storing each edit for its own family only raised the mean on re-scoring, with no harmful edit (§6, Tab. 4). ReplayLens's authors warn that an endpoint check "can approve a migration with unchanged accuracy even when later decisions have changed" ([ReplayLens](#/papers/xu2026replaylens "ReplayLens: Auditing Agents' Use of Outcomes (2026)") §1); in their bounded-memory tests, restoring a FIFO store from an unordered backup changed which entries it kept, a hazard they say endpoint comparison misses (§4.5). The certified gate against such regressions: [Self-improvement that compounds](#/challenges/compounding_self_improvement) § Verifiable signal.

In SQL, stores check less than SQL allows (ours): GenRewrite keeps a natural-language rule when the rewrite it came from passes a prover or, on *unknown*, a tester ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §4 Alg. 1, §4.4), so the rule itself is never checked (our reading); E3-Rewrite adds pairs that "yield equivalent" to its demonstration pool by a check the paper doesn't name for inference ([E3-Rewrite](#/papers/xu2025e3rewrite "E3-Rewrite: Learning to Rewrite SQL for Executability, Equivalence, and Efficiency (2025)") (unchecked) § "Hybrid Demonstration Retrieval"); Crystallization stores a corrected query when its result matches the [gold query](#/glossary/gold-query)'s, a match its authors say "can pass a semantically wrong query on a lucky database state", leaving the card text written from it unchecked ([Measuring Crystallization in Text-to-SQL](#/papers/wang2026crystallization "From Test-Time Scaling to Reusable Memory: Measuring Crystallization in Text-to-SQL (2026)") §3.2, §3.5, App. C); MIRA builds memory items from a repair whose result matches a confirmed correction's on the one database, which its authors say "does not prove equivalence over all database instances", each accepted by a "semantic judge" ([MIRA (Memory-Item Reuse and Adaptation)](#/papers/liu2026mira "MIRA: Evidence-Verified Repair Memory for Text-to-SQL Correction (2026)") §3.2.1–3.2.2); ReSequel caches a rewritten template once it matches the original's results on sampled data with one query's constants, and reuses it for the template's later queries, picking the first of them or the original to finish ([ReSequel](#/papers/fathollahzadeh2026resequel "ReSequel: Robust LLM-assisted Query Rewriting and Optimization using Templatization and Sampling (2026)") §6.1, §6.3): one instance's check reused for others (our reading).

## Why it matters
- **Authors call for it** (AHE's, above). Dynamic Cheatsheet's: without careful curation, erroneous heuristics may spread, "requiring careful memory refinement and verification of solution strategies" ([Dynamic Cheatsheet](#/papers/suzgun2025cheatsheet "Dynamic Cheatsheet: Test-Time Learning with Adaptive Memory (2025)") App. B.2). SkillOpt's authors say their loop is most directly applicable to tasks with "automatic verifiers, exact-match metrics, executable checks" ([SkillOpt](#/papers/yang2026skillopt "SkillOpt: Executive Strategy for Self-Evolving Agent Skills (2026)") App. B).
- **The loop accumulates state.** The [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop) improves over rounds, and an unchecked lesson compounds: "faulty heuristics that slip into memory can be equally amplified" ([Dynamic Cheatsheet](#/papers/suzgun2025cheatsheet "Dynamic Cheatsheet: Test-Time Learning with Adaptive Memory (2025)") §5). Asadolahi et al. prove that when an agent grades its own memories and the grade overrates wrong ones, the wrong ones gain influence on later answers ([Memory Reward Inflation in…](#/papers/asadolahi2026memoryinflation "Memory Reward Inflation in Self-Improving LLM Agents (2026)") Thm. 1); on BIRD they measure that, over two runs, demoting episodes flagged by cheap checks of the SQL and how it runs beat the self-graded memory agent (Tab. 5). A gate on entries could also let memory help a compact model, whose own lessons Dynamic Cheatsheet found flawed ([Bringing compact models to frontier accuracy](#/challenges/compact_model_accuracy); our reasoning).
- [Measuring Crystallization in Text-to-SQL](#/papers/wang2026crystallization "From Test-Time Scaling to Reusable Memory: Measuring Crystallization in Text-to-SQL (2026)") measures it on BIRD but gates with the gold result, which its authors say a deployment must replace by "an independently reliable verification channel"; its ungated self-vote bank fell below no memory (App. C, §5.3). What a deployable sound check buys is unmeasured (our reading).

**Size of the gain:** enabler. The quantity it lifts is the certified-verdict rate after many memory updates in the challenges it unblocks ([The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop), [Bringing compact models to frontier accuracy](#/challenges/compact_model_accuracy)), against the same system with no memory and with unchecked memory. Our estimate: checked entries make memory usable in the loop and for compact models.

## Why it's hard
- **Most lessons are not claims about queries.** "Check NULL handling first" is a strategy: only its effect on held-out pairs tests it, an A/B comparison inside run-to-run noise unless large and paired (our reasoning).
- **A lesson generalizes past its evidence.** One counterexample shows that two particular queries differ; a lesson says a pattern always or never does. Checking the general form is checking a rewrite rule, with the provers' limits ([Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) § Why it's hard). On ALFWorld with Gemini 3.1 Flash-Lite, verdicts from re-running a skill's source task, or from random tasks, "barely separate helpful from harmful skills", while tasks built around the skill's situation do better ([SkillSandbox](#/papers/kim2026skillsandbox "SkillSandbox: Skill Verification via Dynamic Scenario Synthesis (2026)") §5.1, Fig. 3).
- **Verified outcomes are not verified lessons.** In DIVE's comparison, retrieving summaries of verifier-labelled trajectories (Experience RAG) left the average at or below zero-shot on all three models, while ExpeL's rules from the same kind of labels sat above it ([DIVE](#/papers/xiong2026dive "DIVE: Unlocking Self-Improvement in Frozen Language Models Through Diversity-Driven Skill Evolution (2026)") (unchecked) Tab. 1, our reading; baselines run by a competing method's authors). Traj-Bootstrap stores only trajectories the environment marks successful (on InterCode-SQL, a result match against a reference) and retrieves segments of them at each decision step ([Self-Generated In-Context Examples Improve…](#/papers/sarukkai2025selfgenerated "Self-Generated In-Context Examples Improve LLM Agents for Sequential Decision-Making Tasks (2025)") §2.2), yet its authors find "some trajectories marked as successful lead to failures when retrieved" (§5.1, App. H.2, §5.3). Memory Transfer Learning writes lessons from failed runs too, an LLM judge's success label choosing only the writing prompt, and traces some [negative transfer](#/glossary/negative-transfer) to memories of verification routines that "create a false sense of certainty" ([Memory Transfer Learning (MTL](#/papers/kim2026memorytransfer "Memory Transfer Learning: How Memories are Transferred Across Domains in Coding Agents (2026)") §3.1.1, §4.4.1). Skill Issue's authors warn that a synthesized SKILL can state "claims that are stale or over-general" and that their paired score "does not certify that the document is accurate" ([Skill Issue](#/papers/kozyrev2026skillissue "Skill Issue: Lessons from Optimizing Repository SKILLs for Coding Agents (2026)") (unchecked) § Responsible use statement). MEMCoder ([Learning from Execution](#/papers/li2026privatelibrary "Learning from Execution: Self-Evolving Memory for Private-Library Code Generation (2026)")) stores code that passed the tests (in its experiments, the benchmark's own, §VII-A), but its LLM-written usage guidelines, reflected from failures, enter unchecked (§IV-B); in the authors' audit of sampled records most were correct, which they read as "generally reliable", and they warn that "inaccurate reflections may introduce noisy guidance" (§IV-D, §VII-A). CwI admits a skill edit only once the repaired code recovers the gold answer on multiple failing cases ([Self-Evolving Code-with-Image Reasoning](#/papers/yang2026codewithimage "Self-Evolving Code-with-Image Reasoning (2026)") §4.2, App. D): the instances are checked, the skill's text is not (our reading). Which form of entry to keep (lesson, labelled record, certificate) is open.
- Suresh et al.'s curator probes the task's environment read-only (in CLBench, its tables) to test a lesson before it creates, revises, narrows, deletes or skips it ([Grounding Agent Memory](#/papers/suresh2026grounding "Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents (2026)") §3.3), the role a DSL engine can play (ours).
- **The checker must be sound, and the store prunable.** An unsound gate admits wrong lessons ([Can SQL equivalence checkers be trusted?](#/challenges/checker_soundness), [Weak checkers get exploited](#/challenges/weak_checker_exploitation)). In the systems cited here, removal is absent (ACE above), an outcome rule (MEMCoder's proposed pruning by use and success records, [Learning from Execution](#/papers/li2026privatelibrary "Learning from Execution: Self-Evolving Memory for Private-Library Code Generation (2026)") §VII-A) or an LLM's call (AHE's agent, deciding rollbacks from an attribution report, [Agentic Harness Engineering (AHE)](#/papers/lin2026ahe "Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses (2026)") App. B.2, which Alg. 1 and App. F; GRACE's repair prompts near each edit, after an LLM checks the rules there for contradictions and redundancy, [GRACE](#/papers/hsu2026grace "Scoped Verification for Reliable Long-Horizon Agentic Context Evolution under Distribution Shift (2026)") §4.2, App. G), never a sound check. Retiring entries by measured contribution needs a grader whose false-pass rate stays below a level the retirement margin sets; at or above it, the rule retires nothing at any sample size ([Ratchet](#/papers/zhang2026ratchet "Ratchet: How Reliable Must an LLM Judge Be to Retire a Skill? (2026)") §4.1). Zhou et al. ([Many Steps into One](#/papers/zhou2026contraction "Many Steps into One: Reasoning Contraction and the Limits of Safe Memory Reuse for LLM Agents (2026)")) prove, in their model, that vote counters as they idealize ExpeL's and ACE's (one vote per verified use, ACE's flag taken as retirement) are badly tuned change detectors (outcomes i.i.d. before and after one change, §3), an unclipped one possibly never retiring a partly stale entry (Rem. 2); on KQA-Stream such counters left many stale memories in service, while a likelihood-ratio [CUSUM](#/glossary/cusum-cumulative-sum-change-detection) on an exact verifier's audits retired them far sooner (§2–3, §6, Fig. 2), and their certificate restarts trust at each notice that the facts changed (§5): a statistical outcome rule, not a sound check (our reading). Nor can an LLM screen skills by their text: unguided, a GPT-5.4 judge picked the more useful of two skills no better than chance, while some extractor–target pairings scored lower with the skill than without ([From Raw Experience to Skill Consumption](#/papers/huang2026skillconsumption "From Raw Experience to Skill Consumption: A Systematic Study of Model-Generated Agent Skills (2026)") §5.2, §4.2); against a reference skill's key points, "coverage alone is an incomplete proxy for skill utility" ([SkillLearnBench](#/papers/zhong2026skilllearnbench "SkillLearnBench: Benchmarking Continual Learning Methods for Agent Skill Generation on Real-World Tasks (2026)") App. J, a case study).

## Verifiable signal
Cheap and sound for entries about query behaviour (our reasoning throughout): a lesson that two query forms differ (say, `NOT IN` over a nullable column versus `NOT EXISTS`) is confirmed on an instance by a validated [counterexample database](#/glossary/counterexample-database) (both queries run in a real engine, deterministic, no error or timeout; [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence)); a lesson that they are equivalent is refuted by one, and admitted only with a proof. Strategy entries have no cheap sound check. What a memory or harness edit breaks is the no-regression gate's to name, by rerunning stored certificates: [Self-improvement that compounds](#/challenges/compounding_self_improvement) § Verifiable signal.
**Named attack (ours):** a SQL memory whose entries are counterexample databases and proofs, against unchecked memory, on a long stream; it measures the certified-verdict rate after N updates.
