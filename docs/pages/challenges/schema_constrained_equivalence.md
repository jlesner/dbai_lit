# Equivalence under schema constraints

> Queries that look different can be equivalent because of keys, foreign keys, NOT NULL or CHECK constraints, and a checker has to know about them.

<p class="tags"><a class="tag" href="#/tags/cex">cex</a><a class="tag" href="#/tags/prove">prove</a><a class="tag" href="#/tags/smt">smt</a></p>

## Challenge
Decide equivalence relative to the databases the schema actually allows, not relative to all databases. A counterexample that violates a constraint is not a valid refutation.

## What's known
- **Checkers support constraints unevenly.** Declared keys, foreign keys and NOT NULL are encoded by VeriEQL ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §4.3; [integrity constraints](#/glossary/integrity-constraint) such as keys and `NOT NULL`, §1) and modelled by QED ([QED](#/papers/wang2024qed "QED: A Powerful Query Equivalence Decider for SQL (2024)") §3.3). Logos's equivalence ranges over databases satisfying keys, foreign keys, NOT NULL, CHECK and unique indexes ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") Fig. 2, Def. 7); its WeTune running example needs a unique key (§2). WeTune's rules carry constraints such as `Unique` and `NotNull` ([WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)") §4.2). SPES encodes keys only as two normalization rules, a self-join on a primary key and grouping on a primary key ([SPES](#/papers/zhou2020spes "SPES: A Symbolic Approach to Proving Query Equivalence Under Bag Semantics (2022)") §4.2, §7.4), so none covers joins of different tables ([QED](#/papers/wang2024qed "QED: A Powerful Query Equivalence Decider for SQL (2024)") §1), and the QED authors report that none applies to an aggregate push-down from Calcite's tests that needs a key (§2). Other checkers' constraint models are thin, hidden or stronger than SQL's: EQUITAS supports none ([EQUITAS](#/papers/zhou2019equitas "Automated verification of query equivalence using satisfiability modulo theories (2019)") §6.4); SPES's released code hard-codes keys for the benchmark's `EMP` and `DEPT` tables; WeTune's Unique forbids repeated NULLs, which a SQL `UNIQUE` column allows, yet its released rewriter takes any `UNIQUE` column as Unique and doesn't check NotNull; QueryBooster calls its self-join removal safe on any UNIQUE column, NULLs included ([QueryBooster](#/papers/bai2023querybooster "QueryBooster: Improving SQL Performance Using Middleware Services for Human-Centered Query Rewriting (2023)") §4.2).
- **Complete tests and synthesis modulo constraints.** Functional dependencies alone keep a complete test: take each query's "limit" under them, then compare ([Equivalences among Relational Expressions](#/papers/aho1979equivalences "Equivalences among Relational Expressions (1979)") §4.3, Thm 6). SlabCity seeks queries equivalent on databases meeting the constraint ([SlabCity](#/papers/dong2023slabcity "SlabCity: Whole-Query Optimization Using Program Synthesis (2023)") Def. 3.1, PDF p. 4), arguing rule-based rewriters exploit constraints largely through local changes (PDF p. 3).
- **Mined constraints.** SpotIt+ mines constraints from the test database and has an LLM keep, drop or widen each one ([SpotIt+](#/papers/tremante2026spotitplus "SpotIt+: Verification-based Text-to-SQL Evaluation with Database Constraints (2026)") §IV-B), so its check is only as sound as the constraints the LLM accepts.

Still open (ours): passing declared constraints to the pipelines that drop them; proofs of constraint-dependent rewrites across tables in checkers whose key rules don't cover them (SPES); and inducing implicit constraints from data and schema descriptions, with each mined constraint checked against that data.

## Why it matters
- **Refutations that hold on legal databases.** A checker that ignores constraints refutes equivalent queries with databases the schema forbids. The VeriEQL authors measured this: with integrity constraints dropped, most of the refutations VeriEQL reported on LeetCode came from databases that violate them ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §6.3; App. C.1). Those constraints were written by hand for each LeetCode problem (§6.1). Such refutations become wrong labels and rewards. ReViSQL cuts the RL reward when VeriEQL refutes a query ([ReViSQL](#/papers/zhu2026revisql "Human-Level Text-to-SQL via Reinforcement Learning on Verified Data, Without Pipeline Engineering (2026)") §4.2, App. D; [Weak checkers get exploited](#/challenges/weak_checker_exploitation) § What's known), and its code gives VeriEQL column types only, with no keys or NOT NULL (project `ReViSQL` @ 9fac371, `verieql_helper.py`; our reading).
- **Proofs for rewrites that need a key.** Some real rewrites hold only under constraints; how many depends on the source. About a third of WeTune's useful rules carry a Unique, NotNull or RefAttrs condition ([WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)") Tab. 7, our count), and its GitLab examples are on primary-key columns (Tab. 1). One of the rules the QO-Verify authors distill from LLM rewrites is stated over a primary-key–foreign-key join ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §3.3, Fig. 5). SPES's key rules cover none that joins different tables (§ What's known). On the other side, among the minority of Calcite test pairs UDP can process, few need a constraint ([UDP](#/papers/chu2018udp "Axiomatic foundations and algorithms for deciding semantic equivalences of SQL queries (2018)") §6.2).
- **Implicit constraints.** The SpotIt+ authors hypothesize that most mined constraints make counterexamples more realistic rather than remove them ([SpotIt+](#/papers/tremante2026spotitplus "SpotIt+: Verification-based Text-to-SQL Evaluation with Database Constraints (2026)") §V-A).
- **Other challenges inherit it.** "Different" labels in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth), refutations in [Refuting faulty rewrite rules](#/challenges/faulty_rewrite_rules) and proofs in [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) are only as right as the constraints the checker was given.

**Size of the gain:** incremental, our estimate. It is measured as the share of refutations that hold on databases the schema allows, plus the share of constraint-dependent rewrites that get a proof. The reason: declared keys, foreign keys and NOT NULL are already encoded by VeriEQL and modelled by QED (§ What's known), so most of the gain is in passing them to pipelines that drop them.

## Why it's hard
- Constraints must become axioms or rewrite rules: HoTTSQL defines k as a key when the table equals its self-join on k, and functional dependencies through keys ([HoTTSQL](#/papers/chu2016hottsql "HoTTSQL: proving query rewrites with univalent SQL semantics (2017)") §4.2); its [index](#/glossary/index-database) rule assumes a primary key (§5.1.4). Chase-like rewriting may not terminate ([UDP](#/papers/chu2018udp "Axiomatic foundations and algorithms for deciding semantic equivalences of SQL queries (2018)") §5, citing Fagin et al. 2003), and implication of functional plus inclusion dependencies is undecidable (Chandra and Vardi, *SIAM J. Comput.* 14(3), 1985, doi:10.1137/0214049; not listed).
- Shrinking a counterexample can break a foreign key: RATest's sub-instances keep keys, NOT NULL and functional dependencies, but each foreign key becomes an implication ([RATest](#/papers/miao2019ratest "Explaining Wrong Queries Using Small Examples (2019)") §2.1, §4.3).
- Keys change which semantics applies. A table with a key holds no duplicate rows, so [bag-set semantics](#/glossary/bag-set-semantics) applies ([Optimization of real conjunctive queries](#/papers/chaudhuri1993real "Optimization of real conjunctive queries (1993)") §7; [Few Rows Tell Them Apart](#/papers/cohen2026fewrows "Few Rows Tell Them Apart: Equivalence of Queries Mixing Set and Bag Semantics (2026)") §1) and a counterexample with duplicate rows is illegal. A key can make an inequivalent pair equivalent, and with keys the known complete size bounds cover only "key-anchorable" pairs ([Few Rows Tell Them Apart](#/papers/cohen2026fewrows "Few Rows Tell Them Apart: Equivalence of Queries Mixing Set and Bag Semantics (2026)") §4).
- Column types are constraints too. Two sum-queries can be equivalent over integers only because no other integers lie in the range they filter on ([Deciding Equivalences among Conjunctive…](#/papers/cohen2007aggregate "Deciding Equivalences among Conjunctive Aggregate Queries (2007)") Ex. 9.2); over rationals they differ, so a checker that models a `DECIMAL` column as an integer can certify a false *equivalent* (our reading).
- Real schemas often omit constraints the data obeys anyway (implicit keys), so "different on a legal database" can still be irrelevant in practice. The test-suite authors call inducing such constraints from data and schema descriptions "on its own an open research problem" ([Semantic Evaluation for Text-to-SQL…](#/papers/zhong2020testsuite "Semantic Evaluation for Text-to-SQL with Distilled Test Suites (2020)") §8).
- Tools support constraints unevenly, and some constraint models are thin, hidden or stronger than SQL's (§ What's known): EQUITAS supports none ([EQUITAS](#/papers/zhou2019equitas "Automated verification of query equivalence using satisfiability modulo theories (2019)") §6.4), and SpotIt+'s check is only as sound as the mined constraints its LLM accepts ([SpotIt+](#/papers/tremante2026spotitplus "SpotIt+: Verification-based Text-to-SQL Evaluation with Database Constraints (2026)") §IV-B).

## Verifiable signal
A [counterexample database](#/glossary/counterexample-database) is checked by loading it into an engine *with the constraints and column types declared*. The engine then rejects illegal counterexamples.
