# Verified query speedups

> "Q2 is faster than Q1" is worth nothing unless Q2 ≡ Q1 has also been established.

<p class="tags"><a class="tag" href="#/tags/qo">qo</a><a class="tag sub" href="#/tags/rewrite-llm">rewrite-llm</a></p>

## Challenge
Rewrite a slow query into a faster one, and certify both the speedup and the equivalence.

## What's known
- **LLM rewrites speed up real queries, and a tuning tool ships verified ones.** LLM rewrites speed up real enterprise queries, not only benchmark ones ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §4.2, Fig. 7), and SQL Server's demo builds a tuning tool around verified rewrites ([Verified LLM-Based Query Rewriting…](#/papers/lee2026mssqlrewrite "Verified LLM-Based Query Rewriting for Microsoft SQL Server (2026)") abstract).
- **Where the prover can't certify, rewriters fall back.** GenRewrite's correctness gate falls back from a prover that verifies only a minority of its TPC-DS rewrites to a tester ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §4.4, §6); SlabCity flags rewrites it can't fully verify "[bounded verification](#/glossary/bounded-verification)", for manual inspection ([SlabCity](#/papers/dong2023slabcity "SlabCity: Whole-Query Optimization Using Program Synthesis (2023)") §1, PDF p. 2). LITHE's authors say rewrites that pass only statistical tests still need "the DBA to make a final call", which keeps LITHE out of fully automated use ([LITHE](#/papers/dharwada2025lithe "LITHE: A Query Rewrite Advisor using LLMs (2026)") §8.4).
- **A rewrite benchmark gates by results:** SQL-RewriteBench is gated by result consistency on its packaged data, not formal equivalence ([SQL-RewriteBench](#/papers/long2026sqlrewritebench "SQL-RewriteBench: A Correctness-Gated, Full-Denominator Benchmark for Statement-Level SQL Rewriting (2026)") §4.1, §5.1).
- **Rule-based, trained and search-based rewriters** (LLM-R2, R-Bot; SPA, E3-Rewrite, LASER; LearnedRewrite) are listed with their checks under § Techniques.

Still open (ours): rewrites whose equivalence and speedup are both certified for the fast candidates that today's checkers answer *unknown*; how much of the gap between the best candidate and the best verified rewrite is wrong rewrites is not known.

## Why it matters
- **For DBAs and tuning tools.** A rewrite that changes the result is worse than none, and the QO-Verify authors name checking equivalence as what "limits the practical adoption of LLM-based rewriting today" ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") abstract).
- **Verification decides how much of the speedup survives.** For the median query, the best *verified* rewrite gains much less than the best candidate that merely matched results on the given database (§4.3, Fig. 11 against §4.2, Fig. 7); at the 90th percentile the gap is smaller. Per query the verified gain is a constant factor, usually modest at the median, with a tail of large speedups (§4.3, Fig. 11). The candidates are not proven equivalent, so part of that gap may be rewrites that are wrong.
- **A source of new rules.** Fast rewrites the optimizer can't verify point to rules it lacks; that case is made in [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery).

**Size of the gain:** incremental, our estimate. The quantity: the latency of queries whose rewrite is certified, against the original. The reason: per query the gain is a constant factor (above), and the step change, in what can be deployed, comes from [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps), not from better rewriting.

## Why it's hard
- LLM rewriters often change meaning: in QO-Verify's SQL Server study, a large share of LLM rewrites returned different results on the given database, over real enterprise and benchmark queries together ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §4.2).
- [Certificates](#/glossary/certificate) cover only part of the rewrites: QO-Verify verifies a minority of the candidate rewrites, answering *unknown* for the rest (§4.3), and QED verified none of the LLM rewrites of the real-world queries (§5). Freedom costs checkability: the unconstrained General prompt is one of the two whose rewrites most often speed queries up (§4.2, Fig. 8b), yet its rewrites differ most from the original, while hint-only rewrites have the highest coverage (§4.3, Fig. 13). Other rewriters' fallbacks: § What's known.
- Latency is noisy: caching, plan variance, data size. Papers average repeated runs ([LearnedRewrite](#/papers/zhou2021learnedrewrite "A learned query rewrite system using Monte Carlo tree search (2021)") §6.1, [LLM-R2](#/papers/li2024llmr2 "LLM-R2: A Large Language Model Enhanced Rule-Based Rewrite System for Boosting Query Efficiency (2024)") §6.1.6), and SPA's reward treats small latency changes as neutral ([SPA](#/papers/huang2026spa "SPA: A SQL-Plan-Aware Reinforcement Learning Framework for Query Rewriting with LLMs (2026)") §3.4). Plan cost is only an estimate: the LASER authors reward measured latency instead because cost estimates are prone to cardinality errors, citing work we haven't listed ([LASER](#/papers/li2026laser "LASER: A Data-Centric Method for Low-Cost and Efficient SQL Rewriting based on SQL-GRPO (2026)") §5.2).
- Returning the input is a safe optimum. A reward that pays for equivalence pays the identity rewrite: SPA adds an edit-distance gate against "[reward hacking](#/glossary/reward-hacking) where the model repeatedly returns near-identical SQL strings to obtain correctness rewards" ([SPA](#/papers/huang2026spa "SPA: A SQL-Plan-Aware Reinforcement Learning Framework for Query Rewriting with LLMs (2026)") §3.4), and LASER amplifies speedup rewards to favour "aggressive optimization over conservative equivalence" ([LASER](#/papers/li2026laser "LASER: A Data-Centric Method for Low-Cost and Efficient SQL Rewriting based on SQL-GRPO (2026)") §5.2).
- Minimization doesn't carry over to SQL's [bag semantics](#/glossary/bag-semantics). Chandra and Merlin use a [conjunctive query](#/glossary/conjunctive-query)'s minimal equivalent to get a program within a constant of optimal for every database, in their model ([Optimal Implementation of Conjunctive…](#/papers/chandra1977conjunctive "Optimal Implementation of Conjunctive Queries in Relational Data Bases (1977)") Thm. 16, PDF p. 9); Chaudhuri and Vardi state without proof that under bag semantics no conjunctive query can be optimized by removing conjuncts, only by reordering ([Optimization of real conjunctive queries](#/papers/chaudhuri1993real "Optimization of real conjunctive queries (1993)") §1, PDF p. 2).
- Verification must fit the tuning loop's time budget. The SQL Server tool calls QO-Verify's speed acceptable for *offline* tuning ([Verified LLM-Based Query Rewriting…](#/papers/lee2026mssqlrewrite "Verified LLM-Based Query Rewriting for Microsoft SQL Server (2026)") §3.2); slower provers may not fit.

## Verifiable signal
Two parts: an equivalence certificate (a proof, or verification through the optimizer memo, which can answer only *yes* or *unknown*) plus a measured speedup over repeated runs. A counterexample immediately disqualifies the rewrite. For a rewriter, *unknown* costs nothing: the original query is always a correct answer, so a rewrite the checker can't certify need not be shipped. ReSequel keeps the original query as a fallback, as does GenRewrite's performance gate ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §4.4), and the RL rewriters describe none at inference ([ReSequel](#/papers/fathollahzadeh2026resequel "ReSequel: Robust LLM-assisted Query Rewriting and Optimization using Templatization and Sampling (2026)"); our reading, Propose and verify).
