# Can SQL equivalence checkers be trusted?

> Provers, bounded checkers and the harnesses around them certify wrong *equivalent* verdicts, and the benchmarks they are tested on can't show it.

## Challenge
A proof is the only [certificate](#/glossary/certificate) for *equivalent* outside the fragments where a finite test family decides it (ours: [Query equivalence: prove or refute](#/challenges/query_equivalence) § Verifiable signal). But a prover's answer is only as sound as every layer under it: the implementation against its paper, the application of its rules, its [formal semantics](#/glossary/formal-semantics) against the engine, and the harness and front end that build its goals. Find the false *equivalent* verdicts in each layer, and certify each one.

## What's known
The collection holds failures at each layer:
- **Reported by others.** The cvc5 authors found false *equivalent* verdicts in SQLSolver and SPES, which their developers "acknowledged … as an error" ([Verifying SQL Queries using…](#/papers/mohamed2024cvc5sql "Verifying SQL Queries using Theories of Tables and Relations (2024)") §5); the Argus authors reported bugs, since fixed, in SQLSolver and QED, among them a wrong SQLSolver equivalence proof ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") §8); the QED authors report a SPES rule that "unsoundly rewrites" a left join on TRUE into a cross join, there making SPES miss an equivalence ([QED](#/papers/wang2024qed "QED: A Powerful Query Equivalence Decider for SQL (2024)") §6.3.1); the ParSEval authors say formal verification-based approaches "ignore projection" and called pairs differing in projected columns equivalent, results they "manually fixed" without naming the tool ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §5.3, PDF p. 11).
- EquiTrace takes optimizer rules as inputs "assumed sound", and its replay checks only that a proof's derivation is reproducible, "rule-level semantic validity" being "the separate obligation" ([EquiTrace](#/papers/chen2026equitrace "Building SQL Equivalence Proofs from Query Rewrite Rules (2026)") §1, §3.5).
- **Semantics vs engine.** A checker sound for its formal semantics is wrong where the semantics is: one that ignores NULLs can "prove [query equivalences](#/glossary/query-equivalence) that are unsound in realistic databases" ([A Formalization of SQL with Nulls](#/papers/ricciotti2020nulls "A Formalization of SQL with Nulls (2022)") abstract). The numeric domain is part of the semantics: some equivalences of aggregate queries hold over the integers but not over the rationals ([Deciding Equivalences among Conjunctive…](#/papers/cohen2007aggregate "Deciding Equivalences among Conjunctive Aggregate Queries (2007)"): [Equivalence under schema constraints](#/challenges/schema_constrained_equivalence) § Why it's hard).

Still open (ours): a method that searches each layer for false *equivalent* verdicts and certifies each by a counterexample; the failures above were found by other tools' authors and by audits of papers and releases, and the benchmarks the checkers are scored on count a false proof as a success (§ Why it matters). The nearest attack we know is outside SQL: a "hacker" agent with white-box access to an agent benchmark's verifier searches for exploits that earn reward without completing the task, and a "fixer" agent patches them ([Scalable Weak-to-Strong Verifier Hardening…](#/papers/zeng2026hardening "Scalable Weak-to-Strong Verifier Hardening for Agent Environments (2026)") §1, §3).

## Why it matters
- **Every certified label rests on it.** [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth), [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) and the [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop) turn a checker's *equivalent* into a label, an admitted rule or a reward; GaussDB's GRewriter treats a rule as correct once SQLSolver proves its representative concrete pairs equivalent ([GRewriter](#/papers/jiang2025grewriter "GRewriter: Practical Query Rewriting with Automatic Rule Set Expansion in GaussDB (2025)") §6.2, Thm. 6.1; [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery) § Verifiable signal). An unsound checker poisons all three, and search and training find its holes ([Weak checkers get exploited](#/challenges/weak_checker_exploitation)).
- **The benchmarks can't see it.** SPES's test suite "contains … semantically equivalent query pairs" ([SPES](#/papers/zhou2020spes "SPES: A Symbolic Approach to Proving Query Equivalence Under Bag Semantics (2022)") §7.2) and SQLSolver's evaluation counts "equivalent query pairs" ([SQLSolver](#/papers/ding2023sqlsolver "Proving Query Equivalence Using Linear Integer Arithmetic (2023)") PDF p. 21), so a false proof scores as a success (ours); QO-Verify asserts "It does not produce any false positives" ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §2.2) and is run only on rewrites whose results already matched (§4.2–4.3). The Argus authors say such bugs are common in prototypes "validated only on small benchmarks" ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") §8).
- **The method carries over.** Every verifier-anchored system, in code and mathematics too, trusts a checker; a way to certify the checker's mistakes is general (our reasoning). In code, stronger tests or a human audit expose wrong programs that unit tests accept ([The Limits of Inference…](#/papers/stroebl2024resampling "The Limits of Inference Scaling Through Resampling (2024)") §3; [When the Reward Suite Is Leaky](#/papers/zhang2026leaky "When the Reward Suite Is Leaky: A Preregistered Causal Contrast of Natural Verifier False Positives in RLVR (2026)") abstract), and each of CodeARC's two test-generating oracles passes programs the other refutes ([CodeARC](#/papers/wei2025codearc "CodeARC: Benchmarking Reasoning Capabilities of LLM Agents for Inductive Program Synthesis (2025)") App. A.3). An optimization-model evaluator keeps its verifier apart from the code that builds the evidence, and its authors say that this separation, exact arithmetic, hashes and fail-closed routing "reduce but cannot eliminate implementation defects" ([ModelEquivBench](#/papers/zhu2026modelequivbench "ModelEquivBench: Certifying Multi-Relational Evaluation of LLM-Generated Optimization Models (2026)") §4.2, App. L.2). Generated task suites have the same hole: an audit found scorers that accept wrong outputs, one giving full credit to any nonempty answer, in some Reasoning Gym tasks ([Reasoning Core](#/papers/sileo2026reasoningcore "Reasoning Core: Designing Broad Procedural Data for Completion-Supervised Reasoning Training (2026)") §3.4, App. G).

**Size of the gain:** enabler, our estimate. The quantity it lifts is the share of correct labels in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and of sound rules in [Discovering new rewrite rules](#/challenges/rewrite_rule_discovery), counted here as the certified soundness bugs found in the checkers that label pairs and admit rules. The reason: each bug found removes a class of false labels and of false rules, and lets the loop's reward be trusted.

## Why it's hard
- A false *equivalent* has no certificate of its own: it shows only when someone finds a database where the two queries differ, and a checker's users have no reason to look (ours).
- Each layer fails differently, so no single test covers them: semantics needs comparison with engines, implementations need pairs near their rules' edges, harnesses need adversarial proofs.

## Verifiable signal
Cheap and certain in one direction (ours): an *equivalent* verdict on a pair for which a validated [counterexample database](#/glossary/counterexample-database) exists (run both queries in a real engine; deterministic, no error or timeout, [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence)) is a certified soundness bug in the checker or in the layer that produced its goal. For a rule, one counterexample instance certifies a bug in the rule and in its verifier. For a [proof assistant](#/glossary/proof-assistant), accepted proofs of both a statement and its negation certify a harness bug.
