# Discovering new rewrite rules

> Where do new optimizer rules come from? Have an LLM propose them and a prover verify them.

<p class="tags"><a class="tag" href="#/tags/pairgen">pairgen</a><a class="tag sub" href="#/tags/rules-discover">rules-discover</a></p>

## Challenge
Grow a verified rule library beyond what humans wrote, and use the trusted rules to generate labelled equivalent query pairs.

## What's known
- **Enumeration with verification is how rules are found today.** WeTune enumerates templates of up to four operators and verifies the rules it finds ([WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)") §4.1); some rules it discovered are missing from SQL Server and Calcite (§8.2, Tab. 7). Discovered rules also run in production: GaussDB's GRewriter generates rules with a WeTune-derived enumerator, and its authors report rules that speed up two customer applications and that PostgreSQL, MySQL and SQL Server mostly lack ([GRewriter](#/papers/jiang2025grewriter "GRewriter: Practical Query Rewriting with Automatic Rule Set Expansion in GaussDB (2025)") §8.2, Tab. 5). Enumeration with pruning still yields verified rules at scale: GRewriter reports thousands, a few hundred of them useful on every setup it timed (Tab. 6, §8.3). SLER's authors find verification impractical from seven plan nodes, and rules beyond ten nodes too specific to trigger often ([SLER](#/papers/zhang2026sler "Efficient Query Rewrite Rule Discovery via Standardized Enumeration and Learning-to-Rank (2026)") §III-B, §VII).
- **Rules from LLM rewrites are proposals so far.** Four groups propose turning LLM rewrites into engine rules. The QO-Verify authors present three candidate rules that SQL Server lacks, distilled by hand from LLM rewrites it had answered *unknown* ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §1, §3); adding them to the optimizer is future work (§1). The GenRewrite authors propose aggregating verified pairs that share a natural-language rule into a guarded pattern rule ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §6, App. B), the LITHE authors propose distilling optimizer rules from its rewrites ([LITHE](#/papers/dharwada2025lithe "LITHE: A Query Rewrite Advisor using LLMs (2026)") §8.2), and the ReSequel authors list rules generated from verified LLM rewrites as future work ([ReSequel](#/papers/fathollahzadeh2026resequel "ReSequel: Robust LLM-assisted Query Rewriting and Optimization using Templatization and Sampling (2026)") §9).
- **One system already reuses LLM-derived rules, unproved.** RISE extracts dialect translation rules from LLM translations of reduced queries and applies them directly to later queries ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §3.3–§3.4). Its authors report that, once it has enough rules, it translates faster than an LLM that handles each query on its own (§4.4, Fig. 5).
- **Nearest work: outside optimizers, or without an LLM.** Argus has an LLM write pairs of equivalent query skeletons with blanks and keeps the pairs a prover proves equivalent, as [test oracles](#/glossary/test-oracle) for database engines ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") §5.2–5.3). Rules generalized from example pairs without an LLM share the generalization gap: QueryBooster's authors say an over-general suggested rule "can be erroneous in many cases" ([QueryBooster](#/papers/bai2023querybooster "QueryBooster: Improving SQL Performance Using Middleware Services for Human-Centered Query Rewriting (2023)") §5.1) and suggest existing equivalence verifiers to check rules (§3); in SqlRewriter's usage story an administrator approves a rule "Because the rule is syntactically correct and captures a nontrivial optimization", and a user then finds it returning more rows ([SqlRewriter](#/papers/bai2026sqlrewriter "SqlRewriter: Harnessing Community Knowledge to Rewrite SQL Queries (2026)") §III-B, PDF p. 3; its Fig. 6 doesn't show that flaw).

Still open (ours): rules for the template sizes between where enumeration stops and where rules stop triggering, and predicate-level rules, proposed by an LLM and proved before they are admitted; how much of a real workload such rules cover is unmeasured.

## Why it matters
- **Optimizers miss rewrites that a rule would catch.** The WeTune authors say hand-written rules "can take decades to accumulate" ([WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)") §1). In their study of performance issues in popular web applications, the rewriters of SQL Server, MySQL, PostgreSQL and Calcite each missed most of the rewrites developers made by hand (§2.2).
- **Each verified rule widens what other challenges can certify.** QO-Verify proves equivalence only through rules the optimizer already has. Its authors say that adding a distilled rule would let it prove the equivalence it had answered *unknown* ([QO-Verify](#/papers/narasayya2026qoverify "Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites for Real-World Workloads, and More! (2026)") §1, §3). So, in our reasoning, a verified rule turns *unknown* answers into proofs for [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps), lets [Verified query speedups](#/challenges/verified_query_speedup) certify more rewrites, and, applied to a workload, yields labelled equivalent pairs for [Sourcing realistic, hard query pairs](#/challenges/query_pair_sourcing) and [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth). A rule proved once can also travel: RuleScript's authors verify each rule once, for every instantiation, with QED ([RuleScript](#/papers/pan2026rulescript "An Extensible and Verifiable Language for Query Rewrite Rules (2026)") §2, §3.2) and run their rules in Calcite, CockroachDB and DataFusion, except DataFusion's set-operation rules, through per-engine adapters (§7.1; their trust: [Can SQL equivalence checkers be trusted?](#/challenges/checker_soundness) § What's known).
- Per query, a rule's speedup is no larger than that of the rewrite it captures ([Verified query speedups](#/challenges/verified_query_speedup)), and enumeration already supplies small verified rules at scale (§ What's known), so the gain lies in the larger and predicate-level rules it can't reach (our reasoning).
- **Reuse multiplies errors as well as gains.** A rule admitted wrongly corrupts every query it matches ([Refuting faulty rewrite rules](#/challenges/faulty_rewrite_rules)), as RISE's unproved rules show (§ What's known). So discovery pays only if each rule is proved before it is admitted (our reasoning).

**Size of the gain:** step change, our estimate. The quantity: the verified rules added beyond the template sizes that enumeration reaches, and the share of a workload's queries they rewrite. The reason: each rule is checked once and then rewrites every matching query at an optimizer rule's cost, which decides whether LLM-found rewrites can run on every query at all.

## Why it's hard
- The search space is huge. Enumeration plus verification scales only to small plans: WeTune enumerates templates of up to four operators ([WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)") §4.1), and SLER goes further only with pruning and a learned pre-filter, which gives up completeness ([SLER](#/papers/zhang2026sler "Efficient Query Rewrite Rule Discovery via Standardized Enumeration and Learning-to-Rank (2026)") §6).
- Enumeration over symbolic predicates misses predicate-level rewrites. Most of the developer fixes WeTune could not reproduce "need to rewrite the predicate expression or add a new predicate", which "requires finer-grained modeling and reasoning of the predicate expressions" ([WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)") §8.3). In our reasoning, that is where an LLM proposer adds to enumeration, provided the checker interprets predicates.
- Generalizing from one rewrite is itself the hard step. GenRewrite's authors say a rule distilled from one pair "overfits incidental syntax choices and misses necessary preconditions" ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)") §6), and LITHE's authors find some LLM rewrites hard to encode as generic rules at all, "given the combinatorial ways in which such transformations can occur" ([LITHE](#/papers/dharwada2025lithe "LITHE: A Query Rewrite Advisor using LLMs (2026)") §8.2). Rules generalized without an LLM share the gap (§ What's known).
- Even concrete LLM rewrites of TPC-DS queries and of ReSequel's workloads mostly fall outside what SQLSolver proves ([GenRewrite](#/papers/liu2024genrewrite "GenRewrite: Query Rewriting via Large Language Models (2026)"), [ReSequel](#/papers/fathollahzadeh2026resequel "ReSequel: Robust LLM-assisted Query Rewriting and Optimization using Templatization and Sampling (2026)"); [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps) § What's known).
- A rule that is valid can still be useless: it never fires, or never speeds anything up. GRewriter keeps only the verified rules that cut latency in all six of its test setups ([GRewriter](#/papers/jiang2025grewriter "GRewriter: Practical Query Rewriting with Automatic Rule Set Expansion in GaussDB (2025)") §6.3), and SLER trains its ranker on measured speedups, not validity ([SLER](#/papers/zhang2026sler "Efficient Query Rewrite Rule Discovery via Standardized Enumeration and Learning-to-Rank (2026)") §5.1.3).

## Verifiable signal
A proof over the rule's pattern makes the rule trusted. It often goes through a reduction that is part of the trusted base: GRewriter instantiates each rule into finitely many representative concrete pairs and checks them with SQLSolver, on the strength of a theorem whose full proof is in an external appendix ([GRewriter](#/papers/jiang2025grewriter "GRewriter: Practical Query Rewriting with Automatic Rule Set Expansion in GaussDB (2025)") §6.2, Thm 6.1). A counterexample on any instance refutes the rule, and is the practical way to say no: WeTune's verifier times out on most incorrect rules instead of refuting them, and WeTune treats a timeout as "incorrect" ([WeTune](#/papers/wang2022wetune "WeTune: Automatic Discovery and Verification of Query Rewrite Rules (2022)") §5.1.2). The prover also bounds what discovery finds (our reading): inside WeTune's discovery module, SQLSolver finds all the useful rules WeTune found plus new ones that remove unnecessary aggregates and UNIONs ([SQLSolver](#/papers/ding2023sqlsolver "Proving Query Equivalence Using Linear Integer Arithmetic (2023)") §6.3, PDF p. 23). Usefulness (does it fire, does it speed things up) is measurable but noisy.
