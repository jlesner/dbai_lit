# Telling bad translations from legitimate engine differences

> When a translated query returns different results, is the translation wrong, or does no exact translation exist?

<p class="tags"><a class="tag sub" href="#/tags/dialect-difftest">dialect-difftest</a></p>

## Challenge
Find translations that silently change meaning. Separate those from differences that come from the engines themselves, and use one engine as the reference for finding bugs and sharp edges in another.

## Why it matters
- **For migration teams: less checking by hand.** Wrong translations often run ([SQL dialect translation](#/challenges/dialect_translation)), and two migration systems on this site still end with people: Horizon returns each candidate "for human review" ([Horizon](#/papers/emani2025horizon "Horizon: Robust Checks for SQL Migration Using LLMs (2025)") §2.1), and in AgentMigrate's production deployment experts reviewed every AI-generated migration ([AgentMigrate](#/papers/yu2026agentmigrate "Bridging the Procedural Code Gap: Agentic Database Migration with Execution-Grounded Validation (2026)") §6). AgentMigrate's agent compares results under configurable tolerances (§3), and its human-reviewed tests fail a hand-verified reference translation on Oracle NUMBER vs PostgreSQL NUMERIC precision, which the author calls "an inherent cross-platform difficulty" (Tab. 2 note, §5.5); that is the author's judgment, since the reference chose `decimal(7,2)` and the paper doesn't show that another target type would also differ. Deciding such cases without a person is this challenge.
- **For benchmark makers: scores that measure translation.** CrackSQL and PARROT, from overlapping authors, count a translation as right only if its results are "strictly identical", including format, precision and displayed order ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.1; [PARROT](#/papers/zhou2025parrot "PARROT: A Benchmark for Evaluating LLMs in Cross-System SQL Translation (2025)") §4). So a benchmark that doesn't separate "bad translation" from "no exact translation" mislabels its pairs. PARROT doesn't split its gap between running and matching by cause (Tab. 3), and its curation drops any pair whose reference gives a different result, whatever the cause (§3.2, Step 4). Separating causes would keep and label such pairs ([Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth)). UniQL sends to people the cases where "automatic verification cannot safely certify equivalence under database-specific execution behavior, such as under-specified ordering, duplicate-sensitive outputs, or target-engine differences" ([UniQL](#/papers/gao2026uniql "UniQL: Towards Dialect-Universal Benchmarking for Text-to-SQL (2026)") §6.3).
- **For engine testers: comparing engines beyond common SQL.** The RAGS author found cross-vendor comparison useful "only for the small set of common SQL", with NULL, string and numeric-coercion differences "particularly problematic" ([Massive Stochastic Testing of SQL](#/papers/slutz1998rags "Massive Stochastic Testing of SQL (1998)") §6). The ACME authors say such differences cause false alarms or push testers to exclude features, e.g. NULLs ([ACME](#/papers/jiang2026acme "ACME: Automated Clause Mapping Engine for Testing Emerging Database Systems (2026)") §1); once their mappings absorb them, they report previously unknown logic bugs, some of which needed the mappings to be found (abstract, §5.2).
- **For translators that repair from feedback.** RISE treats every result difference as an unresolved dialect element to fix ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §3.1), so in our reading a legitimate difference sends its repair loop after something it cannot fix. The TRAF authors offer a typing semantics to show "where behavior cannot be preserved in the target engine" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §1).

**Size of the gain:** enabler, measured as the share of result differences between a query and its translation that are attributed, without a person, to a translation error or to a catalogued engine difference. The gain shows up in [SQL dialect translation](#/challenges/dialect_translation), [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and cross-engine [Differential testing](#/glossary/differential-testing) across engines. On its own it works on the refute side only (equal results can still hide a bad translation, below), so the step change that [SQL dialect translation](#/challenges/dialect_translation) expects from it also needs checkers that prove equivalence across engine semantics. This is our estimate.

## Verifiable signal
A result difference is checkable. Its *cause* is not, until it is explained by a catalogued engine difference or reduced to a minimal case.
