# Telling bad translations from legitimate engine differences

> When a translated query returns different results, is the translation wrong, or does no exact translation exist?

<p class="tags"><a class="tag" href="#/tags/dialect">dialect</a><a class="tag" href="#/tags/difftest">difftest</a></p>

## Challenge
Find translations that silently change meaning. Separate those from differences that come from the engines themselves, and use one engine as the reference for finding bugs and sharp edges in another.

## What's known
- **Benchmarks count every difference, or drop it.** CrackSQL and PARROT, from overlapping authors, count a translation as right only if its results are "strictly identical", including format, precision and displayed order ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") SIGMOD PDF §7.1; [PARROT](#/papers/zhou2025parrot "PARROT: A Benchmark for Evaluating LLMs in Cross-System SQL Translation (2025)") §4). PARROT doesn't split its gap between running and matching by cause (Tab. 3), and its curation drops any pair whose reference gives a different result, whatever the cause (§3.2, Step 4). DLBench drops SQL-92-compliant statements as not needing translation, after a sample of them behaved alike across its engines ([DLBench](#/papers/lin2025dlbench "DLBench: A Comprehensive Benchmark for SQL Translation with Large Language Models (2025)") §III-A).
- **Migration systems and benchmarks hand the hard cases to people.** Horizon returns its final candidate "for human review" ([Horizon](#/papers/emani2025horizon "Horizon: Robust Checks for SQL Migration Using LLMs (2025)") §2.1), and in AgentMigrate's production deployment experts reviewed every AI-generated migration ([AgentMigrate](#/papers/yu2026agentmigrate "Bridging the Procedural Code Gap: Agentic Database Migration with Execution-Grounded Validation (2026)") §6). UniQL's authors say some cases reach its human stage because "automatic verification cannot safely certify equivalence under database-specific execution behavior, such as under-specified ordering, duplicate-sensitive outputs, or target-engine differences" ([UniQL](#/papers/gao2026uniql "UniQL: Towards Dialect-Universal Benchmarking for Text-to-SQL (2026)") §6.3).
- **Nearest work: explaining differences by cause.** ACME's mappings absorb engine differences for cross-engine testing ([ACME](#/papers/jiang2026acme "ACME: Automated Clause Mapping Engine for Testing Emerging Database Systems (2026)") §1; results: § Why it matters). The TRAF authors say a type-aware formalization such as theirs can guide where "behavior cannot be preserved in the target engine" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §1). QueryHouse's authors, comparing five engines (the latest versions as of late 2024, PDF p. 10) on translated queries, count a difference that contradicts official documentation as a bug and an undocumented one as an inconsistency, decided in a triage step after the comparison ([QueryHouse](#/papers/oh2026queryhouse "QueryHouse: Cross-DBMS Differential Testing with LLM and Query Transpilation (2026)") §1, PDF p. 2; §3.1, PDF p. 5); they name their translator's own mistranslations as a source of false positives (§3.2, PDF p. 6; the SQLGlot cases: [SQL dialect translation](#/challenges/dialect_translation) § Why it matters).

Still open (ours): attributing a result difference between a query and its translation, without a person, to a translation error or to a catalogued engine difference; and equal results can still hide a bad translation (§ Why it's hard).

## Why it matters
- **For migration teams: less checking by hand.** Wrong translations often run ([SQL dialect translation](#/challenges/dialect_translation)), and two migration systems on this site still end with people (§ What's known). Deciding such cases without a person is this challenge.
- **For benchmark makers: scores that measure translation.** A benchmark that doesn't separate "bad translation" from "no exact translation" mislabels its pairs (ours; § What's known, the strict-equality benchmarks; see Why it's hard), and separating causes would keep and label them ([Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth)).
- **For engine testers: comparing engines beyond common SQL.** The RAGS author found cross-vendor comparison useful "only for the small set of common SQL", with NULL, string and numeric-coercion differences "particularly problematic" ([Massive Stochastic Testing of SQL](#/papers/slutz1998rags "Massive Stochastic Testing of SQL (1998)") §6). The ACME authors say such differences cause false alarms or push testers to exclude features, e.g. NULLs ([ACME](#/papers/jiang2026acme "ACME: Automated Clause Mapping Engine for Testing Emerging Database Systems (2026)") §1); once their mappings absorb them, they report previously unknown logic bugs in the latest versions of four emerging engines, tested against PostgreSQL 14.0 (§5.1), some of which needed the mappings to be found (abstract, §5.2).
- **For translators that repair from feedback.** RISE treats every result difference as an unresolved dialect element to fix ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §3.1), so in our reading a legitimate difference sends its repair loop after something it cannot fix.

**Size of the gain:** enabler, our estimate. The quantity it lifts, in [SQL dialect translation](#/challenges/dialect_translation), [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and cross-engine [Differential testing](#/glossary/differential-testing) across engines: the share of result differences between a query and its translation that are attributed, without a person, to a translation error or to a catalogued engine difference. The reason: today such differences go to people, are dropped or count as errors (§ What's known); on its own this works on the refute side only, so the step change [SQL dialect translation](#/challenges/dialect_translation) expects also needs checkers that prove equivalence across engine semantics.

## Why it's hard
- **Engines legitimately differ.** This list is the home for such differences; other files link here. Examples:
  - NULL sort order ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.4; tested on MySQL 8.0 and PostgreSQL 14, §7.1);
  - integer division: PostgreSQL truncates when both operands are integers, MySQL's `/` doesn't ([PostgreSQL 18 manual](https://www.postgresql.org/docs/18/functions-math.html), § 9.3 "Mathematical Functions and Operators", Table 9.4; [MySQL 8.4 Reference Manual](https://dev.mysql.com/doc/refman/8.4/en/arithmetic-functions.html), § 14.6.1 "Arithmetic Operators"; both accessed 2026-11-07); RISE's rules can't tell without the column types ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §5.2);
  - numeric precision in results ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.4; versions as above);
  - `||`, OR in MySQL but concatenation in PostgreSQL and SQLite ([SQLFlex](#/papers/an2026parsing "Dialect-Agnostic SQL Parsing via LLM-Based Segmentation (2026)") §8; no versions given; in MySQL 8.4, OR unless the `PIPES_AS_CONCAT` mode is on, and that use is deprecated: MySQL 8.4 Reference Manual § 14.4.3 Logical Operators, accessed 2026-11-07);
  - `CONCAT` with a NULL argument ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §2.2, Example 1; no versions given);
  - string collation: MySQL 8.0 defaults to the case- and accent-insensitive `utf8mb4_0900_ai_ci` (MySQL 8.0 Reference Manual, [§ 12.3.2 "Server Character Set and Collation"](https://dev.mysql.com/doc/refman/8.0/en/charset-server.html) and [§ 12.3.1 "Collation Naming Conventions"](https://dev.mysql.com/doc/refman/8.0/en/charset-collation-names.html), accessed 2026-11-07);
  - Oracle's implicit commit before DDL, which silently discards `TEMPORARY` table data: documented, yet it surfaced as a false positive that manual triage explained ([QueryHouse](#/papers/oh2026queryhouse "QueryHouse: Cross-DBMS Differential Testing with LLM and Query Transpilation (2026)") §5.1, PDF p. 12; Oracle Database 23ai, §5, PDF p. 10);
  - empty string vs NULL: Oracle "treats a character value with a length of zero as null", which its manual says "may not continue to be true in future releases" ([Oracle Database 19c SQL Language Reference](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Nulls.html), "Nulls", accessed 2026-11-07);
  - `SELECT *` over a [subquery](#/glossary/subquery-nested-query) that repeats a column: PostgreSQL accepts it, some commercial engines reject it alone but accept it under `EXISTS`, so "no single semantics will account for all the existing RDBMSs, even for the core language", though its authors call the differences "minor and well documented" ([A Formal Semantics of SQL Queries](#/papers/guagliardo2017semantics "A formal semantics of SQL queries, its validation, and applications (2017)") §1, Example 2, PDF p. 2; no versions given).
- **Standard syntax doesn't mean standard behaviour.** TRAF's Table 1 has short queries that give different results or errors on five engines, and its authors say [SQL standards](#/glossary/sql-standard) "either do not cover many typing-related issues or leave their interpretation rather open" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §1, Tab. 1).
- **Where the line falls can be the vendor's call.** The same QTRAN finding was confirmed as a bug in MariaDB 11.5.2 and not recognized as one in TiDB 8.3.0, the difference put down to implicit casting ([QTRAN](#/papers/lin2025qtran "QTRAN: Extending Metamorphic-Oracle Based Logical Bug Detection Techniques for Multiple-DBMS Dialect Support (2025)") §4.2.3, Fig. 7; versions: Tab. 3).
- **Strict result equality conflates the two.** The CrackSQL authors put most result differences among the translations that run down to "the inner difference of the underlying databases", for example numeric precision and the row order of queries without `ORDER BY` ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") SIGMOD PDF §7.4); the latter is, in our reading, [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence), not an engine difference. Normalizing formats instead (dates, number precision) is meant to isolate "the semantic correctness" of a query ([PolySQL](#/papers/perlitz2026polysql "PolySQL: Scaling Text-to-SQL Evaluation Across SQL Dialects via Automated Backend Isomorphism (2026)") §2.3, App.
- **Equal results can hide a bad translation.** In RISE, both engines returned empty results for a mistranslated `||`, and the comparison accepted it ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §5.2).

## Verifiable signal
A result difference is checkable. Its *cause* is not, until it is explained by a catalogued engine difference or reduced to a minimal case.
