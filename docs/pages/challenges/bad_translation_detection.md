# Telling bad translations from legitimate engine differences

> When a translated query returns different results, is the translation wrong, or does no exact translation exist?

<p class="tags"><a class="tag sub" href="#/tags/dialect-difftest">dialect-difftest</a></p>

## Challenge
Find translations that silently change meaning. Separate those from differences that come from the engines themselves, and use one engine as the reference for finding bugs and sharp edges in another.

## What's known
- **Benchmarks count every difference, or drop it.** CrackSQL and PARROT, from overlapping authors, count a translation as right only if its results are "strictly identical", including format, precision and displayed order ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.1; [PARROT](#/papers/zhou2025parrot "PARROT: A Benchmark for Evaluating LLMs in Cross-System SQL Translation (2025)") §4). PARROT doesn't split its gap between running and matching by cause (Tab. 3), and its curation drops any pair whose reference gives a different result, whatever the cause (§3.2, Step 4). DLBench drops SQL-92-compliant statements as not needing translation, after a sample of them behaved alike across its engines ([DLBench](#/papers/lin2025dlbench "DLBench: A Comprehensive Benchmark for SQL Translation with Large Language Models (2025)") §III-A).
- **Migration systems and benchmarks hand the hard cases to people.** Horizon returns each candidate "for human review" ([Horizon](#/papers/emani2025horizon "Horizon: Robust Checks for SQL Migration Using LLMs (2025)") §2.1), and in AgentMigrate's production deployment experts reviewed every AI-generated migration ([AgentMigrate](#/papers/yu2026agentmigrate "Bridging the Procedural Code Gap: Agentic Database Migration with Execution-Grounded Validation (2026)") §6). UniQL sends to people the cases where "automatic verification cannot safely certify equivalence under database-specific execution behavior, such as under-specified ordering, duplicate-sensitive outputs, or target-engine differences" ([UniQL](#/papers/gao2026uniql "UniQL: Towards Dialect-Universal Benchmarking for Text-to-SQL (2026)") §6.3).
- **Nearest work: explaining differences by cause.** ACME's mappings absorb engine differences for cross-engine testing ([ACME](#/papers/jiang2026acme "ACME: Automated Clause Mapping Engine for Testing Emerging Database Systems (2026)"); its results: § Why it matters, the engine-testers bullet). The TRAF authors offer a typing semantics to show "where behavior cannot be preserved in the target engine" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §1). Outside SQL, the authors of [Why Aren't Regular Expressions…](#/papers/davis2021lingua "Why Aren't Regular Expressions a Lingua Franca? An Empirical Study on the Re-use and Portability of Regular Expressions (2019)") classified regexes' cross-language differences by cause, with heuristics encoded from the engines' documentation; the causes explain most differences, though many of the behaviours are undocumented ("Testing, not reading the manual, is the only way for developers to learn these behaviors"), and a language that disagreed with the others and its own documentation led to bug reports, some confirmed (§7.1.3–7.1.4).

Still open (ours): attributing a result difference between a query and its translation, without a person, to a translation error or to a catalogued engine difference; and equal results can still hide a bad translation (§ Why it's hard).

## Why it matters
- **For migration teams: less checking by hand.** Wrong translations often run ([SQL dialect translation](#/challenges/dialect_translation)), and two migration systems on this site still end with people (§ What's known). Deciding such cases without a person is this challenge.
- **For benchmark makers: scores that measure translation.** A benchmark that doesn't separate "bad translation" from "no exact translation" mislabels its pairs (§ What's known, the strict-equality benchmarks; see Why it's hard). Separating causes would keep and label such pairs ([Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth)).
- **For engine testers: comparing engines beyond common SQL.** The RAGS author found cross-vendor comparison useful "only for the small set of common SQL", with NULL, string and numeric-coercion differences "particularly problematic" ([Massive Stochastic Testing of SQL](#/papers/slutz1998rags "Massive Stochastic Testing of SQL (1998)") §6). The ACME authors say such differences cause false alarms or push testers to exclude features, e.g. NULLs ([ACME](#/papers/jiang2026acme "ACME: Automated Clause Mapping Engine for Testing Emerging Database Systems (2026)") §1); once their mappings absorb them, they report previously unknown logic bugs, some of which needed the mappings to be found (abstract, §5.2).
- **For translators that repair from feedback.** RISE treats every result difference as an unresolved dialect element to fix ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §3.1), so in our reading a legitimate difference sends its repair loop after something it cannot fix.

**Size of the gain:** enabler, our estimate. The quantity it lifts, in [SQL dialect translation](#/challenges/dialect_translation), [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and cross-engine [Differential testing](#/glossary/differential-testing) across engines: the share of result differences between a query and its translation that are attributed, without a person, to a translation error or to a catalogued engine difference. The reason: today such differences go to people, are dropped or count as errors (§ What's known); on its own this works on the refute side only, so the step change [SQL dialect translation](#/challenges/dialect_translation) expects also needs checkers that prove equivalence across engine semantics.

## Why it's hard
- **Engines legitimately differ.** This list is the home for such differences; other files link here. Examples:
  - NULL sort order ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.4);
  - integer division: PostgreSQL truncates when both operands are integers, MySQL's `/` doesn't (PostgreSQL manual, "Mathematical Functions and Operators", Table 9.4; MySQL 8.4 Reference Manual, "Arithmetic Operators"; both accessed 2026-10-03); RISE's rules can't tell without the column types ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §5.2);
  - numeric precision in results ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.4);
  - `||`, OR in MySQL but concatenation in PostgreSQL and SQLite ([SQLFlex](#/papers/an2026parsing "Dialect-Agnostic SQL Parsing via LLM-Based Segmentation (2026)") §8);
  - `CONCAT` with a NULL argument ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §2.2, Example 1);
  - string collation: MySQL 8.0 defaults to the case- and accent-insensitive `utf8mb4_0900_ai_ci` (MySQL 8.0 Reference Manual, "Server Character Set and Collation", accessed 2026-10-01);
  - empty string vs NULL: Oracle "treats a character value with a length of zero as null" (Oracle Database 19c SQL Language Reference, "Nulls", accessed 2026-10-01);
  - `SELECT *` over a [subquery](#/glossary/subquery-nested-query) that repeats a column: PostgreSQL accepts it, some commercial engines reject it alone but accept it under `EXISTS`, so "no single semantics will account for all the existing RDBMSs, even for the core language" ([A Formal Semantics of SQL Queries](#/papers/guagliardo2017semantics "A formal semantics of SQL queries, its validation, and applications (2017)") §1, Example 2, PDF p. 2).
- **Standard syntax doesn't mean standard behaviour.** TRAF's Table 1 has short queries that give different results or errors on five engines, and its authors say [SQL standards](#/glossary/sql-standard) "either do not cover many typing-related issues or leave their interpretation rather open" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §1, Tab. 1). DLBench, by contrast, treats SQL-92-compliant statements as not needing translation (§ What's known).
- **Where the line falls can be the vendor's call.** The same QTRAN report was confirmed as a bug in MariaDB and not recognized as one by TiDB, whose developers traced the difference to implicit casting ([QTRAN](#/papers/lin2025qtran "QTRAN: Extending Metamorphic-Oracle Based Logical Bug Detection Techniques for Multiple-DBMS Dialect Support (2025)") §4.2.3, Fig. 7).
- **Strict result equality conflates the two.** CrackSQL reports that most result differences among the translations that run come from numeric precision or from comparing the row order of queries without `ORDER BY` ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") SIGMOD PDF §7.4); the latter is [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence), not an engine difference. Normalizing formats instead (dates, number precision) is meant to isolate "the semantic correctness" of a query ([PolySQL](#/papers/perlitz2026polysql "PolySQL: Scaling Text-to-SQL Evaluation Across SQL Dialects via Automated Backend Isomorphism (2026)") §2.3, App. B), but its authors say NULL ordering and mixed-type comparisons may still give false negatives (§8), and a permissive comparator can accept wrong results (our reading).
- **Equal results can hide a bad translation.** In RISE, both engines returned empty results for a mistranslated `||`, and the comparison accepted it ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §5.2).

## Verifiable signal
A result difference is checkable. Its *cause* is not, until it is explained by a catalogued engine difference or reduced to a minimal case.
