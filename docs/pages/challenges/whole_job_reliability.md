# Whole-job reliability of multi-step LLM work

> Per-step errors compound over long jobs, so a model that is good at each step still fails most long jobs. Which checks restore whole-job success, and can a small local model, checked at every step, finish long jobs as reliably as a frontier model?

<p class="tags"><a class="tag" href="#/tags/harness">harness</a><a class="tag" href="#/tags/scaling">scaling</a></p>

## Challenge
A long job succeeds only if every essential step does: a migration done object by object, a chain of rewrites, a pipeline of dependent queries, an agent's tool loop. If each step succeeds with probability p and errors are independent, a job of n steps succeeds with probability pⁿ, so a per-step reliability that looks good fails most long jobs.

## What's known
The decay as measured:
- on simulator-checked synthetic task families, the authors report that success follows a geometric law in per-step reliability ([How Fast Do Agents Rot?](#/papers/mittal2026rot "How Fast Do Agents Rot? An Empirical Study of Long-Horizon Degradation in LLM Agents for Production Decision-Making (2026)") p. 2), that most models collapse on a long tool loop (Tab. 2, PDF p. 6), that errors are absorbing (§4.6, PDF p. 8) and that step count, not context length, drives the decline (§4.5, PDF p. 8); its released analysis doesn't support the geometric-law count;
- on a benchmark built so that formula depth can't be shortcut, next-step accuracy without tools collapses with depth in small and frontier models, while code execution largely removed the collapse in frontier and small thinking models and only mitigated it in small instruct ones ([Tool Use Reduces Depth-Induced…](#/papers/koplow2026depthcollapse "Tool Use Reduces Depth-Induced Collapse in OOD Reasoning (2026)") §4.2–4.3, Fig. 4);
- context length alone lowers single-step accuracy, even with the evidence next to the question ([Context Length Alone Hurts…](#/papers/du2025contextlength "Context Length Alone Hurts LLM Performance Despite Perfect Retrieval (2025)") §4.1), so outside [How Fast Do Agents Rot?](#/papers/mittal2026rot "How Fast Do Agents Rot? An Empirical Study of Long-Horizon Degradation in LLM Agents for Production Decision-Making (2026)")'s setting length is a driver too (our reading);
- models given the plan and the knowledge still fail long simple tasks, and err more after seeing their own earlier errors ([The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)") §3.1, §3.2, Fig. 5);
- 4-bit quantization leaves an agent benchmark's final score flat while one model's tool-name errors grow, hidden by the benchmark's failure budget ([Flat Score, Amplified Failures](#/papers/jang2026flatscore "Flat Score, Amplified Failures: How the Error Budget Masks Damage in Quantized LLM Agents (2026)") Tab. 1, Tab. 2);
- on database jobs, PL/SQL conversations with every turn correct are much rarer than correct turns, which its authors read as errors that "compound across successive modifications" ([PLSQLBench](#/papers/liu2026plsqlbench "PLSQLBench: Benchmarking LLM Systems for Executable Procedural Database Programming (2026)") §4.3); agents repairing live PostgreSQL faults "often localize the root cause without completing the repair" ([DBA-Bench](#/papers/chen2026dbabench "DBA-Bench: A Production-Fidelity Benchmark for LLM-Based Database Operations Agents (2026)") §6.2); and the best ELT agent loads all sources far more often than it builds correct target tables, while one agent's [pass^k](#/glossary/passk-reliability-over-k-trials) "drops significantly" over repeated trials ([ELT-Bench](#/papers/jin2025eltbench "ELT-Bench: An End-to-End Benchmark for Evaluating AI Agents on ELT Pipelines (2025)") §3.3, §6.1).

Open: the decay is partly measured already ([How Fast Do Agents Rot?](#/papers/mittal2026rot "How Fast Do Agents Rot? An Empirical Study of Long-Horizon Degradation in LLM Agents for Production Decision-Making (2026)"), [The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)"), [Tool Use Reduces Depth-Induced…](#/papers/koplow2026depthcollapse "Tool Use Reduces Depth-Induced Collapse in OOD Reasoning (2026)")); what remains is which checks restore whole-job success, at what cost, for which models, on real jobs.

## Why it matters
- The authors of [The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)") argue that the horizon a model completes grows sharply with per-step accuracy once that is high (§2.1, Fig. 2, an illustrative model).
- If every step is checked and only failed steps get more compute, a compact model on one local server could finish long checkable jobs as reliably as a frontier API model (our reasoning). On single tasks, cheaper models passed larger ones once checks or evolved context were added, their authors report ([GRACE](#/papers/hsu2026grace "Scoped Verification for Reliable Long-Horizon Agentic Context Evolution under Distribution Shift (2026)") §5.2, one domain; [RoboPhD](#/papers/borthwick2026robophd "RoboPhD: Self-Improving Text-to-SQL Through Autonomous Agent Evolution (2026)") §4.2, Tab. 1; and [compute-optimal test-time scaling](#/papers/snell2024scaling "Scaling LLM Test-Time Compute Optimally can be More Effective than Scaling Model Parameters (2024)") abstract, §7, which finds the reverse on the hardest problems). On kinship chains, a per-step symbolic check with repair lifted 3–4B local models far more than frontier ones, and at the longest chains two of the three, patched, scored above both frontier models' plain chain of thought ([Reason Popper-ly](#/papers/chen2026popper "Reason Popper-ly: Patching In-Context Reasoning with Inductive Logic Programming (2026)") §4, Tab. 1, our comparison); its check table was completed from the benchmark's gold table (§3.1). The single-step version is [Bringing compact models to frontier accuracy](#/challenges/compact_model_accuracy).
- **Self-review keeps the errors; independent checks remove them.** A model critiquing its own answers made most of four checkable tasks worse while an exact checker's feedback helped ([On the Self-Verification Limitations…](#/papers/stechly2024selfverification "On the Self-Verification Limitations of Large Language Models on Reasoning and Planning Tasks (2024)") §5, Tab. 1); self-repair of code gains little at a matched budget while stronger feedback helps more ([Is Self-Repair a Silver…](#/papers/olausson2023selfrepair "Is Self-Repair a Silver Bullet for Code Generation? (2024)") §4.1, §4.2); errors correlate more within one model's samples than across model families ([LLMs as a Jury](#/papers/liu2026jury "LLMs as a Jury: Cross-Model Consensus Can Outperform Process Reward Models for LLM Reasoning (2026)") §5.4, Tab. 8); and at matched token cost no prompting method beats majority voting on small models, while every one that does significantly worse has the model inspect its own output ([Sample More, Reflect Less](#/papers/mirzaei2026samplemore "Sample More, Reflect Less: Self-Refine and Reflexion Lose to Repeated Sampling at Equal Token Cost, from 1.5B to 7B (2026)") abstract, §5.1).
- **What the evidence covers so far** (ours): the per-step decay is measured mainly on synthetic tasks (database benchmarks show only whole-job drops), and no summary of a listed paper shows a small model reaching a frontier model's whole-job success on long real jobs.
- **Who needs it:** every multi-step job with a check at each step, such as migrations with per-object tests ([SQL dialect translation](#/challenges/dialect_translation)), chains of certified rewrites ([SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps)), and the describer/writer/checker loop ([The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop)).

**Size of the gain:** step change, our estimate. It is measured as whole-job success on long checkable jobs: a small local model with a check at every step against a frontier model alone, at equal or lower cost. The reason: under the O-ring model a 10× cut in per-step error turns most failed long jobs into finished ones, and moving that work from an API to one local server changes where it can run.

## Why it's hard
- **Few long jobs have a cheap check at every step.** Migrations and rewrite chains do. The steps that fail most when an agent writes SQL from English, such as reading the user's intent, have no cheap check ([Checking text-to-SQL against intent](#/challenges/text_to_sql_verification)). Checking the computed steps is not enough by itself: in an MD5 computation run as dependent tool calls and compared call by call with an exact reference, the authors attribute failed runs mostly to the driver mis-carrying state between calls, and report that correcting every worker operation does not by itself rescue such a run ([Long-Horizon State Tracking in LLMs](#/papers/pai2026md5 "Long-Horizon State Tracking in LLMs: Executing MD5 through a Deep Sequence of Dependent Tool Calls (2026)") §5.2, §5.4, Tab. 2; the worker setting's counts are unprinted).
- **Each extra call corrupts as well as corrects.** Logging each extra model call's fixes and breaks on the same tasks shows that net accuracy hides both ([Correction and Corruption](#/papers/reitich2026correction "Correction and Corruption: A Two-Rate View of Error Flow in LLM Protocols (2026)") Tab. 1, §2.3). Repeating repair on one candidate can end below no repair: with noisy verifiers and a repairer shown a perturbed copy of the problem, true validity fell round after round of unconditional repair in most of VRR-Stop's settings, rising only in the one without perturbation ([VRR-Stop ("Verify](#/papers/wu2026vrrstop "Verify, Repair, Repeat, or Stop? Robust Stopping for Noisy Verify-Repair Loops in LLM Agents (2026)") §5.2, App. C.1).
- **Errors are not independent.** One misunderstanding can sink several steps, so pⁿ need not hold, and a model conditions on its own earlier errors ([The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)"), above). On long procedural outputs, decline generally deviates from a constant per-entry error rate, the rate rising with length, and later segments fail more even after a correct prefix ([LongProc ("Long Procedural Generation")](#/papers/ye2025longproc "LongProc: Benchmarking Long-Context Language Models on Long Procedural Generation (2025)") App. A.5, §5, Fig. 4). SWE-agent's odds of recovering from failed edits "decrease as the agent accumulates more failed edits" ([SWE-agent](#/papers/yang2024sweagent "SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering (2024)") §5.2), and once its first approach fails it "struggles to make use of later turns that build upon past mistakes" (App. B.3.1).
- **Weak checks cap the gain.** When tests accept wrong programs, sampling until they pass hits a ceiling ([The Limits of Inference…](#/papers/stroebl2024resampling "The Limits of Inference Scaling Through Resampling (2024)") §3, Fig. 3), so the per-step check must be sound ([Weak checkers get exploited](#/challenges/weak_checker_exploitation)).
- **The target moves, and small models can't tune themselves.** Frontier per-step reliability rises with each model generation, and for many published LLM techniques, one generated prompt on a newer model beats the published result ([What Survives the Next Model?](#/papers/salsabil2026survives "What Survives the Next Model? Benchmarking LLM-Based Techniques Against Single-Prompts (2026)") §V-A, Tab. II). Small models used as their own prompt optimizer and scorer produced instructions that scored below plain chain-of-thought prompts ([Revisiting OPRO](#/papers/zhang2024opro "Revisiting OPRO: The Limitations of Small-Scale LLMs as Optimizers (2024)") §3.2, Tab. 1), so the optimizer or the check must come from outside.

## Verifiable signal
A job is a sequence of steps, each with a programmatic check: a query's result on test databases, a counterexample search, a schema or type check, a test. Whole-job success is checked the same way at the end. Per-step reliability, and the share of observed or injected errors that survive self-review against an independent check, are counts over checked steps. Each extra call's fixes and breaks are logged on the same tasks (the method of [Correction and Corruption](#/papers/reitich2026correction "Correction and Corruption: A Two-Rate View of Error Flow in LLM Protocols (2026)")), and reliability over repeated tries is measurable as pass^k (as in [GRACE](#/papers/hsu2026grace "Scoped Verification for Reliable Long-Horizon Agentic Context Evolution under Distribution Shift (2026)") §5.1). No LLM judge is needed wherever each step has a program check.
