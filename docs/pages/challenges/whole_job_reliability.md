# Whole-job reliability of multi-step LLM work

> Per-step errors compound over long jobs, so a model that is good at each step can still fail most long jobs. Which checks restore whole-job success, and can a small local model, checked at every step, finish long jobs as reliably as a frontier model?

<p class="tags"><a class="tag" href="#/tags/harness">harness</a><a class="tag" href="#/tags/scaling">scaling</a></p>

## Challenge
A long job, such as a migration done object by object, a chain of rewrites or an agent's tool loop, succeeds only if every essential step does. If each step succeeds independently with probability p, an n-step job succeeds with probability pⁿ, so per-step reliability that looks good fails most long jobs. The decay is measured mainly on synthetic tasks, and no paper listed here's summary shows a small model matching a frontier model's whole-job success on long real jobs (ours).

## What's known
The decay as measured:
- on simulator-checked synthetic task families, the authors report that success follows a geometric law in per-step reliability ([How Fast Do Agents Rot?](#/papers/mittal2026rot "How Fast Do Agents Rot? An Empirical Study of Long-Horizon Degradation in LLM Agents for Production Decision-Making (2026)") p. 2), that most models collapse on a long tool loop (Tab. 2, PDF p. 6), that errors are absorbing (§4.6, PDF p. 8) and that step count, not context length, drives the decline (§4.5, PDF p. 8); its released analysis doesn't support the geometric-law count;
- on a benchmark built so that compositional depth can't be shortcut, next-step accuracy without tools collapses with depth in small and frontier models, while code execution largely removed the collapse in frontier and small thinking models and only mitigated it in small instruct ones ([Tool Use Reduces Depth-Induced…](#/papers/koplow2026depthcollapse "Tool Use Reduces Depth-Induced Collapse in OOD Reasoning (2026)") §4.2–4.3, Fig. 4);
- elsewhere length is a driver too, by varying shares (our reading): context length alone lowers single-step accuracy in two 7–8B open models, even with the evidence next to the question ([Context Length Alone Hurts…](#/papers/du2025contextlength "Context Length Alone Hurts LLM Performance Despite Perfect Retrieval (2025)") §4.1); with the context held fixed, proof depth and context length lower Prolog proof accuracy comparably ([Probing for Long-Horizon Deductive…](#/papers/alnegheimish2026prolong "Probing for Long-Horizon Deductive Reasoning Capabilities in Language Models with Prolog (2026)") §4.5, Tab. 1); on prompts of many easy items to label and aggregate, success tracks item count more than length ([Understanding LLM Performance Degradation…](#/papers/chen2026multiinstance "Understanding LLM Performance Degradation in Multi-Instance Processing: The Roles of Instance Count and Context Length (2026)") §6.2);
- models given the plan and the knowledge still fail long simple tasks, and without thinking err more after seeing their own earlier errors ([The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)") §3.1, §3.2, Fig. 5);
- on τ²-bench, 4-bit weights leave the final score flat while tool-name errors rise significantly in two of ten model–domain cells, in the worst one hidden by the benchmark's budget of failed calls ([Flat Score, Amplified Failures](#/papers/jang2026flatscore "Flat Score, Amplified Failures: How the Error Budget Masks Damage in Quantized LLM Agents (2026)") Tab. 1, Tab. 2);
- on database jobs, which show only whole-job drops (ours), PL/SQL conversations with every turn correct are much rarer than correct turns, which its authors read as errors that "compound across successive modifications" ([PLSQLBench](#/papers/liu2026plsqlbench "PLSQLBench: Benchmarking LLM Systems for Executable Procedural Database Programming (2026)") §4.3); agents repairing live PostgreSQL and TiDB faults often pass the diagnosis check yet leave the task incomplete: "satisfying the diagnostic criteria does not ensure completion of the required operational tasks" ([DBA-Bench](#/papers/chen2026dbabench "DBA-Bench: A Production-Fidelity Benchmark for LLM-Based Database Operations Agents (2026)") §6.2); the best ELT agent loads all sources far more often than it builds correct target tables, and one agent's [pass^k](#/glossary/passk-reliability-over-k-trials) "drops significantly" over repeated trials ([ELT-Bench](#/papers/jin2025eltbench "ELT-Bench: An End-to-End Benchmark for Evaluating AI Agents on ELT Pipelines (2025)") §3.3, §6.1).

Checks during the job, as measured:
- per-step voting, with over-long or badly formatted answers discarded, carried gpt-4.1-mini through a Towers of Hanoi run of over a million moves "with zero errors": one run, the solution strategy in every prompt ([Solving a Million-Step LLM…](#/papers/meyerson2025maker "Solving a Million-Step LLM Task with Zero Errors (2025)") §3.2–3.3, §4.1, §4.4);
- in a four-agent financial pipeline with wrong numbers injected into the first agent's output, the same deterministic number check after every handoff, passing corrections on, left far fewer in the final report than one check after the last agent, which cannot correct, at a cost in the report's internal-consistency score ([The Hallucination Snowball](#/papers/singh2026snowball "The Hallucination Snowball: Modeling Error Propagation as State Transitions in Multi-Agent LLM Pipelines (2026)") §3.4, Tab. 3);
- program checkers that test a run as it goes and feed violations back raised Qwen3-30B-A3B's τ²-bench telecom success on all four of four runs well above chain of thought, less with an LLM-simulated user than with the user's details given up front, where the gain came mostly from rules debugged from traces and task checks from the user's request, not the policy alone ([interwhen](#/papers/bhat2026interwhen "interwhen: A Generalizable Framework for Steering Reasoning Models with Test-time Verification (2026)") §4.1, §5.1, Tab. 3).

## Why it matters
- The authors of [The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)") argue that the horizon a model completes grows sharply with per-step accuracy once that is high (§2.1, Fig. 2, an illustrative model).
- If every step is checked and only failed steps get more compute, a compact model on one local server could finish long checkable jobs as reliably as a frontier API model (our reasoning).
- **Small models with checks can pass large ones.** On single tasks, cheaper models passed larger ones once checks or evolved context were added, their authors report ([GRACE](#/papers/hsu2026grace "Scoped Verification for Reliable Long-Horizon Agentic Context Evolution under Distribution Shift (2026)") §5.2, one domain; [RoboPhD](#/papers/borthwick2026robophd "RoboPhD: Self-Improving Text-to-SQL Through Autonomous Agent Evolution (2026)") §4.2, Tab. 1; [compute-optimal test-time scaling](#/papers/snell2024scaling "Scaling LLM Test-Time Compute Optimally can be More Effective than Scaling Model Parameters (2024)") abstract, §7, which finds the reverse on the hardest problems). On kinship chains, a per-step symbolic check with repair lifted 3–4B models far more than frontier ones, and at the longest chains two of the three, patched, scored above both frontier models' plain chain of thought ([Reason Popper-ly](#/papers/chen2026popper "Reason Popper-ly: Patching In-Context Reasoning with Inductive Logic Programming (2026)") §4, Tab. 1, our comparison); its check table was completed from the benchmark's gold table (§3.1).
- **Self-review keeps the errors; independent checks remove them.** GPT-4 critiquing its own answers made three of four checkable tasks worse while an exact checker's feedback helped ([On the Self-Verification Limitations…](#/papers/stechly2024selfverification "On the Self-Verification Limitations of Large Language Models on Reasoning and Planning Tasks (2024)") §5, Tab. 1); self-repair of code often gains little at a matched budget, while a stronger model's feedback helps more ([Is Self-Repair a Silver…](#/papers/olausson2023selfrepair "Is Self-Repair a Silver Bullet for Code Generation? (2024)") §4.1, §4.2); errors correlate more within one model's samples than across model families ([LLMs as a Jury](#/papers/liu2026jury "LLMs as a Jury: Cross-Model Consensus Can Outperform Process Reward Models for LLM Reasoning (2026)") §5.4, Tab. 8); at matched token cost no prompting method beats majority voting on small models, and every one that does significantly worse has the model inspect its own output ([Sample More, Reflect Less](#/papers/mirzaei2026samplemore "Sample More, Reflect Less: Self-Refine and Reflexion Lose to Repeated Sampling at Equal Token Cost, from 1.5B to 7B (2026)") abstract, §5.1).
- **Who needs it:** migrations with per-object tests ([SQL dialect translation](#/challenges/dialect_translation)), chains of certified rewrites ([Verified query speedups](#/challenges/verified_query_speedup)), the describer/writer/checker loop ([The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop)): every multi-step job with a check at each step.

**Size of the gain:** step change, our estimate. It is measured as whole-job success on long checkable jobs: a small local model with a check at every step against a frontier model alone, at equal or lower cost. The reason: under the O-ring model a 10× cut in per-step error turns most failed long jobs into finished ones, and moving that work from an API to one local server changes where it can run.

## Why it's hard
- **Few long jobs have a cheap check at every step.** Migrations and rewrite chains do (ours); reading the user's intent, when an agent writes SQL from English, has no cheap check ([Checking text-to-SQL against intent](#/challenges/text_to_sql_verification)). Checking the computed steps is not enough by itself: in an MD5 computation run as dependent tool calls and compared call by call with an exact reference, the authors attribute failed runs mostly to the driver mis-carrying state between calls, and report that correcting every worker operation does not by itself rescue such a run ([Long-Horizon State Tracking in LLMs](#/papers/pai2026md5 "Long-Horizon State Tracking in LLMs: Executing MD5 through a Deep Sequence of Dependent Tool Calls (2026)") §5.2, §5.4, Tab. 2; the worker setting's counts are unprinted).
- **Each extra call corrupts as well as corrects.** Logging each extra call's fixes and breaks on the same tasks shows that net accuracy hides both ([Correction and Corruption](#/papers/reitich2026correction "Correction and Corruption: A Two-Rate View of Error Flow in LLM Protocols (2026)") Tab. 1, §2.3). Repeated repair of one candidate can end below no repair: with noisy verifiers and a repairer shown a perturbed copy of the problem, true validity fell round after round of unconditional repair in most of VRR-Stop's settings, rising only in the one without perturbation ([VRR-Stop ("Verify](#/papers/wu2026vrrstop "Verify, Repair, Repeat, or Stop? Robust Stopping for Noisy Verify-Repair Loops in LLM Agents (2026)") §5.2, App. C.1).
- **Errors are not independent.** One misunderstanding can sink several steps, so pⁿ need not hold. Measured departures from pⁿ go both ways. On synthetic API workflows, 20-step chains passed far more often than the product of their steps' solo pass rates, which its authors say plausibly comes from chain grading that checks only selected earlier steps and from correlated within-session competence ([APIFlow-Bench](#/papers/wan2026apiflowbench "APIFlow-Bench: Measuring Whether Agents Survive Long, Dependent API Workflows (2026)") §8.5). On graphs of dependent math and Python tasks that each model solved reliably alone, final-task accuracy fell below the product of the isolated accuracies in every condition, and outside one shuffled topology most failed runs first went wrong at a node that had received its intended input ([ArbiGraph](#/papers/golikov2026arbigraph "ArbiGraph: Composing Arbitrary Verifiable Tasks for Agent Evaluation (2026)") abstract, §4.2, §6).
- **Later steps can fail more.** On long procedural outputs, decline generally deviates from a constant per-entry error rate, the rate rising with length, and later segments fail more even after a correct prefix ([LongProc ("Long Procedural Generation")](#/papers/ye2025longproc "LongProc: Benchmarking Long-Context Language Models on Long Procedural Generation (2025)") App. A.5, §5, Fig. 4). SWE-agent's odds of recovering from failed edits "decrease as the agent accumulates more failed edits" ([SWE-agent](#/papers/yang2024sweagent "SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering (2024)") §5.2), and once its first approach fails it "struggles to make use of later turns that build upon past mistakes" (App. B.3.1).
- **Weak checks cap the gain.** When tests accept wrong programs, sampling until they pass hits a ceiling ([The Limits of Inference…](#/papers/stroebl2024resampling "The Limits of Inference Scaling Through Resampling (2024)") §3, Fig. 3), so the per-step check must be sound ([Weak checkers get exploited](#/challenges/weak_checker_exploitation)).
- **The target moves, and small models tune themselves poorly.** Frontier per-step reliability rises with each model generation (ours), and for many published LLM-based software-engineering techniques, one generated prompt on a newer model beats the published result ([What Survives the Next Model?](#/papers/salsabil2026survives "What Survives the Next Model? Benchmarking LLM-Based Techniques Against Single-Prompts (2026)") §V-A, Tab. II). Three of four small models used as their own prompt optimizer and scorer produced instructions that scored below plain chain-of-thought prompts on GSM8K ([Revisiting OPRO](#/papers/zhang2024opro "Revisiting OPRO: The Limitations of Small-Scale LLMs as Optimizers (2024)") §3.2, Tab. 1), so the optimizer or the check should come from outside (ours).

## Verifiable signal
Each step has a program check (a query's result on test databases, a counterexample search, a schema or type check, a test), and the whole job is checked the same way at the end. Per-step reliability, the share of observed or injected errors that survive self-review against an independent check, and each extra call's fixes and breaks (as in [Correction and Corruption](#/papers/reitich2026correction "Correction and Corruption: A Two-Rate View of Error Flow in LLM Protocols (2026)")) are counts over checked steps; reliability over repeated tries is measurable as pass^k (as in [GRACE](#/papers/hsu2026grace "Scoped Verification for Reliable Long-Horizon Agentic Context Evolution under Distribution Shift (2026)") §5.1). No LLM judge is needed where every step has a program check.

**Named attack (ours):** a small local model with a program check and resampling at every step, on one long checkable job (a multi-object SQL migration with per-object result tests); it measures whole-job success against the pⁿ prediction from its own per-step rates and against a frontier model alone.
