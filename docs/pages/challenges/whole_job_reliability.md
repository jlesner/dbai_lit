# Whole-job reliability of multi-step LLM work

> Per-step errors compound over long jobs, so a model that is good at each step still fails most long jobs. Which checks restore whole-job success, and can a small local model, checked at every step, finish long jobs as reliably as a frontier model?

<p class="tags"><a class="tag" href="#/tags/harness">harness</a><a class="tag" href="#/tags/scaling">scaling</a></p>

## Challenge
A long job succeeds only if every essential step does: a migration done object by object, a chain of rewrites, a pipeline of dependent queries, an agent's tool loop. The decay as measured:
- on simulator-checked task families, success falls roughly as per-step reliability to the power of the step count, every model tested collapses on a long tool loop, errors are absorbing, and step count, not context length, drives the decline (per [How Fast Do Agents Rot?](#/papers/mittal2026rot "How Fast Do Agents Rot? An Empirical Study of Long-Horizon Degradation in LLM Agents for Production Decision-Making (2026)")'s summary § Results, unchecked; synthetic tasks);
- models given the plan and the knowledge still fail long simple tasks, and err more after seeing their own earlier errors (per [The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)")'s summary § Results, unchecked);
- 4-bit quantization leaves an agent benchmark's final score flat while one model's tool-name errors grow, hidden by the benchmark's failure budget (per [Flat Score, Amplified Failures](#/papers/jang2026flatscore "Flat Score, Amplified Failures: How the Error Budget Masks Damage in Quantized LLM Agents (2026)")'s summary § Results, unchecked);
- on database jobs, PL/SQL conversations with every turn correct are much rarer than correct turns, which its authors read as errors that "compound across successive modifications" ([PLSQLBench](#/papers/liu2026plsqlbench "PLSQLBench: Benchmarking LLM Systems for Executable Procedural Database Programming (2026)") §4.3); agents repairing live PostgreSQL faults "often localize the root cause without completing the repair" ([DBA-Bench](#/papers/chen2026dbabench "DBA-Bench: A Production-Fidelity Benchmark for LLM-Based Database Operations Agents (2026)") §6.2); and the best ELT agent loads all sources far more often than it builds correct target tables, while one agent's [pass^k](#/glossary/passk-reliability-over-k-trials) "drops significantly" over repeated trials ([ELT-Bench](#/papers/jin2025eltbench "ELT-Bench: An End-to-End Benchmark for Evaluating AI Agents on ELT Pipelines (2025)") §3.3, §6.1).

## Why it matters
- Per [The Illusion of Diminishing Returns](#/papers/sinha2025longhorizon "The Illusion of Diminishing Returns: Measuring Long Horizon Execution in LLMs (2026)") the horizon a model completes grows sharply with per-step accuracy once that is high (§ Results, unchecked).
- If every step is checked and only failed steps get more compute, a compact model on one local server could finish long checkable jobs as reliably as a frontier API model (our reasoning). On single tasks, the summaries report cheaper models passing larger ones once checks or evolved context are added (per the summaries of [GRACE](#/papers/hsu2026grace "Scoped Verification for Reliable Long-Horizon Agentic Context Evolution under Distribution Shift (2026)"), one domain; [RoboPhD](#/papers/borthwick2026robophd "RoboPhD: Self-Improving Text-to-SQL Through Autonomous Agent Evolution (2026)"); and [compute-optimal test-time scaling](#/papers/snell2024scaling "Scaling LLM Test-Time Compute Optimally can be More Effective than Scaling Model Parameters (2024)"), which finds the reverse on the hardest problems; all unchecked). The single-step version is [Bringing compact models to frontier accuracy](#/challenges/compact_model_accuracy).
- **Self-review keeps the errors; independent checks remove them.** Per the summaries, a model critiquing its own answers made most of four checkable tasks worse while an exact checker's feedback helped ([On the Self-Verification Limitations…](#/papers/stechly2024selfverification "On the Self-Verification Limitations of Large Language Models on Reasoning and Planning Tasks (2024)") § Results); self-repair of code gains little at a matched budget while stronger feedback helps more ([Is Self-Repair a Silver…](#/papers/olausson2023selfrepair "Is Self-Repair a Silver Bullet for Code Generation? (2024)") § Results); errors correlate more within one model's samples than across model families ([LLMs as a Jury](#/papers/liu2026jury "LLMs as a Jury: Cross-Model Consensus Can Outperform Process Reward Models for LLM Reasoning (2026)") § Results); and at matched token cost no prompting method beats majority voting on small models, while every one that does significantly worse has the model inspect its own output ([Sample More, Reflect Less](#/papers/mirzaei2026samplemore "Sample More, Reflect Less: Self-Refine and Reflexion Lose to Repeated Sampling at Equal Token Cost, from 1.5B to 7B (2026)") § Results); all unchecked.
- **Who needs it:** every multi-step job with a check at each step, such as migrations with per-object tests ([SQL dialect translation](#/challenges/dialect_translation)), chains of certified rewrites ([SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps)), and the describer/writer/checker loop ([The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop)).

**Size of the gain:** step change, measured as whole-job success on long checkable jobs: a small local model with a check at every step against a frontier model alone, at equal or lower cost. Under the O-ring model, a 10× cut in per-step error turns most failed long jobs into finished ones, and moving the work from an API to one local server is a cost drop that changes where the work can run. This is our estimate: the per-step decay is measured mainly on synthetic tasks (database benchmarks show only whole-job drops), and no summary shows a small model reaching a frontier model's whole-job success on long real jobs.

## Verifiable signal
A job is a sequence of steps, each with a programmatic check: a query's result on test databases, a counterexample search, a schema or type check, a test. Whole-job success is checked the same way at the end. Per-step reliability, and the share of observed or injected errors that survive self-review against an independent check, are counts over checked steps. Each extra call's fixes and breaks are logged on the same tasks ([Correction and Corruption](#/papers/reitich2026correction "Correction and Corruption: A Two-Rate View of Error Flow in LLM Protocols (2026)")'s method, per its summary), and reliability over repeated tries is measurable as pass^k (per [GRACE](#/papers/hsu2026grace "Scoped Verification for Reliable Long-Horizon Agentic Context Evolution under Distribution Shift (2026)")'s summary). No LLM judge is needed wherever each step has a program check.
