# Text-to-SQL can't be verified against intent

> English is ambiguous and gold queries are often wrong, so text-to-SQL is used here as a *source of pairs*, not as a goal.

<p class="tags"><a class="tag sub" href="#/tags/nl2sql-eval">nl2sql-eval</a></p>

## Challenge
Evaluate a generated SQL query against an English question. BIRD's official metric, [execution accuracy](#/glossary/execution-accuracy) (EX; SpotIt calls it EX-test), compares the generated query's result with the [gold query](#/glossary/gold-query)'s on one test database, as sets, so row order and duplicates are ignored ([BIRD](#/papers/li2023bird "Can LLM Already Serve as A Database Interface? A BIg Bench for Large-Scale Database Grounded Text-to-SQLs (2023)") App. B.7). That accepts wrong queries that happen to agree on that data (the argument of [Semantic Evaluation for Text-to-SQL…](#/papers/zhong2020testsuite "Semantic Evaluation for Text-to-SQL with Distilled Test Suites (2020)") §1, whose test suites of databases reduce the problem for Spider). Spider's authors already warned that EX "can create false positive evaluation" and that exact matching gives false negatives ([Spider](#/papers/yu2018spider "Spider: A Large-Scale Human-Labeled Dataset for Complex and Cross-Domain Semantic Parsing and Text-to-SQL Task (2018)") §6).

## Why it matters
Checking a query against the intent of the question is not a target here, because it can't be certified. The challenge matters for what it supplies to the other challenges and for what it uses from them.

- **A source of hard, realistic pairs.** A generated query and its gold query answer the same question, so in our reading they are often nearly equivalent, the hard cases for [Query equivalence: prove or refute](#/challenges/query_equivalence). The SpotIt authors collected the generated SQL of top BIRD methods and found separating databases for many pairs that the official test had accepted ([SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)") §5; effect on scores and rankings: [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) § Why it matters). On Spider 2.0 they report that many pairs used operators their engine doesn't support, a majority of them [window functions](#/glossary/window-function) (§5), so the same pairs show where checkers fail ([SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps)).
- **A large user of the part that can be checked.** [Text-to-SQL](#/glossary/text-to-sql) scores, candidate selection and RL rewards all compare one query with another: test suites of databases ([Semantic Evaluation for Text-to-SQL…](#/papers/zhong2020testsuite "Semantic Evaluation for Text-to-SQL with Distilled Test Suites (2020)") §1), separating instances to choose among candidates ([data-aware NL2SQL candidate selection](#/papers/kikot2026separating "Data-aware candidate selection in NL2SQL translation via small separating instances (2026)") abstract), a reward lowered when VeriEQL refutes equivalence with the gold query ([ReViSQL](#/papers/zhu2026revisql "Human-Level Text-to-SQL via Reinforcement Learning on Verified Data, Without Pipeline Engineering (2026)") §4.2; [Weak checkers get exploited](#/challenges/weak_checker_exploitation)). Each could use a certified "different" verdict. What the weaker checks cost there (wrong gold queries, false matches, ties) is the case made in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence).
- **The intent part stays unchecked.** Verifying intent would let users trust an answer to an English question. ROSE, an intent-centered metric, judges it with a Prover and a Refuter that are reasoning models ([ROSE](#/papers/pei2026rose "ROSE: An Intent-Centered Evaluation Metric for NL2SQL (2026)") §1), so its verdict is an LLM's judgment, not a [certificate](#/glossary/certificate) (LLM as judge); LLM-SQL-Solver's authors call their LLM-judged "pragmatic" equivalence "often highly subjective" ([LLM-SQL-Solver](#/papers/zhao2023llmsqlsolver "LLM-SQL-Solver: Can LLMs Determine SQL Equivalence? (2025)") §5.2). A certified difference from the gold query still leaves open which one is wrong (Verifiable signal below). In our reading, that payoff has no certificate in sight.

**Size of the gain:** enabler, measured as the number of realistic, nearly equivalent pairs (generated vs gold, or several systems' answers to one question) that get a proof or a validated counterexample. The gain shows up in [Sourcing realistic, hard query pairs](#/challenges/query_pair_sourcing), [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps) and [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth); for intent itself we expect no certified gain, since the English has no [formal semantics](#/glossary/formal-semantics). This is our estimate.

## Verifiable signal
Only relative to the gold query: a counterexample shows generated ≢ gold, and then either one could be wrong, or both could be valid readings of an ambiguous question, which a single gold query per question ignores ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)")). Starting from SQL instead of English ([The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop)) turns it into a checkable Q ≡ Q′ question.
