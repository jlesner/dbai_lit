# Checking text-to-SQL against intent

> Check a generated SQL query against the intent of its English question. English is ambiguous and gold queries are often wrong, so only the comparison with another query can be certified, and text-to-SQL is used here as a *source of pairs*, not as a goal.

<p class="tags"><a class="tag sub" href="#/tags/nl2sql-eval">nl2sql-eval</a></p>

## Challenge
Evaluate a generated SQL query against an English question. The checkable part is its comparison with the [gold query](#/glossary/gold-query), or between candidates (Verifiable signal).

## What's known
BIRD's official metric, [execution accuracy](#/glossary/execution-accuracy) (EX; SpotIt calls it EX-test), compares the generated query's result with the gold query's on one test database, as sets, so row order and duplicates are ignored ([BIRD](#/papers/li2023bird "Can LLM Already Serve as A Database Interface? A BIg Bench for Large-Scale Database Grounded Text-to-SQLs (2023)") App. B.7). That accepts wrong queries that happen to agree on that data (the argument of [Semantic Evaluation for Text-to-SQL…](#/papers/zhong2020testsuite "Semantic Evaluation for Text-to-SQL with Distilled Test Suites (2020)") §1, whose test suites of databases reduce the problem for Spider). Spider's authors already warned that EX "can create false positive evaluation" and that exact matching gives false negatives ([Spider](#/papers/yu2018spider "Spider: A Large-Scale Human-Labeled Dataset for Complex and Cross-Domain Semantic Parsing and Text-to-SQL Task (2018)") §6). Spider 2.0 handles unspecified output columns by loosening EX: a prediction passes if every gold column appears among its columns ([Spider 2.0](#/papers/lei2024spider2 "Spider 2.0: Evaluating Language Models on Real-World Enterprise Text-to-SQL Workflows (2025)") §2.2, App. A); its authors say this adds no false positives, stated "Empirically" with no data shown (App. A; our reading). Multi-turn benchmarks that change data grade by state instead: DySQL-Bench runs the agent's statements and the golden ones on copies of one database and compares hashes of every table, leaving out timestamp-like columns ([DySQL-Bench](#/papers/sun2025dysqlbench "Rethinking Text-to-SQL: Dynamic Multi-turn SQL Interaction for Real-world Database Exploration (2025)") §III); in our reading that checks the writes on one database only, and leaves the answers given to read requests unchecked. False positives of execution on test databases are on record: ReViSQL reports many positive execution rewards in training that VeriEQL refutes ([ReViSQL](#/papers/zhu2026revisql "Human-Level Text-to-SQL via Reinforcement Learning on Verified Data, Without Pipeline Engineering (2026)") §4.1; caveats in [Weak checkers get exploited](#/challenges/weak_checker_exploitation) § What's known). SpotIt returns no counterexample when it times out or the query is unsupported ([SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)") Alg. 1), so such pairs count as correct: its accuracy is an upper bound (our reading). By the ParSEval authors' manual inspection, BIRD's own databases pass more wrong predictions than ParSEval's suites, generated from the gold queries alone, which in turn miss, for example, an extra table joined only by the prediction ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §5.5, PDF p. 12).

An expert-checked agent audit finds annotation errors, ambiguity included, in most examples of BIRD Mini-Dev and Spider 2.0-Snow ([Pervasive Annotation Errors Break…](#/papers/jin2026annotation "Pervasive Annotation Errors Break Text-to-SQL Benchmarks and Leaderboards (2026)") §4.3, §1). Two benchmarks built for ambiguity give an ambiguous question two or more gold queries, and both report that models often miss the other readings ([AmbiQT](#/papers/bhaskar2023ambiqt "Benchmarking and Improving Text-to-SQL Generation under Ambiguity (2023)") abstract; [AMBROSIA](#/papers/saparina2024ambrosia "AMBROSIA: A Benchmark for Parsing Ambiguous Questions into Database Queries (2024)") §3.4, §4.1). The ReViSQL authors attribute most of their model's remaining failures on two hand-corrected BIRD sets to valid readings that differ from the gold, by their own manual classification ([ReViSQL](#/papers/zhu2026revisql "Human-Level Text-to-SQL via Reinforcement Learning on Verified Data, Without Pipeline Engineering (2026)") §5.2), and SQLDriller's repair of gold queries assumes the question has one reading ([SQLDriller](#/papers/yang2025sqldriller "Automated Validating and Fixing of Text-to-SQL Translation with Execution Consistency (2025)") §3.1 footnote 4, §7). Renggli et al. name ambiguous and unanswerable questions as the main causes of noise in evaluation data ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)") §3) and know of "no methods to automatically find samples with missing alternative variants" (§5.2.2). Alpha-SQL selects by agreement on the premise of "the convergent nature of [Text-to-SQL](#/glossary/text-to-sql): different reasoning paths yield equivalent SQL queries" ([Alpha-SQL](#/papers/li2025alphasql "Alpha-SQL: Zero-Shot Text-to-SQL using Monte Carlo Tree Search (2025)") §4.2), which an ambiguous question breaks (our reading).

ROSE, an intent-centered metric, judges intent with a Prover and a Refuter that are reasoning models ([ROSE](#/papers/pei2026rose "ROSE: An Intent-Centered Evaluation Metric for NL2SQL (2026)") §1), so its verdict is an LLM's judgment, not a [certificate](#/glossary/certificate) (LLM as judge); LLM-SQL-Solver's authors call their LLM-judged "pragmatic" equivalence "often highly subjective" ([LLM-SQL-Solver](#/papers/zhao2023llmsqlsolver "LLM-SQL-Solver: Can LLMs Determine SQL Equivalence? (2025)") §5.2). An evolved verifier for Spider 2.0-Snow agreed with execution match only near chance once prompt grounding left mostly "semantically wrong values under clean execution, invisible to deterministic detectors" ([Who Verifies the Verifier?…](#/papers/zhang2026whoverifies "Who Verifies the Verifier? Co-Evolving Inspectable Graders with Self-Improving Agents (2026)") §5.5); its authors name outputs "that execute cleanly yet are semantically wrong" as the open frontier (§6). Among the referees that choose between candidates (Why it's hard), the SISelection authors call the LLM's wrong answers "the bottleneck of our selection method" ([data-aware NL2SQL candidate selection](#/papers/kikot2026separating "Data-aware candidate selection in NL2SQL translation via small separating instances (2026)") §2), and DPC's released reliability run doesn't support its Python referee as the more reliable side. With no gold query at all, Synthetic Execution has an LLM invent a small database and the answer it expects, then runs the query on it ([Developing and Benchmarking Verification…](#/papers/alrashed2026verification "Developing and Benchmarking Verification Algorithms to Improve Text-to-SQL Generation (2026)") §3.3, PDF p. 3); its authors trace part of its false rejections to hallucinated synthetic data (§5.2.1, PDF p. 6).

Still open (ours): a certificate for intent, which in our reading is not in sight; what can be certified is that two queries differ, not which one answers the question.

## Why it matters
Checking a query against the intent of the question is not a target here, because it can't be certified. The challenge matters for what it supplies to the other challenges and for what it uses from them.

- **A source of hard, realistic pairs.** A generated query and its gold query answer the same question, so in our reading they are often nearly equivalent, the hard cases for [Query equivalence: prove or refute](#/challenges/query_equivalence). The SpotIt authors collected the generated SQL of top BIRD methods and found separating databases for many pairs that the official test had accepted ([SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)") §5; effect on scores and rankings: [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) § Why it matters). On Spider 2.0 they report that many pairs used operators their engine doesn't support, a majority of them [window functions](#/glossary/window-function) (§5), so the same pairs show where checkers fail ([SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps)).
- **A large user of the part that can be checked.** Text-to-SQL scores, candidate selection and RL rewards all compare one query with another: test suites of databases ([Semantic Evaluation for Text-to-SQL…](#/papers/zhong2020testsuite "Semantic Evaluation for Text-to-SQL with Distilled Test Suites (2020)") §1), separating instances to choose among candidates ([data-aware NL2SQL candidate selection](#/papers/kikot2026separating "Data-aware candidate selection in NL2SQL translation via small separating instances (2026)") abstract), a reward lowered when VeriEQL refutes equivalence with the gold query ([ReViSQL](#/papers/zhu2026revisql "Human-Level Text-to-SQL via Reinforcement Learning on Verified Data, Without Pipeline Engineering (2026)") §4.2; [Weak checkers get exploited](#/challenges/weak_checker_exploitation) § What's known). Each could use a certified "different" verdict. What the weaker checks cost there (wrong gold queries, false matches, ties) is the case made in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth) and [Equivalence of nondeterministic queries](#/challenges/nondeterministic_equivalence).
- **The intent part stays unchecked.** Verifying intent would let users trust an answer to an English question. The intent checks on record are in What's known. A certified difference from the gold query still leaves open which one is wrong (Verifiable signal below). In our reading, that payoff has no certificate in sight.

**Size of the gain:** enabler, our estimate. The quantity it lifts is the number of realistic, nearly equivalent pairs (generated vs gold, or several systems' answers to one question) that get a proof or a validated counterexample in [Sourcing realistic, hard query pairs](#/challenges/query_pair_sourcing), [SQL features that verifiers don't cover](#/challenges/verifier_coverage_gaps) and [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth). The reason: generated and gold queries answer the same question, so they are often nearly equivalent (our reading, above), while for intent itself we expect no certified gain, since the English has no [formal semantics](#/glossary/formal-semantics).

## Why it's hard
- There's no formal semantics for the English, so "correct" isn't checkable.
- English is ambiguous, so a question can have several correct queries, but benchmarks accept one, "ignoring alternative, equally likely SQL queries" ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)") §1, §5.2; also [AmbiQT](#/papers/bhaskar2023ambiqt "Benchmarking and Improving Text-to-SQL Generation under Ambiguity (2023)") §1, [AMBROSIA](#/papers/saparina2024ambrosia "AMBROSIA: A Benchmark for Parsing Ambiguous Questions into Database Queries (2024)") §2). A query that differs from the gold one can still be right. Writers whose answers a separating database certifies as different flag the question as ambiguous or a writer as wrong; which reading was meant stays uncertified ([The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop) § Why it's hard, blame assignment; our reasoning).
- Gold queries are wrong often enough to matter: SQLDriller finds many wrong mappings in Spider and BIRD, and model accuracy drops when re-evaluated on corrected sets ([SQLDriller](#/papers/yang2025sqldriller "Automated Validating and Fixing of Text-to-SQL Translation with Execution Consistency (2025)") Tab. 1, Tab. 2, §2.2).
- Test-database execution gives false positives. SpotIt uses [bounded verification](#/glossary/bounded-verification) of generated vs gold SQL to find them ([SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)")).
- **Choosing among candidates without a gold query moves the unchecked part to a referee.** A separating instance certifies that two candidates differ; which one answers the question is then decided by an LLM, which evaluates the question on a small instance extracted from the database by provenance ([data-aware NL2SQL candidate selection](#/papers/kikot2026separating "Data-aware candidate selection in NL2SQL translation via small separating instances (2026)") §2) or writes a Python solution on an LLM-built one ([DPC (Dual-Paradigm Consistency)](#/papers/li2026dpc "DPC: Training-Free Text-to-SQL Candidate Selection via Dual-Paradigm Consistency (2026)") §3.4). The certificate covers *different*, never *which* (our reading).

## Verifiable signal
Only relative to the gold query: a counterexample shows generated ≢ gold, and then either one could be wrong, or both could be valid readings of an ambiguous question, which a single gold query per question ignores ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)"); Why it's hard, the ambiguity bullet). Starting from SQL instead of English ([The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop)) turns it into a checkable Q ≡ Q′ question.
