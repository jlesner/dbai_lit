# Prompt-space self-play judged by an engine

> Can a proposer–solver loop with no labels, judged only by a DSL's engine, teach a compact model through what it writes into prompts (a skill document and a library of verified examples), and does it matter whether the compact model or a frontier model writes them?

<p class="tags"><a class="tag" href="#/tags/compact">compact</a><a class="tag" href="#/tags/promptopt">promptopt</a><a class="tag" href="#/tags/rlvr">rlvr</a></p>

## Challenge
The challenge is the loop between engine-judged [self-play](#/glossary/self-play), so far run in weights, and learning kept in prompts: a proposer writes DSL problems at the edge of what the solver can do, the engine judges every answer, and what passes becomes a skill document and a library of verified examples, with the weights fixed.

## What's known
Engine-judged self-play exists, but the listed loops with a sound check learn in weights: a code executor judges Absolute Zero ([Absolute Zero](#/papers/zhao2025absolutezero "Absolute Zero: Reinforced Self-play Reasoning with Zero Data (2025)")) and SQLite judges SQL-Zero ([SQL-Zero](#/papers/pedrozo2026sqlzero "SQL-Zero: Self-Evolving Text-to-SQL (2026)")) (Proposer–solver self-play).

**The closest listed works in prompt space** (this list's one home) each lack part of the loop:
- Ctx2Skill runs prompt-only self-play that edits skill files, but an LLM with [rubrics](#/glossary/rubric) is the judge ([From Context to Skills](#/papers/si2026ctx2skill "From Context to Skills: Can Language Models Learn from Context Skillfully? (2026)") §3.3); as printed and released, the Judge sees the rubrics and the answer but not the task (§3.3, Fig. 11). Its authors name "verifiable domains, e.g., mathematics, where execution feedback or formal verification can serve as an automatic reward signal, potentially replacing or complementing the Judge" as future work (App. B).
- Voyager's GPT-4 curriculum proposes tasks from the agent's state and its completed and failed tasks ([Voyager](#/papers/wang2023voyager "Voyager: An Open-Ended Embodied Agent with Large Language Models (2024)") §2.1), and what it learns stays in prompts and a retrieved library of programs (§2.2, §6). But the game only runs the programs and returns its chat messages and errors: a GPT-4 self-verifier reading the final state decides success and admission to the library, and sometimes misses a success (§2.3, §4). Its authors say GPT-3.5 and open-source LLMs can't give the code quality it needs, though only GPT-3.5 was run (§4, §3.4), and it counts items and milestones over prompting rounds (§3.3, Tab. 1). Our reading: no setting controls task size; its judge is an LLM, as in Ctx2Skill, so what it admits is unverified; it has the loop's proposer at the frontier and its prompt-kept library, but not the engine as judge, a compact model or success as tasks grow.
- Traj-Bootstrap stores an agent's own trajectories as in-context examples, where "only successful trajectories ($s = 1$) are stored in the database", growing it "as the agent successfully completes training tasks" ([Self-Generated In-Context Examples Improve…](#/papers/sarukkai2025selfgenerated "Self-Generated In-Context Examples Improve LLM Agents for Sequential Decision-Making Tasks (2025)") §5.1), which come from each benchmark rather than from a proposer.
- CwI runs a solver's programs against code-made labels, turns failures into skills, re-runs failed programs once reading them stops helping, and delivers a library only if it beats the bare solver on a validation split ([Self-Evolving Code-with-Image Reasoning](#/papers/yang2026codewithimage "Self-Evolving Code-with-Image Reasoning (2026)") §4.2–4.3); its authors report gains for every executor (§5.3). An executor checks, but items are labelled and no proposer exists (ours).
- MEMCoder keeps test-passing code and LLM-written notes as memory, lifting 7–8B models among others ([Learning from Execution](#/papers/li2026privatelibrary "Learning from Execution: Self-Evolving Memory for Private-Library Code Generation (2026)") §VI-A); the benchmarks' own tests give the feedback, and the paper describes no held-out split (§VI-B, §VII-A; our reading).
- SynTra keeps the weights fixed and tunes a continuous system-message postfix, not text, on one program-checked task, then reuses it on tasks no program checks ([SynTra (Synthetic Transfer)](#/papers/jones2023syntra "Teaching Language Models to Hallucinate Less with Synthetic Tasks (2023)"); details: [Gains made against a checker, carried beyond it](#/challenges/transfer_beyond_the_checker) § What's known); its one task is hand-designed (ours).
- Prompt-only generator loops check their tasks weakly: SIPDO's generator writes ever harder examples, the prompt is rewritten until it solves them and all earlier ones, and labels are fixed first, checked by rules on one task and by three "expert agents" on MMLU ([SIPDO](#/papers/yu2025sipdo "SIPDO: Closed-Loop Prompt Optimization via Synthetic Data Feedback (2025)") §3.1–3.3, §4.2); FORGE's verifier is an LLM agent ([FORGE](#/papers/yuan2026forge "Failure-Guided Co-Evolution of Prompts and Training Data (2026)") § "Failure-Guided Data Synthesis"). A Lean-checked self-modifying agent draws its tasks from a fixed pool ([Self-Modifying Lean Proof Agents](#/papers/li2026selfmodifying "Self-Modifying Lean Proof Agents with Verifier-Grounded Benchmark Coevolution (2026)") §3.3).
- Open (ours): a prompt-only loop whose proposer writes tasks under a sound check.

**Across DSLs.** No listed work tests a prompt-space skill across DSLs (ours); the evidence in weights: cross_dsl_skill_transfer § What's known.

- On who writes the skill, small models write poor memories: "the effectiveness of DC is strongly tied to the model's scale and underlying generative capacity" ([Dynamic Cheatsheet](#/papers/suzgun2025cheatsheet "Dynamic Cheatsheet: Test-Time Learning with Adaptive Memory (2025)") §4.5); skill packs frontier agents wrote for themselves before solving scored below no skills on every configuration tested ([SkillsBench](#/papers/li2026skillsbench "SkillsBench: Benchmarking How Well Agent Skills Work Across Diverse Tasks (2026)") App. D.6). Yet a 9B's own skills lifted it, a 27B's more, frontier ones least, which CwI's authors call co-adaptation ([Self-Evolving Code-with-Image Reasoning](#/papers/yang2026codewithimage "Self-Evolving Code-with-Image Reasoning (2026)") §5.3–5.4); neither extractor nor writer strength reliably predicted skill value ([From Raw Experience to Skill Consumption](#/papers/huang2026skillconsumption "From Raw Experience to Skill Consumption: A Systematic Study of Model-Generated Agent Skills (2026)") §4.2; [SkillLearnBench](#/papers/zhong2026skilllearnbench "SkillLearnBench: Benchmarking Continual Learning Methods for Agent Skill Generation on Real-World Tasks (2026)") §4.2); the best agent's strategy text did little for weaker ones; its helper code lifted two of three, not the weakest ([Frontier Coding Agents Use…](#/papers/sharma2026metaprogramming "Frontier Coding Agents Use Metaprogramming to Adapt to Unfamiliar Programming Languages (2026)") §3.4).

## Why it matters
- **It keeps the weights fixed** while keeping the one thing weight-space self-play has and prompt-space loops mostly lack: a judge that can't be talked into a wrong verdict (ours).
- **It would teach a DSL with no labels at all**, since the engine makes every verdict, so the same loop serves any language with an engine ([Learning a rarely seen DSL in prompts](#/challenges/unseen_dsl_in_prompts)).
- **It answers an open question either way:** evidence on compact models writing their own lessons is mixed (§ What's known), so a compact model that teaches itself with engine feedback, or a clear gap to a frontier teacher, is a finding (ours).
- **It decides whether each DSL needs its own loop:** whether what the loop teaches in one DSL carries to another (a skill learned on XPath, tried on JSONPath or SQL). The case for DSLs counts on a skill that works across them.

**Size of the gain:** enabler, our estimate. The quantity it lifts is the one [Reliability that holds with size, by handing the procedure to an engine](#/challenges/engine_offloading_with_size) measures, the composition level at which a compact model keeps a fixed success rate, with a learned skill against zero-shot DSL use. The reason: the loop is what would turn zero-shot DSL use into a skill that holds with size.

## Why it's hard
- **Small models may write poor lessons**, and a stronger writer doesn't reliably write better ones (§ What's known, the bullet on who writes the skill).
- **Damage the loop can't see:** the Ctx2Skill authors warn that later skill edits may corrupt what earlier iterations mastered, and that "this collapse is undetectable within the loop", since each iteration's judge sees only the new tasks ([From Context to Skills](#/papers/si2026ctx2skill "From Context to Skills: Can Language Models Learn from Context Skillfully? (2026)") §3.4); each change needs a no-regression check on earlier tasks ([Self-improvement that compounds](#/challenges/compounding_self_improvement)). A check on the editing family alone isn't enough ([Scope Before You Persist](#/papers/cheng2026scope "Scope Before You Persist: Preventing Cross-Family Interference in Agent Memory (2026)") §6, Tab. 4: [Checking a memory across problems before it is reused](#/challenges/verified_memory) § What's known; the question: skill_scope_interference).
- **Lessons can be wrong though the examples passed:** a skill generalizes from verified examples, and the generalization itself is unchecked ([Checking a memory across problems before it is reused](#/challenges/verified_memory)).
- **Trivial or exploitable problems:** a proposer rewarded for difficulty can write ambiguous or degenerate tasks, and a weak check gets exploited (Proposer–solver self-play; [Weak checkers get exploited](#/challenges/weak_checker_exploitation)).
- **Leakage:** a skill must carry no facts about held-out tasks.

## Verifiable signal
Every task and answer is judged by the engine (results on the shown data and on held-out variants). The loop's effect is held-out success with the skill document and example library against without, per writer (compact or frontier), on fresh tasks the loop never saw, with a fixed thinking budget; each round's change is kept only if earlier tasks don't regress.
