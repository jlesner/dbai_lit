# Equivalence of nondeterministic queries

> What does "equivalent" mean when a query can legitimately return different results on the same database, run to run, and how do we check it without false counterexamples or false agreement?

<p class="tags"><a class="tag" href="#/tags/bounded">bounded</a><a class="tag" href="#/tags/cex">cex</a><a class="tag" href="#/tags/nondet">nondet</a><a class="tag" href="#/tags/theory">theory</a></p>

## Challenge
Many real queries have more than one correct output. Two equivalent queries (each correctly implementing the same intent) can return different results on the same database; one query can differ from itself on a rerun. The task: define equivalence for such queries, check it, and keep nondeterminism from corrupting the certified signals other challenges rely on. Most listed checkers and benchmarks model or compare a single output per query (ours; § What checkers assume, § Why it matters).

## What's known

### Sources of nondeterminism

| Source | Example | What varies |
|---|---|---|
| Row order without `ORDER BY` | `SELECT * FROM t` | Presentation only; harmless under bag comparison, yet two translation benchmarks score it ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") SIGMOD PDF §7.1, [PARROT](#/papers/zhou2025parrot "PARROT: A Benchmark for Evaluating LLMs in Cross-System SQL Translation (2025)") §4) |
| Ties under `ORDER BY` + `LIMIT` / `OFFSET` / `FETCH` | "top-1 by salary" when two people tie | *Which* rows are returned |
| Order-dependent [window functions](#/glossary/window-function) over ties | `ROW_NUMBER`, `LAG`, `FIRST_VALUE`, `ROWS` frames | Values given to tied rows |
| Arbitrary row choice | `DISTINCT ON`; MySQL non-aggregated columns in `GROUP BY` (with `ONLY_FULL_GROUP_BY` off); SQLite bare columns (with a single `min`/`max`, only on ties) | Which row's values appear |
| Order-sensitive aggregates without an order | `GROUP_CONCAT`, `string_agg`, `array_agg`, `json_agg` | Element order inside a value |
| Volatile functions and sampling | `random`, `now`, `uuid`, sequences, `TABLESAMPLE`; LLM operators such as BigQuery's `AI.IF` ([The Stochastic Shift](#/papers/alrashed2026stochastic "The Stochastic Shift: A New Evaluation Paradigm for Text-to-SQL with AI Operators (2026)") §2) | Values, or which rows |
| Errors under an unspecified evaluation order | `AND`/`OR` operand order is open, so a query whose skipped operand would raise "can succeed or fail depending on the chosen plan" ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §6.4, PDF p. 34) | Whether the query errors |
| Floating-point aggregation | `SUM`/`AVG` over floats with parallel plans | Low-order digits |
| Engine and configuration defaults | `NULLS FIRST/LAST`, collation ([Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection)) | Order or values |

The vendor manuals (accessed 2026-11-07): `DISTINCT ON`'s "first row" of each set "is unpredictable unless `ORDER BY` is used" to put the desired row first (postgresql.org/docs/current/sql-select.html, PostgreSQL 18.6, § DISTINCT Clause); with `ONLY_FULL_GROUP_BY` off, MySQL "is free to choose any value from each group" for a non-aggregated column (dev.mysql.com/doc/refman/8.4/en/group-by-handling.html, MySQL 8.4, § 14.19.3); SQLite takes bare columns from the row of a single `min` or `max`, from one of the tied rows "chosen arbitrarily", and picks a row arbitrarily under `GROUP BY` with no aggregate (sqlite.org/quirks.html § 6); the input order of `string_agg`, `array_agg` and `json_agg` "is unspecified by default" (postgresql.org/docs/current/functions-aggregate.html, PostgreSQL 18.6, § 9.21), and that of SQLite's `group_concat` "is arbitrary unless an ORDER BY argument is included" (sqlite.org/lang_aggfunc.html § 3). The floating-point row is ours: PostgreSQL computes a parallel aggregate from per-worker partial results combined by the leader (postgresql.org/docs/current/parallel-plans.html, PostgreSQL 18.6, § 15.3.3), and float addition isn't associative; none of these pages says the digits change.

### Candidate definitions of equivalence

- **Same output sets.** Q1 ≡ Q2 if, on every database, the sets of outputs each can legally produce are equal; the strongest definition. In Logos's FormalSQL semantics, sorting "admits every bag-preserving list" consistent with the sort keys ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") §3.2). An early form is Coburn and Weddell's "possible results semantics": a query denotes a set of lists ([A logic for rule-based…](#/papers/coburn1993logic "A logic for rule-based query optimization in graph-based data models (1993)") §3, printed pp. 128–129).
- **Refinement.** Q2 refines Q1 if every output Q2 can produce is one Q1 could produce. One-directional; what a *rewrite* needs, since narrowing an optimizer's legal choices is correct (ours). Coburn and Weddell define `(Ref E1 E2)` as ⟦E2⟧ ⊆ ⟦E1⟧ ([A logic for rule-based…](#/papers/coburn1993logic "A logic for rule-based query optimization in graph-based data models (1993)") Def. 4.1, printed p. 136) and use it to justify an [index](#/glossary/index-database) scan for an unordered request, the scan's order being one of the request's possible results (§3, printed p. 128).
- **Equivalence where deterministic.** Compare only on databases where both queries are deterministic (no ties, volatile values fixed). Weaker; route 1 of § Verifiable signal checks it.
- **Equivalence after normalization.** Sort rows, round floats and sort aggregated lists before comparing (LASER sorts before hashing, [LASER](#/papers/li2026laser "LASER: A Data-Centric Method for Low-Cost and Efficient SQL Rewriting based on SQL-GRPO (2026)") §4.2). This removes presentation-only differences, not *which tied rows* were chosen. Slivinskas et al. require equal multisets and equal lists on the sort keys ([A Foundation for Conventional…](#/papers/slivinskas2001foundation "A Foundation for Conventional and Temporal Query Optimization Addressing Duplicates and Ordering (2001)") §5.5, PDF p. 17), for queries with `ORDER BY`, in "some temporal variants of SQL" (§6, PDF p. 18): ties may permute, but top-k can still pick different tied rows (ours).

The use decides the definition (ours): refinement for rewrites; arguably overlapping output sets ("could these be the same answer?") for [text-to-SQL](#/glossary/text-to-sql) and the round-trip loop. Renggli et al. ask for a match "against all possible candidate results" ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)") §6.1); no evaluation method, they say, yet captures top-k answers that may be any k tied rows (§5.3.2). Some benchmarks state their notion. BIRD compares results as sets ([BIRD](#/papers/li2023bird "Can LLM Already Serve as A Database Interface? A BIg Bench for Large-Scale Database Grounded Text-to-SQLs (2023)") App. B.7). ReViSQL grades by set, subset or list; subset grading checks that an any-k answer of the right size lies within the gold's full result ([ReViSQL](#/papers/zhu2026revisql "Human-Level Text-to-SQL via Reinforcement Learning on Verified Data, Without Pipeline Engineering (2026)") §3.3.4). SQLDriller's case study of Spider training errors replaces `LIMIT 1` over tied extremes with `RANK` ([SQLDriller](#/papers/yang2025sqldriller "Automated Validating and Fixing of Text-to-SQL Translation with Execution Consistency (2025)") §6.4, Tab. 7, PDF pp. 20–21). Often the notion must be "reverse-engineered via code inspection" ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)") §6.2.2), and gets misdescribed, as Renggli et al. do BIRD's.

### What checkers assume

- **Verifiers mostly model one output per query.** VeriEQL defines `ORDER BY` deterministically ([VeriEQL](#/papers/he2024verieql "VeriEQL: Bounded Equivalence Verification for Complex SQL Queries with Integrity Constraints (2024)") §3.3) and compares sorted outputs as lists (§4.5), so on tied sort keys its verdicts rest on one tie order (ours). SQLSolver's ordered-bag equivalence requires tuples "in the same order in both results" ([SQLSolver](#/papers/ding2023sqlsolver "Proving Query Equivalence Using Linear Integer Arithmetic (2023)") §4.4, Def. 1). EQUITAS models functions as uninterpreted, equal on equal arguments, and doesn't support nondeterministic UDFs ([EQUITAS](#/papers/zhou2019equitas "Automated verification of query equivalence using satisfiability modulo theories (2019)") §3.4.1). Logos/FormalSQL keeps every legal ordered output, nested tie-sensitive top-k included; its authors rate none of the four other verifiers in Tab. 3 as fully doing so and say existing verifiers "have yet to combine" unbounded proofs with such a semantics ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") abstract; §6, Tab. 3).
- **Testers exclude the problem or assume it away.** Argus rejects query snippets with nondeterministic functions such as `RANDOM` ([Argus](#/papers/mang2025oracles "Automated Discovery of Test Oracles for Database Management Systems Using LLMs (2025)") §6.2). GQLBench leaves queries such as `LIMIT` without `ORDER BY` out of its automated SQL-to-graph-query matching ([GQLBench](#/papers/su2026gqlbench "GQLBench: A Large-Scale Cross-Domain, Cross-Dialect Benchmark for NL2GQL (2026)") App. D.2.4, PDF pp. 13–14), then calls its translations equivalent without that scope. ParSEval argues that test suites give "no False Negatives" ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §2.1), yet its released generator aims for repeated output values, which are ties when a sort key is output, and runs each query once.

Still open (ours): equivalence and refinement checks over every legal output beyond Logos's reach, with certified refutations (§ Verifiable signal); a stated definition per use in benchmarks; and a measure of how many "different" verdicts, labels and rewards come from a tie-break (SpotIt reports what share of its counterexamples survive re-execution, [SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)") §5, Tab. 2, but doesn't split the rest by cause, nondeterminism or over-approximation, §4.2).

## Why it matters
Whether a "different" verdict, an execution-match score or a reward can be trusted depends on this, in every search area (ours).

- **Labels and scores that are wrong today.** The authors of [Evaluating Cross-Domain Text-to-SQL Models…](#/papers/pourreza2023evaluating "Evaluating Cross-Domain Text-to-SQL Models and Benchmarks (2023)") count a large share of Spider, Spider-DK and BIRD queries that can return tied rows, so a correct prediction returning a different tied row is scored wrong (§1, Tab. 1). Tab. 1 counts queries that *can* tie, not ties observed; the authors suspect the test data has none (§6.1; § Why it's hard), so today's main cost may be false agreement, not false refutation (ours).
- **Rewrite checks get ties wrong both ways (ours).** Demanding equality rejects a correct rewrite that narrows which tied rows come back; one run can accept a rewrite wrong on another plan.
- **Not only SQL.** The Monkeys authors report code tests that accept only one of several correct outputs ([Large Language Monkeys](#/papers/brown2024monkeys "Large Language Monkeys: Scaling Inference Compute with Repeated Sampling (2024)") §4.2.2) and solutions over unordered sets that pass only on "lucky" runs (§4.2.1); Absolute Zero keeps only deterministic programs "to keep the verifier simple" ([Absolute Zero](#/papers/zhao2025absolutezero "Absolute Zero: Reinforced Self-play Reasoning with Zero Data (2025)") §3.3.3).

**Size of the gain:** enabler, our estimate. The quantity is the share of "different" verdicts, benchmark labels and rewards that come from a tie-break or a volatile value rather than a real difference, and of "same" verdicts that hide a difference another tie-break would show (false agreement; ours, and perhaps the larger share today: § Why it matters), in [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth), [Checking text-to-SQL against intent](#/challenges/text_to_sql_verification), [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection), [Refuting faulty rewrite rules](#/challenges/faulty_rewrite_rules), [Verified query speedups](#/challenges/verified_query_speedup) and the [The self-improving SQL ↔ text ↔ verify loop](#/challenges/sql_text_round_trip_loop). The reason: wherever a checker compares one run of each query, those numbers can be trusted only once nondeterminism is ruled out.

## Why it's hard
- **False counterexamples.** A naive execution check sees two runs differ and reports "different", even for Q against itself (ours). SpotIt traces [spurious counterexamples](#/glossary/spurious-counterexample) to over-approximated operators and to nondeterminism it can't model, and filters both by re-executing the queries, e.g. in SQLite ([SpotIt](#/papers/klopfenstein2025spotit "SpotIt: Evaluating Text-to-SQL Evaluation with Formal Verification (2026)") §4.2; a tie case in App. C). That engine's tie order then decides: SpotIt marked a surviving `LIMIT 1` tie case "ambiguous" on inspection (App. D.3, Example 11).
- **Errors are not counterexamples.** Whether a query errors can depend on the plan. In SQLite 3.45.1, two equivalent filters differing only in the order of their `AND` operands return no rows and "integer overflow" on the same one-row table (our probe). ProbeGen treats all exceptions as equivalent ([Disproving Program Equivalence with LLMs](#/papers/allamanis2025disproving "Disproving Program Equivalence with LLMs (2025)") §4); Logos counts observable failures among a query's legal outcomes ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") abstract, §3.2).
- **False agreement.** One engine often picks the same tied row every run, so two queries can agree there by accident and disagree on another engine, plan or index (ours). A database without ties hides the difference: Pourreza and Rafiei hypothesize "the absence of ties in the test data" behind the small effect of their tie-returning rewrites ([Evaluating Cross-Domain Text-to-SQL Models…](#/papers/pourreza2023evaluating "Evaluating Cross-Domain Text-to-SQL Models and Benchmarks (2023)") §6.1); Renggli et al. note that variants often agree on "a single, typically small, database instance" ([Fundamental Challenges in Evaluating…](#/papers/renggli2025text2sql "Fundamental Challenges in Evaluating Text2SQL Solutions and Detecting Their Limitations (2025)") §5.3.2); Zhao et al., that execution match on route 1's pair (or its `MIN` form) depends "on the underlying database" ([LLM-SQL-Solver](#/papers/zhao2023llmsqlsolver "LLM-SQL-Solver: Can LLMs Determine SQL Equivalence? (2025)") §4.3).
- **Sampling gives evidence, not proof.** How many runs, plans or engines show a query deterministic, or an output impossible? The latter needs reasoning over all legal outputs.

## Verifiable signal
Weak by default. It becomes a [certificate](#/glossary/certificate) in these ways:

1. **Tie-free counterexamples** (equivalence where deterministic): with unique sort keys and fixed volatile values, an ordinary execution check certifies. Cheapest, but only for pairs that also differ without ties: with `x` declared `NOT NULL`, `ORDER BY x DESC LIMIT 1` and `WHERE x = (SELECT MAX(x) …)` differ only when the maximum is tied (our probe, SQLite 3.45.1), so route 2 must separate them.
2. **Order-insensitive differences.** The outputs differ in something no tie-break can change: row count, the multiset of a column outside the tie, or a value in no tied row. ParSEval's motivating counterexample is one: the top rating is tied, and the `LIMIT 1` query returns one row whichever it picks, the other query two ([ParSEval](#/papers/chen2025parseval "ParSEval: Plan-aware Test Database Generation for SQL Equivalence Evaluation (2025)") §1, Fig. 2).
3. **Exhaustive outcomes on small databases.** Enumerate all legal outputs of Q1 (e.g. every tie-break permutation) and show that Q2's output isn't among them; tiny counterexamples keep this feasible (ours). Logos does it by proof: it accepts non-equivalence only through a countermodel checked against the complete FormalSQL semantics, with "a legal outcome on one side that no legal outcome on the other can match", or a mismatch of output signatures, never one engine run ([Logos](#/papers/ke2026logos "Logos: Certified Order-Sensitive SQL Rewrites with Mechanized Semantics and LLM Guidance (2026)") §1, §4). TRAF runs each MSSQL and Oracle SQLancer++ query in its interpreter twice, strict left-to-right and short-circuit ([TRAF](#/papers/ye2026traf "A Formal Framework for Typing and Cast Semantics in SQL Engines (2026)") §6.4, PDF p. 34), a small case of this for errors (ours).
4. **Volatile functions as parameters.** Replace `now`/`random` with a shared input value.
5. **Order-aware proofs** for the *equivalent* side.

When a "different" verdict needs one of these routes: the determinism pre-check.
