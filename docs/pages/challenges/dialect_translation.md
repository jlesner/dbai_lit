# SQL dialect translation

> Translate queries between engines (PostgreSQL, MySQL, SQLite, DuckDB, SQL Server, …) without changing their meaning.

<p class="tags"><a class="tag sub" href="#/tags/dialect-pairs">dialect-pairs</a><a class="tag sub" href="#/tags/dialect-translate">dialect-translate</a></p>

## Challenge
Migration is a separate use case from optimization. Rule-based translators exist (SQLGlot, jOOQ, SQLines), and research systems add LLMs: CrackSQL combines rules with an LLM ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §3), and RISE has an LLM translate a reduced query and turns the result into a rule ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)")). Recent papers measure translation accuracy and find frequent failures: for the rule-based tools in CrackSQL, RISE and DLBench ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.3, Tab. 1; [RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §4.2, Tab. 2; [DLBench](#/papers/lin2025dlbench "DLBench: A Comprehensive Benchmark for SQL Translation with Large Language Models (2025)") §VII, Tab. VI, PDF p. 10), and for plain LLMs in PARROT and CrackSQL ([PARROT](#/papers/zhou2025parrot "PARROT: A Benchmark for Evaluating LLMs in Cross-System SQL Translation (2025)"), [CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)")). PARROT uses rule-based tools only to annotate its benchmark (§3.2), not as systems under test. Meanwhile RISE reports its plain-LLM baseline right on most queries ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §2.2), though in a replication single prompts to a newer LLM fell consistently short of RISE itself on its benchmarks ([What Survives the Next Model?](#/papers/salsabil2026survives "What Survives the Next Model? Benchmarking LLM-Based Techniques Against Single-Prompts (2026)") §V-A, Tab. II).

## Why it matters
- **For organizations moving between engines.** The Horizon authors (Microsoft) call database migration "a common problem" for organizations that switch engines for cost, performance or features. They say vendors' rule-based migration tools don't reach full coverage, and that LLMs are being added to fill the gaps ([Horizon](#/papers/emani2025horizon "Horizon: Robust Checks for SQL Migration Using LLMs (2025)") §1). The AgentMigrate author calls migrating stored procedures "among the most labor-intensive steps in database modernization" ([AgentMigrate](#/papers/yu2026agentmigrate "Bridging the Procedural Code Gap: Agentic Database Migration with Execution-Grounded Validation (2026)") abstract).
- **Wrong translations often run.** On SQL-ProcBench, AgentMigrate reports that a rule-based converter's output runs far more often than it returns the source's results ([AgentMigrate](#/papers/yu2026agentmigrate "Bridging the Procedural Code Gap: Agentic Database Migration with Execution-Grounded Validation (2026)") abstract, Tab. 2). Gaps between "runs" and "same result" elsewhere are weaker evidence: PARROT's result metric also counts differences in format, precision and displayed order ([PARROT](#/papers/zhou2025parrot "PARROT: A Benchmark for Evaluating LLMs in Cross-System SQL Translation (2025)") §4; [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection) § Why it matters), and the CrackSQL authors attribute most of that gap, across all the methods they compare, to numeric precision and to the row order of queries without `ORDER BY` ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") SIGMOD PDF §7.4); telling the two apart is [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection). In our view, a translation that runs but changes the answer is the costly case, because a migration can ship it unnoticed.
- **For tool builders.** Rule-based translators rely on engineers writing rules by hand, and the CrackSQL authors point to SQLGlot's issue tracker for reports of wrong translations ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §1). RISE turns an LLM's translation of a reduced query into a reusable rule ([RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §3.3), which is rule discovery across dialects ([Discovering new rewrite rules](#/challenges/rewrite_rule_discovery)).
- **Pairs for checkers and benchmarks.** Translations are realistic near-equivalent query pairs ([Sourcing realistic, hard query pairs](#/challenges/query_pair_sourcing)). The CrackSQL authors note that dialect translation lacks a large open dataset of translation pairs ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §1). PARROT's reference pairs are checked with LLM-generated test data, not proved ([PARROT](#/papers/zhou2025parrot "PARROT: A Benchmark for Evaluating LLMs in Cross-System SQL Translation (2025)") §3.2, Step 4; LLM-generated test databases), so checked pairs would serve [Benchmarks with checkable ground truth](#/challenges/checkable_benchmark_ground_truth). UniQL accepts a translation automatically only when it runs and matches the source's result, and sends the rest to two annotators ([UniQL](#/papers/gao2026uniql "UniQL: Towards Dialect-Universal Benchmarking for Text-to-SQL (2026)") §3.2, §3.4); its authors say execution agreement "cannot fully guarantee semantic equivalence" (§8). PolySQL avoids translating gold queries, which it calls "inherently lossy", and compares results across engines instead ([PolySQL](#/papers/perlitz2026polysql "PolySQL: Scaling Text-to-SQL Evaluation Across SQL Dialects via Automated Backend Isomorphism (2026)") §2.1).

**Size of the gain:** incremental, measured as the share of a migration's queries and procedures whose translation returns the source's results without manual repair. In the Horizon authors' account rule-based engines already handle most schema objects ([Horizon](#/papers/emani2025horizon "Horizon: Robust Checks for SQL Migration Using LLMs (2025)") §1), though not procedural code: in one enterprise migration AWS SCT left the complex objects to manual work ([AgentMigrate](#/papers/yu2026agentmigrate "Bridging the Procedural Code Gap: Agentic Database Migration with Execution-Grounded Validation (2026)") §1, §6), and a query transpiler compiles few procedural objects (§4, Tab. 1), and recent LLM systems already report large gains over rule tools ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §7.3, Tab. 1; [RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §4.2, Tab. 2; [AgentMigrate](#/papers/yu2026agentmigrate "Bridging the Procedural Code Gap: Agentic Database Migration with Execution-Grounded Validation (2026)") Tab. 2). The step change, trusting a translation without re-testing it by hand, would come from [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection) and from checkers that model engine semantics, not from better translators. This is our estimate.

## Verifiable signal
Refutation only: run the original on engine A and the translation on engine B over the same data. Different results refute the translation, *unless* the engines legitimately differ (see [Telling bad translations from legitimate engine differences](#/challenges/bad_translation_detection)). Equal results don't prove the translation right (RISE's own limitations show a case, [RISE](#/papers/xie2026rise "RISE: Rule-Driven SQL Dialect Translation via Query Reduction (2026)") §5.2), and ACME's authors note that incorrect LLM-written clause mappings "may initially pass" its execution check on both systems ([ACME](#/papers/jiang2026acme "ACME: Automated Clause Mapping Engine for Testing Emerging Database Systems (2026)") §3, PDF p. 8). The data to run on may not be available: CrackSQL avoids execution because it "is generally not allowed in real scenarios" ([CrackSQL](#/papers/zhou2025cracksql "Cracking SQL Barriers: An LLM-based Dialect Translation System (2025)") §6), and Horizon's customers "are often unwilling to share proprietary data" ([Horizon](#/papers/emani2025horizon "Horizon: Robust Checks for SQL Migration Using LLMs (2025)") §2.2), so the refuting run needs generated data.
