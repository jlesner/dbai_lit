## Challenges

- **[Repairing and rewriting DSL programs with a certified result](#/challenges/certified_dsl_repair)**: Change a DSL program (fix it, make it safe, make it shorter or faster) and certify the result: unchanged meaning where that is the aim, or the reference's meaning where the program was wrong.
- **[Distinguishing documents for two programs in any DSL](#/challenges/dsl_counterexamples)**: Given two programs in a DSL, find an input (a document, a fact set, a graph, a string) on which their results differ, small enough for a person or an LLM to read, across the family and not only in SQL.
- **[A gym of DSL tasks with answer keys made by code](#/challenges/dsl_gym)**: Task families in several DSLs (predict a program's output, write a program from examples or from English, decide whether two programs agree and show where they don't) whose answer keys come from the engine, with a size setting on two axes, and checks whose false accepts are measured.
- **[Checking a program written from English, in any DSL](#/challenges/dsl_intent_verification)**: A program an LLM writes from an English request can be checked against a reference program, but rarely against the request itself; find checks of intent that work across the DSL family, and measure the errors they miss.
- **[Porting programs between DSLs and dialects without changing their meaning](#/challenges/dsl_porting)**: Port a program to another dialect or DSL (Cypher to SQL/PGQ, Soufflé to clingo, PCRE to ECMAScript) and show that its meaning didn't change, when engines themselves disagree silently on what the source means.
- **[Learning a rarely seen DSL in prompts](#/challenges/unseen_dsl_in_prompts)**: Can a compact model learn a DSL that is rare in its training data, K through the open-source ngn/k engine, from the language's documentation and its engine alone, with what it learns kept in prompts?
